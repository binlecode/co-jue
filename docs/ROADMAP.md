## 演进路线与待办/待决事项（优先级降序）

依据产品与体验演进路线，**人机交互面（TUI Design / Look and Feel / 美化与交互体验）全面处于最高优先级**，集中解决终端操作确定性、视觉层次感与界面审美质感；底层媒体源扩展与协议增强紧随其后。

### 🔴 第一梯队：TUI Design · Look and Feel · 交互美化专项（最高优先级）

- **【中高 ROI · 待做 · 视觉层级】三层灰阶对比规范与按键/底噪弱化（Visual Hierarchy）。**
  - **收益**：中高。全面提升 13 套内置主题的审美质感与沉浸感，向 Linear/现代极简主义对齐。
  - **核心设计**：收敛建立三层视觉层级 —— Foreground（焦点标题/发声歌词，Bold+Accent）、Secondary（时长/排序/分 P 数，中灰阶）、Muted/Tertiary（按键提示/滚动条/分割线，暗灰阶）；确保底部快捷键提示不喧宾夺主，保持内容区呼吸感。
  - **实施草案**：详见 [`docs/PLAN-visual-hierarchy.md`](PLAN-visual-hierarchy.md)。
  - **成本**：低。整理 `internal/tui/style.go` 与 `view.go` 的色阶映射。

- **【最高优先级 · TUI Design / 视觉排版 · 待决】付费权限徽章（`access`）排版与信息熵裁决。**
  - **收益**：高。优化单行视觉设计与决策信息密度。`ne` 的信封已经免费带着 `fee → access`（`full` / `preview` / `paywalled`），一枚精炼徽章能让用户在按 Enter 之前一眼预判单曲可用性。
  - **成本**：中。行模型（`internal/tui` 的 `row`）今天不带 `access`，加上它是跨引擎的数据模型改动（存储行没有这个字段），不是一处单纯的渲染改动。
  - **信息熵困境**：网易云引擎默认 `select(.access == "full")`，若全量打标，屏上每一行都是 `full`，沦为纯粹视觉噪音，且 5 字符徽章在窄屏下会挤压 CJK 歌名 2~3 个汉字宽度。
  - **待决裁决方案**：
    - 方案 A（Exception-only 异常行尾标）：默认 `full` 保持 100% 纯净（零占宽），仅在 `TING_NE_INCLUDE_VIP=1` 产生 `preview` / `paywalled` 等不可播曲目时在行尾/时长前追加微型弱化标识（如 `30s` / `VIP`）；
    - 方案 B（纯 Details 下沉）：列表行永不贴标，保持最大标题宽度与对齐容错；权威权限状态下沉至焦点行下方的 details meta 行（与播放量/年份并列）。
    - 待决核心：是否允许方案 A 在异常时微调行尾预算，还是全量收敛至零视觉侵入的方案 B。

### ⚪ 第二梯队：底层媒体源 · 数据契约 · 后台系统（次要优先级）

- **【中 ROI · 待决 · 平台闭环】真实播放进度心跳回写 (Playback Heartbeat / Watch Ping)。**
  - **收益**：中。将终端收听行为真实同步至平台云端历史，训练算法推荐模型，闭环跨端消费偏好。
  - **核心冲突与卡点**：解流期打点存在“刚播放 2 秒切歌即被标满”的算法污染，且在起播关键路径增加延迟；高质量打点需由播放器在跨过播放阈值（如 >30s 或 >50%）后触发异步打点，但需设计无分层违规的异步通知通道（保持播放器不碰平台私有知识与 Cookie）。待方案成熟后另行单独立项。

- **【中高 ROI · 待决】第四媒体源选型 —— SoundCloud (`sc`) vs 开放播客 (`pod`)。**
  - **收益**：中高。扩展纯音频生态位（独立音乐/混音 DJ 电台 或 开放播客长音频），进一步验证引擎对解耦架构。
  - **成本**：中。SoundCloud 的搜索、单曲解析与播放已实测贯通，但 Set 的 yt-dlp flat 条目缺时长，尚未闭合 `--items` 契约与请求预算；开放播客另有去中心化 host、Apple 200 集上限与 RSS 身份问题。
  - **待决核心**：SoundCloud 能否在不复制私有 API、不新增依赖且不触发请求风暴的前提下，产出完整、可分页的容器信封？失败则转为 `$TING_ENGINE_DIR` 的仓外候选，第四内置源继续开放。
  - **评审草案**：当前建议优先 SoundCloud，但只有容器完整性、请求预算、冻结契约与内置源五项判据全部通过后才确认；开放播客仍是后续候选，不预先命名为第五内置源。详见 [`docs/PLAN-fourth-media-source-selection.md`](PLAN-fourth-media-source-selection.md)。
  - **准入判据**：住在 [`docs/ARCH-engine.md`](ARCH-engine.md)「音源准入判据与已否决路线」，仓外那条路由 `$TING_ENGINE_DIR` 接住。

- **【低 ROI · 待决 · 契约改动】`c` 键能力词与引擎支持门控。**
  - **现状**：视频的分 P 就是它的 `--items`，而三个引擎都有 `--items`，所以 `c` 在 yt / ne 上也出现，按下时显示引擎自己的拒绝（「not a container」），不是静默无反应（[`docs/ARCH-tui.md`](ARCH-tui.md)「一个视图，六个行源」）。
  - **成本**：低，但它是契约改动：要一个新的能力词进 `ting-play --engines -j` 的 `flags[]`，说“这个引擎的单条媒体可能有分 P”。
  - **待决核心**：这枚键省下的一次无用按键，值不值得在公开契约里多一个词。

- **【中 ROI · 待做】队列条目的标题回填 —— `--queue-show` 会对在播的那一条报 `title:null`。**
  - **收益**：中。一个从裸句柄起的播放器（在搜索行上按 `Enter` 就是）写下的队列条目只有 url；标题是之后才知道的，而回填进的是**播放器记录**，队列文件写过一次就不再动。于是 `ting-play --queue-show` 对那一条报 `title:null`，agent 面看到的是一条没有名字的曲目。
  - **现状**：TUI 侧已经绕过去了 —— 队列视图里在播那一行借横幅的标题与 `--watch` 的时长显示，其余没存标题的项按句柄从屏上已知的行补（[`docs/ARCH-tui.md`](ARCH-tui.md)「一个视图，六个行源」）。**CLI 侧没有绕**，因为那里没有第二个知道标题的地方。
  - **成本**：中等。要在子进程解析出标题之后往队列文件写一次 —— 那是队列文件的**第六个写者**，每个曲目边界多取一次 `lock_queue_state`（[`docs/ARCH-player.md`](ARCH-player.md)「队列」的写者清单）。
  - **待决核心**：这一次写是搭 `queue_advance_from` 已有的那次取锁，还是独立一次？以及 `duration` 要不要一并回填（它同样只有播放器知道）。

- **【中 ROI · 待决】多单曲队列整体失败的判定与墓碑标准（最后一首 vs 全局失败）。**
  - **收益**：中。消除多单曲队列由于最后一首失败导致整个播放器被判定为崩溃墓碑的逻辑失真。
  - **成本**：中等。需重新梳理队列消费循环退出码定义。
  - **待决核心**：一个包含 10 首曲目的队列跳过了 1 首故障曲目，整体退出时应报 0 视为业务完成，还是记录部分失败？

- **【低 ROI · 待决】MCP 官方包装层（stdio server）。**
  - **收益**：中低。最新实测（[`docs/RESEARCH-tui-player.md`](RESEARCH-tui-player.md)「MCP 调研与 Agent 契约面」）证实外部 MCP 工具均无法托管播放生命周期；而本仓裸 CLI 契约天然可被 Coding Agent（Claude Code / Codex）无损驱动。
  - **成本**：高。需引入长连接 JSON-RPC 通信与额外运行时封装，是开启 Go 重写 NO 的唯一业务前置。
  - **待决问题**：是否需要官方封装一层 MCP stdio server，还是保持由 Agent 直接调用通用 CLI 动词？

- **【低 ROI · 待决/架构冲突】下载器归属与形态 —— 是内置动词还是保持非目标。**
  - **收益**：低。核心使用场景为背景流媒体在线播放，外部调用方已可直接调用底层 `yt-dlp` 独立下载。
  - **成本**：高。离线文件管理、断点续传、进度回调会大幅膨胀工具链，且易将轻量引擎误导为"完整下载客户端"。
  - **待决问题**：是否提供离线音视频流转存动词？还是坚持"解流与播放分离、不做完整客户端"的定位（[`docs/ARCHITECTURE.md`](ARCHITECTURE.md)「站点知识的边界」），将离线转存彻底留给外部调用方自行处理？
