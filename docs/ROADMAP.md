## 横切规范 —— 每个新功能都要过的判据

这几条不描述代码，它们是**提案的过关条件**：一条新功能、一个新键、一条新提示进来之前，
先拿它们量一遍。写在这里而不是 `ARCHITECTURE.md`，因为那一份装的是**已落地的决定**，
而这些是**约束未来**的东西 —— 与下面那些 NO 同一性质，只是形状是"必须"而不是"不做"。

- **一个功能必带 agent 面。** 人有按键，agent 就要有动词加一个 `-j` 信封。
  **理由**：这套东西的定位是 agent 优先（`ARCHITECTURE.md`「定位与设计目标」），
  一个只有键位的功能只做了一半。**它挡住的形状**：先给 TUI 加个键、"agent 面回头再说"。

- **按下前可预期 —— 分清"根本做不了"与"答案可能是没有"。**
  **一、结构上做不了的键，不许占一格**：如单引擎下的 `e`、未装存储时的 `a`/`b`/`d`，
  按前即可判定，必须在界面上门控排除。
  **二、`c`/`i` 是提问键**：问的是行内是否还有分 P 或详情，"没有"是合法答案。
  提问键由三条硬约束管理：提示进帧不偷下一个按键、否定答案带回基础元数据、单槽缓存不买第二次。
  **严禁**由 UI 启发式猜测信号（`ARCHITECTURE.md`「站点知识的边界」）。

- **只为一个答案停下来。** 界面阻塞等键，只能是因为它真的要一个**答案**（歌单名）。
  "你确定吗"不算：它会被练成连招，挡不住误操作；让操作能撤回（`z`）才挡得住。
  一条不需要回答的消息是**帧的内容**，由那唯一的渲染器画出来，下一次状态变化就没了。
  **判据**：要么进帧，要么别占屏（`ARCHITECTURE.md`「人机面」）。

- **付了的代价不丢。** 用户明确触发的网络往返，取回的数据必须落屏；不因"没有行可换"
  就把整份丢弃。

## 记录在案的 NO

每条一个形状：**决定 · 理由 · 重开条件**。已否决的方向不保留死线索与废弃执行细节，只留结论。

- **喜马拉雅 NO —— 不做喜马拉雅音源引擎。**
  **决定**：不收录喜马拉雅音源。
  **理由**：端点依赖动态令牌鉴权且缺少公开搜索接口；仅有解析没有搜索违反引擎契约（`ARCHITECTURE.md`「平级动词，没有内核」）。
  **重开**：出现免动态鉴权的公开搜索与解析接口。

- **QQ 音乐 / 酷狗 / 酷我 (TME) NO —— 不做腾讯音乐系音源引擎。**
  **决定**：不收录 QQ 音乐、酷狗、酷我等 TME 系音源。
  **理由**：API 端点深度依赖 JSVMP 虚拟机与动态 sign 签名（未登录或缺签名直接返回 `code: 2001` 强制登录）；曲库全量锁 VIP 且试听流碎片化；纯 bash 无法在零依赖下维护动态逆向算法，严重违背轻量化与低维护负债契约。
  **重开**：出现免复杂动态签名、无 JSVMP 防爬的公开搜索与免登录完整流媒体直链端点。

- **小宇宙 NO —— 不做小宇宙播客音源引擎。**
  **决定**：不收录小宇宙播客音源。
  **理由**：缺少公开 Web 搜索端点；App 端点强制校验 `x-jike-access-token` 登录态与设备指纹，第三方逆向调用面临官方风控封号惩罚；触发与「喜马拉雅 NO」相同的双半边残缺与鉴权红线。
  **重开**：出现免账号动态鉴权的公开 Web 搜索与音频直链解析接口。

- **汽水音乐 NO —— 不做汽水音乐音源引擎。**
  **决定**：不收录汽水音乐音源。
  **理由**：音频流采用私有 AES-CTR 传输加密（带 `spade_a` 密钥需本地二次解密），无法直接输出为 mpv 原生可播放直链；搜索依赖 PC 接口专有签名 Header 与临时设备标识。
  **重开**：出现提供向播放器直接输出免私有解密直链与免签名搜索的公开端点。

- **Spotify NO —— 不做 Spotify 音源引擎。**
  **决定**：不收录 Spotify 音源。
  **理由**：核心音频流受 Widevine DRM 保护，无公开流媒体直链；依赖专有二进制库（`librespot`）及 Spotify Premium 付费账号，违反零新增二进制依赖、纯 bash 3.2 胶水与匿名可用原则。
  **重开**：提供免 DRM 的标准流媒体直链与免注册公共端点。

- **ut-search NO —— 不做跨引擎聚合搜索动词。**
  **决定**：不做跨引擎合并搜索命令 `ut-search`。
  **理由**：聚合动词仅提供 fan-out 与信封合并，砍掉即消除冗余拼法（`ARCHITECTURE.md`「平级动词，没有内核」）；且各引擎数据形状互异，统一信封成本过高。调用方可直接在外部循环调用各引擎。
  **重开**：调用方明确要求输出跨引擎合并的单一信封。

- **`--vo-tct-algo=plain` NO —— viz 不提供"满格"这一档。**
  **决定**：音频可视化（viz）拒绝 `plain` 降采样算法，仅提供 `half-blocks`。
  **理由**：`plain` 降采样产生杂色与边缘模糊，牺牲显示质量；节省的字符带宽并非瓶颈。
  **重开**：终端吞吐存在极端瓶颈且画布同步下调至 `rows × 1`。

- **图片不走 mpv 的 VO NO —— 终端里画图这件事，mpv 不是那个后端。**
  **决定**：终端图片显示（封面等）严禁使用 mpv 的视频输出驱动（VO）。（封面已由 TUI 进程发射 Kitty 协议落地，mpv 仅以 `--vo=image` 充当后台转码器，详见 `ARCH-tui.md`「封面」）。
  **理由**：mpv VO 语义为独占全屏终端而非局部嵌入组件（附带清屏与夺取输入控制）；全量未压缩重传带宽开销过大；且拒绝引入外部图形库依赖（详见 `ARCH-tui.md`「封面」）。
  **重开**：mpv 原生支持不接管终端屏幕与输入的局部嵌入模式。

- **Go 重写 NO —— 引擎与播放器不做 Go 版。**
  **决定**：拒绝将引擎对、`ting-play` 与两个存储以 Go 等编译型语言重写。TUI（`ting`）不在此列：
  2026-09-24 定位改为要一张 bash 3.2 给不了的人机脸，TUI 改用 Go，只作为这套 CLI 的又一个调用方
  （`PLAN-go-tui.md`）。
  **理由**：核心价值在 CLI 契约与生命周期安全边界，与实现语言无关；引擎依赖外部站点，shell 原地可改性不可替代；重写无法消除外部运行时依赖，且带来状态机与生命周期的大规模回归风险（`ARCHITECTURE.md`「六条发现」）。
  **重开**：确需独立交付官方 MCP Server 门面。（"打包 NO 反转"这条触发器已于 2026-09-11 触发
  并复核完毕：发布 tag 与一份 tap formula 分发的**就是这些 shell 脚本**，重写理由一条未动，
  所以这条 NO 站着不动。）

- **卡片化 NO —— 列表行不套边框盒子。**
  **决定**：终端界面不做卡片/边框容器，保持纯单栏平铺。
  **理由**：一个边框盒子要吃掉 4–6 行垂直高度，而这份高度是和结果行同一份预算
  （`ARCH-tui.md`「重排与分页」：行数是量出来的，chrome 每多一行就少一行结果）；
  在 24 行终端上那是可见条目掉三成。
  **重开**：出现一个不与列表共享垂直预算的视图。

- **双栏中轴竖线 NO —— 不画列与列之间那条竖线。**
  **决定**：不做双栏布局的中轴分隔竖线，回归纯单栏。
  **理由**：一条逐行打印的竖线要求每一行左半边的宽度**精确**，而这个套件的宽度层是
  **刻意保守**的 —— 非 ASCII 默认按两格计，ZWJ emoji 量出 6 格却画成 2
  （`ARCH-tui.md`「宽度层」）。保守值够用是因为今天每一处右贴都用 CHA 落列、宁可多留空气；
  一条竖线没有这条退路，量多一格就是一行锯齿。
  **重开**：终端提供可查询的真实字符宽度，使宽度层从保守变精确。

- **按键注册表 NO —— 键位不进一张表。**
  **决定**：按键处理保持原生分支匹配，不抽象为全局按键映射表。
  **理由**：键位有效性由上下文表达式动态门控，表驱动增加维护间接层，且本套件无自定义键位需求。
  **重开**：确需支持用户自定义键位映射。

- **terminfo 探测 truecolor NO —— 不查 terminfo 的能力位。**
  **决定**：真彩色探针仅检查 `COLORTERM`，不查询 terminfo 的 `RGB`/`Tc` 位。
  **理由**：主流复用器与现代终端均透传 `COLORTERM`；宿主自带旧版 ncurses 对能力位探测存在假阴性。
  **重开**：宿主环境更新至原生支持真彩能力位，或出现支持真彩却不设 `COLORTERM` 的主流终端。

- **收听日志撤销 NO —— `ting-history` 不留撤销副本。**
  **决定**：撤销铁律只覆盖歌单与队列；`ting-history --record` / `--clear` 不留副本，也没有 `--undo`。
  **理由**：撤销副本要求"读修改前 → 写副本 → 写修改后"在同一把锁里完成，而无锁的 `O_APPEND` 追加是日志的设计前提（`ARCH-player.md`「收听日志」「撤销副本」）；`--record` 是播放器自动写的，不是用户操作，`--clear` 也没有 TUI 键。
  **重开**：`ting-history` 放弃无锁追加。

## 待办与待决事项（TUI Design / Look and Feel / 美化专项优先，按优先级降序排序）

依据产品与体验演进路线，**人机交互面（TUI Design / Look and Feel / 美化与交互体验）全面提升至最高优先级**，集中解决终端操作确定性、视觉层次感与界面审美质感；底层媒体源与非核心协议事项紧随其后。统一标明性质、收益、成本与核心卡点。

### 🔴 第一梯队：TUI Design · Look and Feel · 交互美化专项（最高优先级）

- **【最高优先级 · 待做】TUI 改用 Go，CLI 契约成为唯一接缝。**
  **收益**：高。bash 3.2 给不了的人机脸（亚秒时钟、动效、事件循环）；同时关掉 TUI 直读 mpv socket 等绕过契约的洞。
  **成本**：高。`ting-play --watch -j` 与 `ting-play --engines -j` 的 `flags[]` 两项契约已就位，剩下对齐与测试迁移，直接在 main 上替换。
  **计划**：[`docs/PLAN-go-tui.md`](PLAN-go-tui.md)。

- **【高 ROI · 待做 · 前置 Go TUI】焦点行歌词窥探。**
  **收益**：高。光标停在在播行时，details 空间内联当前一句歌词，行预算不变。
  **成本**：中。只消费 `--transcript -j --segments` 与 `--watch -j` 两个已发布动词，零契约改动。
  **前置**：Go TUI 已替换 `shell/ting`；不在 bash TUI 上实现。**计划**：[`docs/PLAN-lyric-peeking.md`](PLAN-lyric-peeking.md)。

- **【最高优先级 · TUI Design / 视觉排版】付费权限徽章（`access`）要不要上屏，以及上在哪一行。**
  **收益**：高。优化单行视觉设计与信息密度。`ne` 的信封已经免费带着 `fee → access`（`full` / `preview` / `paywalled`），一枚设计精炼的 `30s 试听` / `VIP` 徽章能让用户在按 Enter 之前一眼预判单曲可用性。
  **成本**：中。`load_rows` 现在建的是 `R_TITLE/R_DUR/R_VIEWS/R_CHAN/R_LIVE/R_ENGINE/R_RAIL`，多一个 `R_ACCESS` 是跨引擎的数据模型改动，不是一处渲染改动。
  **待决问题一（信息量）**：网易云引擎的搜索与容器默认就 `select(.access == "full")`，所以默认配置下屏上每一行都是 `full` —— 徽章会是一枚贴在每行、什么都不说的常量，只有 `TING_NE_INCLUDE_VIP=1` 时才携带信息。
  **待决问题二（归谁）**：`access` 是行级事实，而 `yt` / `bili` 没有对位字段。放状态行对其余行是假陈述；放行尾需改变行预算；放焦点行的 details meta 行不动行预算，但只说得出一行。

### ⚪ 第二梯队：底层媒体源 · 数据契约 · 后台系统（次要优先级）

- **【中高 ROI · 待决】第四媒体源选型 —— SoundCloud (`sc`) vs 开放播客 (`pod`)。**
  **收益**：中高。扩展纯音频生态位（独立音乐/混音 DJ 电台 或 开放播客长音频），进一步验证引擎对解耦架构。
  **成本**：中。SoundCloud 的搜索、单曲解析与播放已实测贯通，但 Set 的 yt-dlp flat 条目缺时长，尚未闭合 `--items` 契约与请求预算；开放播客另有去中心化 host、Apple 200 集上限与 RSS 身份问题。
  **待决核心**：SoundCloud 能否在不复制私有 API、不新增依赖且不触发请求风暴的前提下，产出完整、可分页的容器信封？失败则转为 `$TING_ENGINE_DIR` 的仓外候选，第四内置源继续开放。
  **评审草案**：当前建议优先 SoundCloud，但只有容器完整性、请求预算、冻结契约与内置源五项判据全部通过后才确认；开放播客仍是后续候选，不预先命名为第五内置源。详见 [`docs/PLAN-fourth-media-source-selection.md`](PLAN-fourth-media-source-selection.md)。
  **前置问题**：已定 —— 进仓判据住在 `ARCHITECTURE.md`「站点知识的边界」，仓外那条路由 `$TING_ENGINE_DIR` 接住。

- **【低 ROI · 待决 · 契约改动】`c` 键要不要只在有分 P 的引擎上出现。**
  **现状**：视频的分 P 就是它的 `--items`，而三个引擎都有 `--items`，所以 `c` 在 yt / ne 上也出现，
  按下时显示引擎自己的拒绝（「not a container」），不是静默无反应（ARCH-tui.md「`ting` 编排」）。
  **成本**：低，但它是契约改动：要一个新的能力词进 `ting-play --engines -j` 的 `flags[]`，说"这个引擎的
  单条媒体可能有分 P"。
  **待决核心**：这枚键省下的一次无用按键，值不值得在公开契约里多一个词。

- **【中 ROI · 待做】队列条目的标题回填 —— `--queue-show` 会对在播的那一条报 `title:null`。**
  **收益**：中。一个从裸句柄起的播放器（在搜索行上按 `Enter` 就是）写下的队列条目只有 url；
  标题是之后才知道的，而回填进的是**播放器记录**，队列文件写过一次就不再动。于是
  `ting-play --queue-show` 对那一条报 `title:null`，agent 面看到的是一条没有名字的曲目。
  **现状**：TUI 侧已经绕过去了 —— 队列视图里在播那一行借横幅的 `CURRENT_PLAY_TITLE` 与
  `CURRENT_PLAY_DUR_WIRE` 显示（ARCH-tui.md「`u` 是第六个行源」）。**CLI 侧没有绕**，
  因为那里没有第二个知道标题的地方。
  **成本**：中等。要在子进程解析出标题之后往队列文件写一次 —— 那是队列文件的**第六个写者**，
  每个曲目边界多取一次 `lock_queue_state`（ARCH-player.md「队列」的写者清单）。
  **待决核心**：这一次写是搭 `queue_advance_from` 已有的那次取锁，还是独立一次？以及
  `duration` 要不要一并回填（它同样只有播放器知道）。

- **【中 ROI · 待决】多单曲队列整体失败的判定与墓碑标准（最后一首 vs 全局失败）。**
  **收益**：中。消除多单曲队列由于最后一首失败导致整个播放器被判定为崩溃墓碑的逻辑失真。
  **成本**：中等。需重新梳理队列消费循环退出码定义。
  **待决核心**：一个包含 10 首曲目的队列跳过了 1 首故障曲目，整体退出时应报 0 视为业务完成，还是记录部分失败？

- **【低 ROI · 待决】MCP 官方包装层（stdio server）。**
  **收益**：中低。最新实测（`RESEARCH-tui-player.md` §10）证实外部 MCP 工具均无法托管播放生命周期；而本仓裸 CLI 契约天然可被 Coding Agent（Claude Code / Codex）无损驱动。
  **成本**：高。需引入长连接 JSON-RPC 通信与额外运行时封装，是开启 Go 重写 NO 的唯一业务前置。
  **待决问题**：是否需要官方封装一层 MCP stdio server，还是保持由 Agent 直接调用通用 CLI 动词？

- **【低 ROI · 待决/架构冲突】下载器归属与形态 —— 是内置动词还是保持非目标。**
  **收益**：低。核心使用场景为背景流媒体在线播放，外部调用方已可直接调用底层 `yt-dlp` 独立下载。
  **成本**：高。离线文件管理、断点续传、进度回调会大幅膨胀工具链，且易将轻量引擎误导为"完整下载客户端"。
  **待决问题**：是否提供离线音视频流转存动词？还是坚持"解流与播放分离、不做完整客户端"的定位（`ARCHITECTURE.md`「站点知识的边界」），将离线转存彻底留给外部调用方自行处理？
