## 战略重心

当前战略演进重心：**媒体源生态扩展与 Agent 契约面完整性**，集中突破内容源丰富度与 CLI 状态权威性；平台算法闭环、播放生命周期增强与边界防腐紧随其后。

## 待办与待决事项（优先级降序）

### 🔴 第一梯队：媒体源生态扩展与契约完整性（最高优先级）

- **【中高 ROI · 待决】第四媒体源选型 —— SoundCloud (`sc`) vs 开放播客 (`pod`)。**
  - **收益**：中高。扩展纯音频生态位（独立音乐/混音 DJ 电台 或 开放播客长音频），进一步验证引擎解耦架构。
  - **成本**：中。SoundCloud 的搜索、单曲解析与播放已实测贯通，但 Set 的 yt-dlp flat 条目缺时长，尚未闭合 `--items` 契约与请求预算；开放播客另有去中心化 host、Apple 200 集上限与 RSS 身份问题。
  - **待决核心**：SoundCloud 能否在不复制私有 API、不新增依赖且不触发请求风暴的前提下，产出完整、可分页的容器信封？失败则转为 `$TING_ENGINE_DIR` 的仓外候选，第四内置源继续开放。
  - **评审草案**：详见 [`docs/PLAN-fourth-media-source-selection.md`](PLAN-fourth-media-source-selection.md)。
  - **准入判据**：住在 [`docs/ARCH-engine.md`](ARCH-engine.md)「音源准入判据与已否决路线」，仓外那条路由 `$TING_ENGINE_DIR` 接住。

- **【中 ROI · 待做 · Agent 面】队列在播条目的标题回填 —— `--queue-show` 消除 `title:null`。**
  - **收益**：中。一个从裸句柄启动的播放器（在搜索行或 CLI 上以 URL 启动）初次写下的队列条目只有 url；标题由子进程异步解析后回填至**播放器记录**，而队列文件未同步更新，导致 `ting-play --queue-show -j` 对在播曲目报 `title:null`，Agent 面看到无名曲目。
  - **现状**：TUI 侧已通过横幅标题借用绕过（[`docs/ARCH-tui.md`](ARCH-tui.md)「一个视图，七个行源」），但 **CLI 契约面尚未闭环**。
  - **成本**：中等。在子进程解析出标题后往队列文件追加一次受控写 —— 引入队列文件的**第七个写者**，每首曲目起播多取一次 `lock_queue_state`（[`docs/ARCH-player.md`](ARCH-player.md)「队列」写者清单）。
  - **实现待定**：此次回填是搭 `queue_advance_from` 既有的取锁流程，还是独立取锁？以及 `duration` 是否一并回填（同属播放器独知字段）。

### 🟡 第二梯队：平台算法闭环与播放器生命周期增强（次要优先级）

- **【中 ROI · 待决 · 平台闭环】真实播放进度心跳回写 (Playback Heartbeat / Watch Ping)。**
  - **收益**：中。将终端收听行为真实同步至平台云端历史，训练算法推荐模型，闭环跨端消费偏好。
  - **成本**：中等。播放器跨过播放阈值后需发出异步通知事件。
  - **核心冲突与卡点**：解流期打点存在“刚播放 2 秒切歌即被标满”的算法污染，且在起播关键路径增加延迟；高质量打点需由播放器在跨过阈值（如 >30s 或 >50%）后触发异步打点。
  - **待决核心**：如何在保持播放器不碰平台私有知识与 Cookie（不发生分层违规）的前提下，设计可靠的异步回写通知通道？待方案成熟后另行单独立项。

- **【中 ROI · 待决 · 契约改动】多单曲队列整体失败的判定与墓碑标准（最后一首 vs 全局失败）。**
  - **收益**：中。消除多单曲队列由于最后一首失败导致整个播放器被判定为崩溃墓碑的逻辑失真。
  - **成本**：中等。需重新梳理队列消费循环退出码定义。
  - **待决核心**：一个包含 10 首曲目的队列跳过了 1 首故障曲目，整体退出时应报 0 视为业务完成，还是记录部分失败？

### ⚪ 第三梯队：防腐边界与低收益议题裁决（低优先级）

- **【低 ROI · 待决 · 契约改动】`c` 键能力词与引擎支持门控。**
  - **收益**：低。省去非容器行按下 `c` 时的一次无效调用。
  - **现状**：视频的分 P 就是它的 `--items`，而三个引擎都有 `--items`，所以 `c` 在 yt / ne 上也出现，按下时显示引擎自己的拒绝（「not a container」），不是静默无反应（[`docs/ARCH-tui.md`](ARCH-tui.md)「人机界面横切规范」与「一个视图，七个行源」）。
  - **成本**：低，但它是契约改动：要一个新的能力词进 `ting-play --engines -j` 的 `flags[]`，说“这个引擎的单条媒体可能有分 P”。
  - **待决核心**：这枚键省下的一次无用按键，值不值得在公开契约里多一个词。

- **【低 ROI · 待决 · 架构冲突】MCP 官方包装层（stdio server）。**
  - **收益**：低。最新调研（[`docs/RESEARCH-tui-player.md`](RESEARCH-tui-player.md)「8. agent 面：2026 年它不再是加分项」）证实外部 MCP 工具均无法托管播放生命周期（依赖全量守护进程的 spotuify 除外）；而本仓裸 CLI 契约天然可被 Coding Agent（Claude Code / Codex）无损驱动。
  - **成本**：高。需引入长连接 JSON-RPC 通信与额外运行时封装，是引入第三张脸（`ting` 之外第二个 Go 二进制）的唯一业务前置（见 [`docs/ARCHITECTURE.md`](ARCHITECTURE.md)「人机面 —— `ting`」重开条件）。
  - **待决核心**：是否需要官方封装一层 MCP stdio server，还是保持由 Agent 直接调用通用 CLI 动词？

- **【低 ROI · 待决 · 架构冲突】下载器归属与形态 —— 是内置动词还是保持非目标。**
  - **收益**：低。核心使用场景为背景流媒体在线播放，外部调用方已可直接调用底层 `yt-dlp` 独立下载。
  - **成本**：高。离线文件管理、断点续传、进度回调会大幅膨胀工具链，且易将轻量引擎误导为"完整下载客户端"。
  - **待决核心**：是否提供离线音视频流转存动词？还是坚持"解流与播放分离、不做完整客户端"的定位（[`docs/ARCHITECTURE.md`](ARCHITECTURE.md)「站点知识的边界」），将离线转存彻底留给外部调用方自行处理？
