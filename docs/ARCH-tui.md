# ARCH-tui —— 人机面 `ting` 的实现

**这份属于 `ARCH-*` 系列**，入口和全文档路由在 [`ARCHITECTURE.md`](ARCHITECTURE.md)。

## 模块功能和结构

**管什么**：**唯一的人机交互界面 `shell/ting`** —— 音源引擎自动发现、单一视图与行源切换、基于差量计算的终端原地重绘、双字节 CJK 字符宽度计算、终端窗口重排（Reflow）与分页、无框架事件循环与 UTF-8 多字节键位解析，以及基于 Kitty 协议的焦点行封面转码发射（`UT_IMAGE`）。
🔴 **纯编排面**：本模块不包含任何站点私有知识，亦不包含播放器后台控制逻辑；对下只通过统一命令行调度其它平级动词。

**不管什么**（边界表，走错门会得到相反的建议）：

| 事项 | 归哪 |
|---|---|
| 音源搜索与解析直链的具体站点实现 | [`ARCH-engine.md`](ARCH-engine.md) |
| 播放器进程生命周期、mpv 参数组装与持久状态库 | [`ARCH-player.md`](ARCH-player.md) |
| CLI 信封标准格式、退出码与 SemVer 约束 | [`ARCH-cli-contract.md`](ARCH-cli-contract.md) |
| 键位注册表、mpv 原生 VO 绘图等已否决路线 | [`ROADMAP.md`](ROADMAP.md) |

这个面持有渲染，且**不持有任何站点知识** —— 一条 YouTube 或 Bilibili 的事实出现在这个
文件里，就是分层违规（ARCHITECTURE.md「命令拓扑」的支配原则）。它也不持有播放与存储：
**纯编排**，对下只调那些动词；唯一被批准的例外是播放器公布出来的那个 mpv socket —— 起播那次
从 `-d -j` 的信封里拿，接管一个不是自己起的播放器时从 `--status -j` 里拿，两处都是**给的**，
从来不是照状态目录布局拼的（ARCH-player.md「运行时 IPC」）。

## 接口与 API

一个 TTY 上的键位面（键表由 `ting --help` 陈述、由 `tests/contract.sh` 的 tmux 段证明），
对下组合动词：`<engine>-search -j`、`t-playlist` / `t-history`、
`<engine>-resolve --info/--parts -j`、`t-play -d -j --engine <行自己的引擎>`。
契约面在 `ARCH-cli-contract.md`。

### 调用面 —— 选项的乘积

`ting` 的 argv 面很窄（搜索参数转发给引擎，菜单参数留给自己），但它有一个别的命令没有的
前提：**它要真 TTY，stdin 和 stdout 都要**。下面每一行 `tests/contract.sh` 都以同样的 argv、
同样的顺序真的跑过一遍（查询词是检查自己的）—— 管进 `</dev/null` 之后每一行都该落在 TTY 门上，
所以一个拼错的 flag 会先被 flag 门答掉，检查随即变红。

```sh
ting                                   # 已证 · 无 query，交互式问
ting "lofi hip hop"                    # 已证 · 直接搜
ting --engine bili -n 40 "周杰伦"       # 已证 · 转发给 bili-search
ting -f video --volume 60 "…"           # 已证 · 菜单参数：起播 mode 与起播音量
TING_LANG=zh ting --theme nord "…"      # 已证 · chrome —— 主题是 flag，语言是键（`l` 键实时轮换）
```

最后一行原来写的是 `ting --theme nord --lang zh`，而 **`--lang` 根本不是 `ting` 的 flag**。
它就那么错着，直到这一节的检查第一次真的跑它（2026-09-01）—— 这正是「示例只印不跑」的代价，
也是这一段现在长成这样的原因。

**两道门，都退 1，而且顺序是固定的**：flag 门在前，TTY 门在后。

| 组合 | 报什么 |
|---|---|
| `-f ascii` / `-f viz` | `-f must be one of: audio, video, fast` —— 它的播放**一律 detached**，终端渲染模式永远到不了一个终端 |
| 管道 / 无 pty（`</dev/null`、CI） | `requires a terminal (interactive menu)` |
| `--theme` / 标量旋钮值非法 | 点名那个键，不是笼统的用法错误 |
| `UT_IMAGE` 不是 `auto`/`on`/`off` | 点名 `UT_IMAGE`，**且在 TTY 门之前** —— 一个默认 `auto` 的能力键写错了值，最容易的失败方式是"屏幕安静地永远不画"，所以它必须出声 |

**这两道门必须靠文案分辨，不能靠退出码** —— 两道都是 1。一个只看退出码的检查，在「拒了这个
值」和「拒了这根管道」之间是分不开的，也就等于**不会失败**。套件里 ting 这一段的每条断言
都是匹配文案的，原因就是这个。

**顺序本身也是这么钉住的：喂同一根管道两次，读回两种文案。** `ting -f viz </dev/null` 报
mode 门，`ting -f video --volume 60 </dev/null` 报 TTY 门 —— 两条检查紧挨着放。单看任何一条
都与「只有一道门」自洽，两条放在一起就不自洽了：一个先查 tty 的实现会让上面那条也报 TTY 门。

## `ting` 编排（自有胶水，零站点逻辑）

图说的是*什么*，图后面的条目说的是不显然的*为什么*。

**引擎发现，以及这个文件为什么不持有源清单。** 启动时 `scan_engines` 在自己所在目录 glob
`*-search`，且只有当 `<name>-resolve` 就在旁边且可执行时才保留这个名字 —— 装了一半的引擎
不算引擎。**然后照样扫 `$UT_ENGINE_DIR`，再照样扫一遍 PATH**（三处的顺序与理由是
`ARCH-cli-contract.md`「加一个引擎 —— 清单」那一条，与 `t-play` 找 resolve 半边的顺序同一条），
同名以先看见的为准 —— 兄弟目录压插件目录压 PATH，所以插件只能加源、替不掉内置源。
于是一个光秃秃的 checkout 不装任何东西也能跑，而一个装了自己引擎的 checkout 仍看得见
外面那一对。这里曾经省过一次：PATH 只在 checkout 一个都没扫到时才扫，常见情形只花一次 glob ——
代价是**第三方引擎唯一真实的处境（旁边有内置引擎、新的那一对在 PATH 上）永远扫不到**，
于是 `t-play --engine foo` 放得出来的源，TUI 的 `e` 键一辈子轮不到它：两个面对"有哪些源"
这个问题给出不同答案，而 `ARCH-cli-contract.md`「加一个引擎 —— 清单」最后一条说的是同一件事。
省下的那次 glob 抵不上这个：3.2 下扫满 44 个 PATH 目录实测 9ms，启动时一次。
**零个引擎是致命的启动错误**，并说出缺的是哪一对。
会话从 `UT_DEFAULT_ENGINE` 起步 —— **与 `t-play` 读的是同一个变量**，不是第二个，
因为一个用户设过一次默认源之后，不该再按面设第二次 —— 那个名字不存在时回退到第一个已安装的引擎。
`e` 轮换（`cycle_engine`）并重新取数，新引擎取数失败时把上一个恢复回来；
少于两个引擎时它立即返回，这个交互也不画出来。

**升级会把工具从一个正在跑的会话底下抽走，而停播是唯一不许悄悄失败的那一次调用。**
`t-play`、`t-playlist`、`t-history` 的路径在启动时解析一次（兄弟目录优先，再 PATH）。包管理器
把每个版本装进它自己的目录，新版一落地就删旧的（Homebrew 的 cleanup 同一秒做完）；于是升级之前
打开的会话握着一组已经不存在的路径。0.14.0 发版时实测：`q` 跑的是一个被删掉的 `t-play --stop`，
`|| true` 把失败吞掉，它本该停的 mpv 在没有任何进程牵着的情况下接着放。两处改动，各管一半：
- **跑不了的路径到 PATH 上重找一次**（`relocate_tools`），因为包管理器在那里为"当前版本"留着
  一个稳定的名字。每个循环转一次、每个工具一次 `[[ -x ]]`（stat，不 fork）；文件还在就绝不重找，
  所以一个普通会话从头到尾说话的对象不会变。
- **停不掉就说出来**：横幅留着（播放器确实还在跑，而横幅是屏上唯一说这件事的东西），提示里写
  停掉它的那条命令，退出时在屏幕之外再打一遍 —— 按 `q` 时那一行是唯一留得下来的证据。
引擎不在其中：引擎调用失败本来就会以一条提示说出来，不会留下什么在后台跑。

**状态行的 `auth=` 来自引擎，不来自这个文件。** 一个源从哪个浏览器读 cookie 是站点知识，
而 `ting` 一条也不持有 —— 所以它去问 `<engine>-resolve --auth -j`
（`engine_resolve_bin`，与 `engine_search_bin` 同一条拼接规矩，不是第二张表），
取回的 `auth`/`cookie_browser` 渲染成 `auth=chrome` 或 `auth=anon`。
`refresh_engine_auth` 在**启动时**与**每次 `e` 换源成功之后**各跑一次 ——
跑在恢复窗口之后，不是之前，因为换源失败时 `ENGINE` 停在原处，而那个 token
必须描述屏幕上真正在的那个引擎。不做缓存表：bash 3.2 没有关联数组，
一次不碰 I/O 的 fork 比维护一组平行数组的正确性便宜。

它**只**出现在搜索结果的状态行上。播放列表与历史的行是**混源**的
（那一支报的是 `engine=${PLAYLIST_ENGINES}`），一个单一的 auth token 在那里
对其中一半是假话。引擎的 resolve 半边没有 `--auth` 时它非零退出、字段直接消失 ——
与 `--transcript` 缺失同一套"以有没有声明能力"的降级（ARCHITECTURE.md「站点知识的边界」），
所以第三个引擎不会被这件事卡住。

**`c` 与 `i` 给不给，也是问引擎要来的。** `refresh_engine_flags` 与 `refresh_engine_auth`
同时跑、同样缓存，问的是 `<engine>-resolve --capabilities -j`：`flags[]` 里有 `--parts`
才提供 `c`，有 `--info` 才提供 `i`。以前的办法是无句柄地调一次那个动词，再从 stderr 里分辨
"缺句柄"还是"unknown flag"。那句文案不在契约里，Go 那一侧也不该去读。仓外引擎没有
`--capabilities` 时退 1，两个键都不给：少一个键，比多一个答"unknown flag"的键代价小。

它说的是"播放会读哪个 profile 的 cookie"，**不是**"你登录着" ——
那条界线在 ARCH-engine.md「先探后播」 量过，别在 UI 文案里把它说宽。

**状态行的 `total=` 是 parts 列表特有的字段，而且它只出现在那一行上。** 它存在的理由是
搜索行的一处不一致：B 站的搜索响应**只给聚合时长**，所以一个 100 P 视频的搜索行写着
`10h:32m:03s`（实测 2026-08-29：那个数字与 `--parts` 的 `total_duration_fmt` **逐字相同**），
而在那一行上按 Enter 放出来的是**第 1 P**，12:07。两个数字都没错，错的是搜索屏上没有任何
东西说它们是两个数字 —— 而这一层修不了：要在搜索行上分辨，得对每条结果多打一次
`/x/web-interface/view`，正是 `bili-search` 最稀缺的那样东西（ARCH-engine.md）。

于是说清它的地方是 `c` 打开的部分列表，它把两个数字放在相隔一行的位置对峙：表头的
`total=` 是集合，下面每一行是它自己那一 P。第 1 P 的时长**不**在表头里再印一遍 ——
那一行就在下面，印了是 chrome 复读。`total=` 同样不印在搜索结果行上：那里没有任何东西
说"这是集合时长"，印了就是把两种数字混进一个字段。parts 列表的来源标签是 `parts=`
（与 `playlist=` / `history=` 同一条规矩）。

**状态行的 `quality=` 在 `auto` 上不印，而这是这个字段唯一值得记的一条。** `f`
（`cycle_quality`）轮换 `PLAY_QUALITY`，走的是 `cycle_mode` 一模一样的形状：纯本地、
不重取、对**下一次** Enter 生效，正在放的那个播放器留着它已经解出来的流。默认档
`auto` 不占格，与 `min=`/`max=` 在 `0s` 上不印是同一条规矩 —— 一个停在默认值上的字段
纯粹是宽度，而从没按过 `f` 的那台机器全都停在 auto 上。它排在 `mode=` 后面是因为它得
**对着 mode 读**：引擎那张表是 (mode, tier) 二维的，`high` 在 video 旁边是 1080p、
在 audio 旁边是一个码率。

这个文件不认识 yt-dlp 串，也不该认识：`f` 选的是一个**规范档位**，翻成 format-sort
是引擎的事（`quality_sort_for_tier`，ARCH-engine.md）。TUI 只是把档位原样交给
`t-play --quality`，与它交 `-f` 的方式一字不差。没有对应的 `ting` 旗标 —— 一个档位是
设一次的调音，它的入口是配置键、这个键、以及 agent 面上的 `t-play --quality`。

**键为什么是 `r`，以及为什么只绑小写。** 终端播放器里循环键的事实标准就是 `r`（cmus、
ncmpcpp、ncspot 都是），所以它是唯一一个不用教的选择；`R` **刻意不一起匹配** ——
`ROADMAP.md`「还没做的事」把大写 `R` 留给了 `b` 歌单层的重命名，一个贪婪的 `r | R` 会在那个键
被写出来之前就吃掉它。三态单键轮换（而不是 MPD/cmus 那种 `single` × `repeat` 两个正交开关）
是这条单栏界面自己的账：两个键要占提示块里两格，而这个块是**量过宽度**的。

**`r`（`cycle_loop_mode`）有三个态，而播放器只有两个 —— 这条不对称就是这个键的全部设计。**
`off` 与 `one` 是播放器自己的 `--loop` 值，按下即对在跑的播放器下发 `--set-loop`：重复是
**正在放的那首**的属性，等下一次 Enter 才生效的徽章会和音箱说不同的话。`seq` 不是播放器的
任何状态 —— 它是这个文件**怎么组装那次启动**：把光标到列表末尾的行做成一条队列交出去
（`build_queue_from_selection`），而 `t-play` 分不清这样一条队列与十次 `+` 有什么不同
（ARCH-player.md「循环」）。所以 `seq` 不下发，它的 agent 面就是本来就有的 `--queue -`。

**切到 `seq` 只对下一次 Enter 生效，并且当场说出这件事**（提示语带「下次起播生效」）。
播放中把剩下的行追加进正在跑的队列是能做的，但按两次 `r` 绕回来就会追加第二遍，而**没有任何
动词能把一个排好的条目取出来** —— 队列的审视与移除整个还挂在 `ROADMAP.md`「还没定的事」上，
一个键顺手把它定了，那不是键，那是决定。徽章因此宁可说清自己什么时候生效。

**启动时接管：屏幕开机时，音箱里可能已经在响。** 播放是脱离终端的，所以一个 `t-play -d`、
一个 agent 起的队列、或者上一次 `ting` 留下的播放器，都可能比这块屏幕活得久。从前这个文件
不问：状态块初始化成"什么都没接"，于是第一帧画一条空横幅盖在正在响的那首歌上，每一个需要目标的
键都在自己的 `[[ -n "$CURRENT_PLAY_ID" ]]` 门前变成静默空操作，而 `Enter` 会在老播放器之上
再起一个 mpv —— 两首歌同时进扬声器，老的那个因为 id 从来没进过这块屏幕，整场会话再也够不着。

`probe_active_player` 在第一帧之前问一次，**只问一次**：接管是启动时的裁决，一次 fork，不是
每拍一次的轮询（那正是读路径存在的理由，ARCHITECTURE.md「已知约束」）。0/1/多这条三岔不是这个
文件发明的 —— 它就是 `t-play` 的 `resolve_target` 从客户端这一侧读出来的同一条规矩：**恰好
一个**活播放器没有歧义，接管；**两个及以上**在那边答 `ambiguous`，这边就不比核心猜得更狠，出一条
提示、横幅留空，下一次 `Enter` 于是是用户自己的明示选择。记录进来走的是
`apply_player_record` 这唯一一个入口，接管来的标题因此和它将要盖住的那一行是**同一种**写法。
唯一进不来的事实是直播：mpv 把直播的 `duration` 报成直播边沿，信封里没有任何东西能把它和一个
长文件分开，所以这一条回头去问列表（行自己的 `live_status`），问不到就维持静态读数。

**退出时的意图表达：小写 `q` 停止退出，大写 `Q` 脱离保留。**
用户在 TUI 界面里听歌，最强烈的操作预期是"听完按 `q` 离开、音乐干净停止"（`q` 统一步入 `stop_current_playback`）。
若用户明确希望退出界面后音乐继续在后台播放（Detach），按大写 **`Q`** 即可在退出 TUI 的同时保持当前播放（`QUIT_KEEP_PLAYING=1`），下次打开 `ting` 亦会自动无缝接管。这一设计彻底解决了此前无论哪种退出都容易遗留孤儿播放器声音的交互困扰，同时闭合了 ROADMAP 中的待决议题。

**队列取料取的是行数组，不是 `$json`。** `/` 过滤改的是屏幕上的行而不是那份信封，照信封组装
会播出用户刚刚筛掉的行。每一项自带 `engine`，理由与 `play_selected` 传 `--engine` 一样：
歌单和历史都可能混来源，路由按项走。**章节行源不参与** —— `Enter` 在那里走 `play_chapter`，
那些行是同一个媒体的偏移量，顺序连播它们没有意义。

状态行上它遵守 `quality=` 那条规矩：默认态 `off` 不占一格。

**单 P 不开视图。** 引擎答 `count: 1` 不是错（ARCH-cli-contract.md 的 `--parts` 一节），
但在 TUI 里开一个单行列表是拿一次按键和一次重绘换一句废话 —— 屏幕上那一行**本来就是**
那唯一的 P。所以 `c` 在那里出的是提示（`分P: 这个视频只有一 P`），回答的正是这个键真正
在问的"这条还有别的吗"。

- **行数由两条边管，不由一个键管 —— 而"哪两条边"由列表模式定。** `page` 模式里是 `→` 越过
  最后一页追加一批（`more_results`，要一次取数）、`←` 在第 1 页砍掉一批（`fewer_results`，
  纯本地截断）；`scroll` 模式里没有页可翻，同一对函数挂在**列表的两端**（`↓` 在最后一行、
  `↑` 在第一行），而 `←/→` 是静默 no-op、连提示块里的那一格都不占。
  **一个模式只有一根轴**，这正是 `m`/`M` 退役的那条理由；两个模式各自的那根轴不同，
  但每个模式里都只有一根。两件事让这条对称成立：
  ① **涨要一次网络往返，缩什么都不要** —— 行已经在 `ALL_ROWS` 里，一个 `head -n` 就够了，
  正是这条不对称让"缩"敢绑在一个裸方向键上；② 从前只有涨没有缩，而涨是被**最被动**的手势
  撑大的（`→` 一直按到底，20 就变成 200），唯一的复原手段是退出会话。
  **`m`/`M` 因此退役**：行数已经归翻页管，再给同一个数字配一个形状不同的手势，
  是给一个事实配第二种拼法 —— `more_results()` 这个**函数**留着，只是唯一的调用方变成了 `→`。
  - **不是 `Shift+←`。** `["*D` 那个 glob 今天就把所有带修饰符的方向键吞成裸 `←`，
    要分开就得在 glob 之前匹配 `[1;2D`，然后**指望终端真的发它** —— iTerm2/Ghostty/kitty 发，
    macOS 自带的 Terminal.app 不发。在一套以"macOS 自带什么就用什么"为地板的东西里，
    一个在自带终端上静默失效的键比没有这个键更糟。而 `←` 在第 1 页今天是个死的 no-op，
    它不挤掉任何东西，还是 `→` 越过末页的**精确镜像**：同一套语法，不用修饰符。
  - **缩不印动作回显。** 状态段里那个计数自己会变，那就是反馈；涨之所以要印，
    是因为它接着要等一次网络。**地板是 max(步长, 一屏)**，到了地板就是原地不动 ——
    与这个键从前在第 1 页的 no-op 一模一样。存的是 `RESULT_N`（要了多少）而不是
    `NUM_ENTRIES`（拿到多少）：一次只有 37 条结果的查询不该把下一次查询的起点钉在 37。
- **十一个键改的设置会写回用户配置**（`mark_pref` / `flush_prefs`；机制、键表与那三条
  硬约束在 `ARCH-cli-contract.md`「配置面」「写回」，决定在 ARCHITECTURE.md「两个根数据文件」）。TUI 这一侧只有三件事
  值得记在这里：① **置脏点全都在成功路径之后** —— `cycle_engine` / `cycle_sort` 有一个
  取数失败就回滚的窗口，屏幕上是旧值，文件里就必须是旧值；② **写是延后的**，真正落盘发生在
  `nav_tick` 与 `cleanup_on_exit` 这两个现成的地方，所以连按 `t`/`l` 只付**一次**重写，
  而不是每键一次 —— 那个键循环同时还在用 `utf8_complete` 拼一个 UTF-8 字符；
  ③ 因为②，下面那个空闲时钟多了一个条件。
- **一个模式由进入它的那个键退出。** `b` 之于歌单，`h` 之于日志，`c` 之于分P，`i` 之于章节，
  `u` 之于队列：
  一个键两个方向，不用多学一个键，也不用在一个**要量宽度**的提示块里多占一格 —— 那个键在
  自己的模式开着时**自己换词**（`b back to results`），而不是旁边多出来一个键。删掉第三个视图
  那一条里早就写着同一句话，只是当时没起名字：一个"去了再回来"的键，每多按一次就少值一点。
  **`Tab` 曾经是这条规矩的一个例外**（它开的是一个视图，不是一个行源），而视图塌缩之后
  它连例外都不是了：六个行源，六个自我关闭的键，没有第七种进出方式。它如今换的是**同一个
  渲染器的两种开窗方式**，不是第二个渲染器 —— 这条规矩因此仍然成立。
  - **回去走的是暂存的那次搜索，不是重跑那个查询**（`stash_search` / `back_to_search`：
    信封、行、标签、引擎集，连同选中行与页码一起收着）。一个存储键的往返因此**零网络**，
    而且回来时屏幕上是他离开时的那些行 —— 重跑一次同样的查询未必给出同样的结果，
    "回去"就会变成一次静默的换页。暂存槽**只有一个**，这也正是 `c` 与 `i` 只在搜索行上
    可用的那条理由（`search_only`，见下）。
  - **Esc 不是这个问题的通用答案，而这是一次测量，不是口味。** `\x1b` 既是 Esc 键，
    又是每一个方向键与功能键的首字节，所以一个**孤立的** Esc 只有等过之后才知道 ——
    而 bash 3.2 没法表达比整整一秒更短的等待（`read -t` 只收整数；实测：孤立 Esc 1s，
    方向键 0s，因为它的 `[` 已经在队列里了）。ncurses 管同一个窗口叫 ESCDELAY，默认正好
    1000 ms —— 也正是每个用户都改成 25 的那个数；vim 与 tmux 落在 10 ms。C 程序用一次
    对着 tty 的 `select()` 就能拿到那个精度，shell 没有这个原语，所以 100 ms 要靠一次外部的
    单字节读。一个要一秒才应答的"返回"键读起来就是坏了，所以列表里回去的路是一个普通字节。
    **这是 shell 目前最锋利的那条交互地板** —— 记在这里是因为它是这条路的**已知代价**
    （`ROADMAP.md` 的 Go 重写 NO 把这类代价整体收下了），不是一句抱怨。
  - **那笔"外部单字节读"的税后来量了价，而量出来的数把它从一条通则拆成了一条按位置的取舍。**
    这一条原先写的是"不存在不付那一秒的版本"，那是错的：不存在的是**到处都不付**的版本。
    做法本身成立 —— tty 自己会按十分之一秒等（`min 0 time 1`），而 `dd bs=1 count=1` 正好是
    **一次** `read(2)`，于是 VTIME 管得住它，且**多一个字节都不会被吃掉**（这一点是硬要求：
    bash 自己两个读法都做不到，`read -n` 会强制 cbreak 因而照样阻塞——实测在 `min 0 time 1` 下
    仍卡到 631 ms；不带 `-n` 的 `read` 认 VTIME 却是**带缓冲**的，它按块读、留到分隔符为止、
    把**剩下的丢掉**，而 tty 上丢掉就是丢掉了——实测吞掉一次粘贴的 `\e[200~jazz\n#ch\e[201~`
    只剩 `[200~jazz`；换 `-d` 躲开分隔符则更糟，3.2 上一个撞上 `-t` 的 read **什么都不交**，
    超时返回部分输入是 bash 4 才有的）。真正决定用在哪儿的是价钱：**两次 stty 加一次 dd
    实测 ~69 ms**。方向键的字节按下时就已经在队列里，那一秒它本来一分不付，给它加 69 ms
    等于把长按导航压到一秒十来行 —— 所以列表的读取器**留着那一秒**，而且这不是妥协，是算过的。
  - **提示处正相反，那一秒是全额付、次次付的，所以提示处用 dd。** 输入本身就是文本的那些模式
    —— 实时过滤，以及三个提示（`n`，还有 `a`/`b` 背后的名称提示）——进入的那个键在模式**内部**
    就是一个普通字符（`/` 真的会出现在标题里，"beats to relax/study to"），所以 Esc 是那里唯一
    一个不是文本的键。而**启动提示**是这一族里最糟的一个：Esc 之后什么都不会来，因为程序正在
    离开，于是那一秒每次都被付满 —— 实测从按下 Escape 到进程退出 **1062 ms**，而在 shell
    提示符回来之前的一秒死屏，读起来就是卡住了。换成 tty 计时的那次读之后是 **~130 ms**。
    列表读取器与提示读取器由此分成两条，各自的注释里写着自己那一半的账。
    `dd` 是 POSIX base、与这个文件每次 resize 都要 fork 的 `stty` 同一层，所以它不是本套件
    禁止的那种依赖 —— 但"不是依赖"必须在**这台机器上是真的**，所以它被探测一次（`ESC_DD`）：
    没有 dd 的主机退回那一秒，慢，但对；不探测的话 `$(dd …)` 会交回空串，而这个函数把空串
    读成"Esc 后面什么都没有"，于是一次粘贴会关掉提示 —— 正是 `\x1b` 那条臂存在要防的那个 bug。
    唯一被吃掉的边角是 `$(…)` 挂不住结尾的换行，于是"Esc 接 Enter"读成孤立 Esc、Enter 被丢 ——
    而老读取器对它的处置一模一样（`read -rsn1` 把换行报成**空**读，落进一个没人接的 PENDING_KEY）。
- **`a` 与 `b` 共用同一段选单，它是滚动区里的一段散文，不是第二个渲染器**（`pick_playlist`）。
  它比"把存储自己的 `--ls` 原样打出来"多两样东西，而那两样就是这两个键能用的全部：一个**序号**，
  于是回答是一次按键而不是一次回忆（一行灰散文加一个与搜索提示**长得一模一样**的 caret，读起来
  是"它没给我看有哪些列表"）；以及一个用 `disp_w` **量出来的**名字列，因为 `--ls` 是按**字节**
  对齐的，而一个 CJK 名字在按字节对齐的列里根本不齐。窄面板先丢日期（<46 列）、再截名字，用的是
  这个文件里所有预算共用的那套 `truncate_disp` + 8 格下限。
  - **两个键的差别只有标题和提示语，由调用方传进来**，别的一概是同一份行为。这也是为什么
    `a` 会走这里：那个"凭记忆打名字"的 caret 在 `a` 上比在 `b` 上更糟 —— 打错一个名字在
    `b` 上是 `not_found`，在 `a` 上不报错，而是**悄悄多出一个播放列表**。
  - **读的是 `--ls -j`，不是那段散文**：选单要把名字当**数据**用（编号，再把其中一个交给
    `--show` 或 `--add`），而存储本来就以那个形状发布它们。这一次取用 `list_playlists`，
    一份，两个键共用 —— 那十行（errfile、rc、两步扒错误前缀）正是 F11/F12 里飘走的那种复制。
  - **空存储是这两个键唯一分岔的地方**，因为同一个 0 对它们意思不同：对 `b` 是死路，就地答掉
    （"还没有播放列表"），而不是去提示一个不可能存在的名字；对 `a` 那恰恰是一个列表开始的
    地方，于是问题换成"新列表叫什么"。
  - **序号在 TUI 里就解析掉**，于是 `t-playlist` 从头到尾只听得懂名字，`open_playlist` 交出去
    的还是它本来要的东西。序号**压过**同名的数字：屏幕上那个数字才是用户看见的东西，而一个真名
    叫 `7` 的列表照样够得着 —— 用它自己那一行的行号。提示器仍然是 `prompt_name`，也就是 `n`
    与 `a` 用的同一个读取器（UTF-8 组装、退格宽度、取消契约都只有一份）。
- **`d` 从它所在的那张歌单里移出一行**（`delete_from_playlist`）。它不先问 —— `z` 能撤回
  （见「可撤销取代预先确认」）。三件事把它和别的存储键分开：
  - **它只在歌单视图里存在。** 键条里那条"不能动作的键不许占一格"的规矩（`e` 在单引擎装机上
    遵守的那条）在这里表现为：`d` 只在 `LIST_SOURCE == playlist` 时才画出来，按在别处由
    `playlist_only` 答掉 —— 它是 `search_only` 的镜像。**不是 `stored_rows`**：收听日志也是
    存储，但 `t-history` 的全部动词是 `--ls --record --clear`，没有按行删除这回事，所以那里
    的 `d` 根本没有可调用的东西。
  - **交出去的是索引，而索引是从行的身份算出来的，不是 `selected`。** 今天这两个数恰好相等，
    但那是靠**另一个函数**的不变量（`filter_live` 退出时必然 `apply_filter ""`，所以主循环里
    永远看不到过滤子集），而它一旦变了，代价不是少删一行，是**删错一行**。所以
    `focused_index` 用 url **加上它的出现序号**（上方有几行是同一个 url）去查存储：歌单允许同
    一个 url 存两次，那时"第一个匹配"未必是光标所在那行；而两边都是条目顺序，于是视图里的第
    k 次出现就是存储里的第 k 次出现。查不到就是屏幕和存储已经不一致，此时**拒绝**而不是拿一个
    可能指向别人的索引去删。
  - **删掉的那一行如果正在放，播放器跟着停**（`focused_is_playing`）。这个耦合只有这一层说得
    出来：播放器不知道歌单（存起来的一条是一个**调用**，不是一个引用），存储不知道播放，"这一行
    既是存储的第 N 条、又是播放器手上那一条"是两个事实的交集，而只有 TUI 同时握着这两个。判断
    用的是渲染器判 `PLAYING_IDX` 的同一套词汇（行的 engine 加 `handle_key` 归一化后的 handle），
    不另起第二种拼法；但 `PLAYING_IDX` 本身在这里用不上 —— 它是重绘里对**可见页**算出来的，答的
    是"这一页哪一行在放"，而 `d` 问的是某一行，且此刻没有重绘跑过。**问在删之前**：`reload_playlist`
    会把 `selected` 指到补上来的那一行，之后没人还记得删的是哪一行。**停，但不是现在**：撤销提示
    开着时停播挂起到它关闭，因为停掉的播放器是撤销唯一放不回去的东西；存储没给撤销（信封里没有
    `undo`）时才当场停，而且**停在重读之前**，否则重读收尾的那一帧还会给一条存储里已经不存在的
    行画横幅。
  - **删完就地重读，光标留在原处**（`reload_playlist`）。重读用的就是 `open_playlist` 本身
    （它取的 stash 对已经属于存储的行是 no-op），所以没有第二份 show+build+load；额外做的只有
    光标 —— 删三首歌否则就是三趟从头往下走。重读失败（包括列表被删空）就回搜索，因为那一条已经
    没了，屏幕上的行是过去的照片；空列表说的还是 `b` 开空列表时的那句话，因为那是同一个事实。
    **删空的列表留着**：移出最后一首不是删列表的请求，在那一刻问"要不要把列表也删了"，是在问
    用户没来回答的问题。它照常出现在 `b` 的选单里（0 首），删它是 `D` 的事。
- **`D` 与 `R`：歌单生命周期的 TUI 闭环**（`delete_current_playlist` 与 `rename_current_playlist`）。
  底层 `t-playlist` 具备 `--del` 与 `--rename` 能力，此前在 TUI 中一直缺失交互入口：
  - **`D` 彻底删除当前歌单**：仅在 `LIST_SOURCE == playlist` 下生效，不先问；调用 `$PLAYLIST_BIN --del`
    成功后退回搜索结果视图，提示位上是删除结果与撤销提示。当前播放器若在放这张歌单里的曲目，停播与 `d`
    一样挂起到撤销提示关闭。
  - **`R` 原地重命名歌单**：仅在 `LIST_SOURCE == playlist` 下生效，借由通用 `prompt_name` 输入新名称并调用
    `$PLAYLIST_BIN --rename`；成功后原地将 `PLAYLIST_NAME` 与 `QUERY_LABEL` 替换为新名称，不重读磁盘也不发网络请求，
    由单视图原地重绘完成响应；重名或非法输入直接通过底层退 4 错误由 notice 承接。

- **播放是异步、非阻塞的，走 `t-play -d -j --engine`。** 引擎取自搜索信封，绝不留给播放器的
  默认值（ARCH-cli-contract.md「门模型」）。`play_selected` 用一次 `jq` 从那个信封里读出
  `id`/`pid`/**`sock`**，从不自己重建 socket 路径（ARCH-player.md「运行时 IPC」）。
  播放在一个独立的 detached 进程组里启动，于是 `ting` 保有对终端的完全控制。
  用户浏览结果、翻页、发起新搜索（`n`）时音频不中断。在任何一行上按一次 `Enter`，
  干净地停掉上一个播放器并启动新选择，没有延迟。
- **一个视图，六个行源。** 屏上永远是**同一个渲染器**画出来的那一张列表：多行结果、顶部
  Now-Playing 横幅、选中行的 details 段。变的只是那些行**从哪来** —— 搜索、歌单（`b`）、
  收听日志（`h`）、一条视频的分P（`c`）、一条视频的章节（`i`）、在播播放器的队列（`u`）——
  每一个都由**进入它的那个键**退出。`display_menu` 因此不再分派：它开关 DCS 帧保持，然后调 `display_list_menu`。
  - **一条提示是帧的内容，不是一次停顿。** 行源答不开门的时候（日志是空的、只有一 P、
    没有章节、取数失败），它记下一条提示（`store_notice` 只赋值），由**同一个渲染器**画在
    标题行底下、计进 `chrome_h`，然后把 **1** 交回菜单循环 —— 那是"没开成"，不是"坏了"。
    提示活**恰好一帧**：`read_nav_input` 一拿到真按键就清掉它（清在那儿而不是在两个循环里，
    是为了让它只有一个主人；清在**时钟**上则会让播放中的提示只活一秒，读不完）。
    **它曾经是模态的** —— `printf` 进滚动区加一次阻塞 `read` 把它按在那儿 —— 而那个形状
    收过两次账：一次是这里的 **1** 在 `set -e` 下恰好死在那次**用来撤下提示的按键**上
    （`h`/`c`/`i` 三条 case 臂上的 `open_… || true` 就是那道疤，今天仍留着，`Enter` 那条
    同形），一次是 `tests/contract.sh` 的章节走行不得不先喂那个读取器一个 `Space`、再等提示
    消失才能发下一个键，于是走行与自己上一圈赛跑而变得 flaky —— 一个检查在替设计还利息。
    债本身是：**一条模态消息让下一个键同时是两件事**（撤提示，或命令），而用户分不清自己
    按下的是哪一个。所以界面只在真的要一个**答案**时才停下来
    （`ROADMAP.md`「横切规范」只为一个答案停下来）：`prompt_name`（歌单名，`a`/`b` 的选单也是
    它）留着自己的阻塞读，因为它里面真有一个问句。曾经的另一个 —— `y/N` 确认 —— 已由撤销取代。
    提示行是**钳的、绝不折行** —— 正文可能是引擎 stderr 的一行，而折出来的那一行正是
    测量链要防的那种高度。
  - **首发搜索一条没中，同样是一帧，不是一次退场。** 这条原则最后一个例外在启动路径上：命令行
    给的第一个查询打错一个字，这里曾经直接 `die`，会话在任何东西画出来之前就结束 —— 用户丢掉的
    不是那次搜索，是整个菜单循环：改词的 `n`、拿同一句话去问另一个音源的 `e`、以及压根不需要
    网络的 `b`/`h`。如今它走上面同一条路：记一条提示，配一张没有行的列表；空行文案说的还是
    `b` 开空歌单时的那句话，理由与上面共用那一句时相同。**只对"搜到了、零条"** —— 引擎自己
    坏掉仍旧 `die`，因为那时屏幕上没有任何可以操纵的东西，而引擎的 stderr 是唯一值得说的那句。
    代价记在这里：这是**唯一**一条 `fetch_json` 没成功过一次就进菜单循环的路径，于是那一次
    取数本该留下的两样东西要在原地补齐 —— 那份**信封**（它是 `focused_payload` 切行、
    `back_to_search` 存取的那个 jq 文档，不能是一张空行表），以及**当前引擎**（一条不带
    engine 标签的存储行按 `Enter` 时的回落值，空在那里就是唯一能把 `--engine ""` 递给
    `t-play` 的口子）。
  - **`c` 与 `i` 是提问键，`b`/`h` 不是，两类的规矩不一样。** `b`/`h` 按下之前就知道自己
    答不答得上（那个存储装没装），答不上就不占提示块的一格。`c`/`i` 问的是"这一行里面还有
    没有东西"，而**答案不在已经取回的那一页里** —— 实测 2026-09-03：B 站一条真 200P 的行与
    一条 5 分钟 MV 的搜索键集逐字相同，YouTube 的 flat 条目里没有任何 chapter 字段，
    要这个信号就得每行加一次往返（三个站的数字在 `ROADMAP.md`「横切规范」按下前可预期）。
    所以它们**不**按行门控，改为各自欠三件事：不偷走下一个按键（上上条）、否定的答案也把
    买到的东西带回来（上一条）、以及**同一个答案不买第二次** —— `fetch_item_info` 与
    `fetch_item_parts` 各持一个单槽缓存，键是 `{engine, url}`。后者是 2026-09-03 补的：
    在一条单 P 视频上按两次 `c`，原来要付两次往返去拿同一个"没有"。
  - **`--info` 那两个字段属于一**行**，不属于一个视图。** 上传日期与点赞数是 `i` 那次往返
    买来的、而任何一行都装不下的东西，所以它们画在**光标正站在那一行上**的时候
    （`info_is_focused`），而不是"章节列表开着"的时候。差别只在一种情况下看得见，而那种情况
    恰恰是常态：**这一条没有章节**。视图开不成，可那次往返已经付过了 —— 旧代码连同没开成的
    视图一起把它扔掉（`ROADMAP.md`「横切规范」付了的代价不丢）。判据是 `{engine, url}` 那一对，
    与 `chapter_span` / `play_chapter` 问的是同一个问题；`handle_key` 会剥掉 `t=`，所以一张
    章节列表里**每一行**都答"是"，于是**一个**判据同时服务两个视图，而搜索视图里只有当初按下
    `i` 的那一行答"是"。光标移开就不画了，缓存还在（再按 `i` 不付第二次往返）。
  - **第二个渲染器是被删掉的，不是没做出来。** 曾经有一张全屏的 Now Playing 焦点卡，`Tab` 切进去，
    带两个主语（在播的那条 / 你按 `i` 问的那一条）。它在 100×30 上只填满 27%（30 行里 8 行），
    换来的是**一个状态两个渲染器** —— 而这正是这份文档一直用来否掉 "mini player" 的那条理由。
    删它是把那条理由用在自己身上：**要么把整屏挣回来，要么别占它**。
    `Tab` 因此**空了出来，并且当时刻意不派新活** —— 一个空着的键比一个硬塞的功能好，
    而"不能动作的键不许占一格"那条既有规矩自己就把它从提示块里请了出去。
    它在 2026-09 重新有了东西可以够：`scroll` ◄──► `page`，**同一个渲染器的两种开窗方式**。
    这不是把卡片放回来 —— 判据没变，还是"要么把整屏挣回来，要么别占它"，而两个模式共用
    `display_list_menu` 的同一段代码，分支只在"窗口怎么算"和"哪根轴管扩缩"两处。
  - **纯显示的损失，直说。** 列表布局一格没改（这次改动**不含任何样式工作**），所以卡上那些
    在列表里没有槽位的东西是**丢掉**的，不是搬走的：大标题、**前方队列块**、条目的**简介**、
    以及元信息行里那个 `selected`（引擎挑中的 format）。丢的全是**画面**，**没有一个能按的键**
    跟着走：`+`/`>` 照旧写队列，`f` 照旧轮换档位，`[`/`]`/`9`/`0`/`Space` 照旧。
    - 队列的**位置**留下了，因为它是 `+` 在屏上唯一的回执：状态行在队列长于 1 时印
      `queue=pos/len`（`CURRENT_QUEUE_POS`/`_LEN`）。队列的**尾巴**（`upcoming`）没有留 ——
      读它的只有那个块。
    - 进度条一个字没动：它本来就是**列表那条 rail**（`render_prog_bar`，见下面"列表那条 rail"），
      卡片只是当初也用了它。
  - **`i` 是第五个行源：把章节变成行。** 一次 `<engine>-resolve --info`，按 `engine:url` **单槽**
    缓存（`INFO_CACHE_KEY`/`INFO_CACHE_JSON`，会话内有效、不落盘）；`chapters[]` 经
    `build_chapter_rows` 变成一个 `{items:[…]}` 信封，再交给**歌单那个同一个** `build_playlist_rows`
    走完。`i` 读的是**那一行自己的** engine，与 `Enter`、`c` 同一条规矩。
    - **这个源叫 `chapters`，2026-08-31 之前叫 `versions`。** 源名不是内部名：`stored_rows` 的
      源名**就是**头一行印出来的字段名（`chapters='<标题>'`，与 `playlist='<名字>'`、
      `parts='<标题>'` 同形），所以一个错的源名，错在整个视图唯一一行"告诉你在看什么"的地方。
      `parts`/`history` 读得通是因为它们本来就是对的词；`versions` 不是这个键做的事。
      函数、信封变量与提示块那一格一并改名 —— 一个东西一个名字，不留第二种拼法。
    - **一个章节行是一个区间，rail 就印区间**（`0:00 → 2:30`）。从前它印**起点**一个数，
      而且是在搜索行印"这条有多长"的**同一列、同一种拼法**里 —— 于是屏上那一个数在两张
      除此之外一模一样的列表之间换了意思，还没有任何东西说一声。一个区间读不成一个时长。
      - **区间在 `build_chapter_rows` 里就拼好**，而不是渲染时从相邻行推：实时过滤与翻页会
        重排屏上的行，所以"下一行的起点"不是这一章的终点。它是记录里**第八个**字段
        （`rail`，见下面的行记录），也是唯一一个已经是显示形态的字段 —— 这正是它的用途：
        一行可以自己点名它的 rail，不点名的源留空、照旧走 `short_dur`。
      - **箭头是一列。** 各自右冲会把**终点**对齐、别的什么都不对齐：`5:42 → 8:00` 与
        `8:00 → 11:32` 的箭头差一格，过了一小时差四格 —— 于是全屏唯一一列供眼睛往下扫的东西
        自己在动。所以每条 rail 都建成**同一个宽度**：两个时间各自在一个字段里右对齐，
        字段宽度**按整张表**取最大（不是按页 —— 一列会随翻页重新对齐，那还是同一列毛边，
        只是晚一点才发现，与行号字段按 `NUM_ENTRIES` 定宽同一条理由）。代价是还没到一小时的
        那几页在箭头后面留着给 `1:0x:xx` 的位置；那正是对齐的价钱。
      - **终点取引擎自己的 `end_time`**，没有这个字段时区间半开（`2:30 →`）、`duration` 缺席，
        而不是猜一个：最后一章的长度要拿条目总时长去减，而这个视图不读条目总时长。
      - **`duration` 是这一章的长度**（秒），`duration_fmt` 是同一个数的 wire 拼法。从前这两个
        字段装的是**起点** —— 一条被 `a` 存进歌单的章节，回来会声称自己长 2 分 30 秒，
        因为那是它开始的地方。details 段、`a`、`+` 现在拿到的都是真时长。
    - **它建的是信封而不是行**，因为 `a` 与 `+` 是从 `json` 里切一条出来的（`focused_payload`）：
      一个 json 与自己的行对不上的行源，是一个能放但存不了的列表。
    - **和 `c` 一样只在搜索行上可用**（`search_only`）：暂存槽只有一个，从歌单里再开一层
      要么丢掉回搜索的路、要么需要一个栈，而栈是另一个单元的事 —— 返回栈只有一层，
      上面那条暂存规则就是它的全部。
    - **没有章节就出一条提示、原地不动**，与 `c` 在只有一 P 时的答法同形：一个空列表要花一次
      按键和一次重绘去说一句"没有"。
    - 状态行捡起那次取数付过、而行装不下的两格：`uploaded=` 与 `likes=`。`--info` 的读取也
      **从八个字段减到三个** —— 频道、时长、播放数本来就在按 `i` 的那一行上，而简介没有了去处。
  - **一个章节行是一次调用，不是一条引用 —— 而这一条 2026-08-29 曾被否掉过。** 当时的理由是
    "章节当行会逼着条目记录长出一个起始偏移字段，并让它蔓延进歌单、队列与历史"。
    **0.4.0 之后那条理由失效了**：`start_seconds` 已经是 resolve 信封的字段，每个引擎都从句柄的
    `?t=` 里读它（`ARCH-engine.md`「起播偏移」）。所以行的 url 就是**带 `t=<秒>` 的那个句柄**
    （`chapter_url`，先把已有的 `t=` 剥掉 —— 带两个 `t=` 的句柄从哪一秒开始取决于解析器往哪看），
    记录**一个新字段都不用加**：`Enter` 从那一章起播、`+` 从那一章入队、
    `a` 存下来的也是从那一章起播的一行。偏移**随行走**，所以实时过滤重排了行也不会错位
    （一个平行数组会）。
  - **`Enter` 在章节行上的两个分支，是同一件事。** `play_chapter`：播放器手上已经是**这一条**
    （engine 与去掉 `t=` 的句柄都相等）就走 `t-play --seek-to <秒>` —— 章节是**已经打开的那个
    文件里的一个偏移**，所以是一次 seek，永远不是一次 re-resolve（这正是这条轴与 `--parts`、
    `--quality` 的分界，ARCH-cli-contract.md「命令规格」）；否则照常 `play_selected`，偏移在 url 里。
  - **`u` 是第六个行源：把在播播放器的队列变成行 —— 也是唯一一个能写的行源。** 一次
    `t-play --queue-show -j`，信封与歌单同形，于是行由 `build_queue_rows` 走完
    （只改两个字段，见下面的行记录）。`+` 是盲写，`u` 是看见自己写了什么，两个键合起来才是
    一件完整的事。
    - **它是这个文件唯一一处会改别人状态的行源，而它一个字节也不碰 `queue-<id>.json`。**
      队列文件的属主是播放器，而且它**有两个写者**（`--enqueue`/`--next` 在父进程里，子进程的
      `queue_advance_from` 在每个曲目边界上），两者靠 `lock_queue_state` 分开。从这里直写会
      绕过那把锁。所以每一次改动都是一条 `t-play` 动词：`--queue-rm` / `--queue-mv` /
      `--queue-jump` / `--queue-clear`（ARCH-player.md「队列」）。
    - **整条队列都在屏上，不只是待播那一段。** 只印 `pos` 之后那一段会让屏上的行号与动词吃的
      `index` 变成两套编号，中间隔着一次心算 —— 一个事实两种拼法。已播的行通常只有一两条，
      往上翻还能看见刚才播过什么。
    - **在播那一行按位置认，不按 url 认 —— 这是它与另外五个行源分道的地方。**
      `PLAYING_IDX` 默认按 url 匹配（重排、过滤、翻页都会动索引而 url 不动），但队列**允许同一
      首出现两次**（`+` 按了两遍，或歌单里本来就有两份），那时 url 匹配会给**第一份**上底色，
      而在播的是 `items[pos]`。屏上于是同时有三个东西回答"我在哪"（光标、底色、状态行的
      `queue=pos/len`），其中两个打架 —— 而这个视图不印 `PLAY` 列，没有第二个真相来源能纠正它。
      判定因此是行记录里**第十个字段**（`R_N`，队列行放自己的 `index`）与 `pos` 相等，
      **不是**屏上位置与 `pos` 相等：`/` 不按行源门控，一次过滤就让第 N 行不再是第 N 条。
      顺带比它替掉的 url 归一化更便宜 —— 每个可见行一次整数比较。
    - **只从搜索行源进出。** 暂存槽只有一个（见上），从歌单上按 `u` 会让 `back_to_search`
      把人丢回搜索、歌单就丢了。与 `c`/`i` 的 `search_only` 同一个约束，但这里印一条**说明**
      而不是套用那条通用提示：`u` 与焦点行无关，所以"这里不行"欠一个理由。
    - **队列只有一条时不开门。** 每个 detached 播放器都有队列文件（一个裸句柄也是长度为一的
      队列），所以"队列为空"不是一种状态；"里面只有正在播的这一首"才是，而那时视图里每个键
      都只会拒绝。同一条规矩也决定了提示块里 `u` 那一格在什么时候出现。
    - **在播那一行的标题与时长可以由横幅补。** 播放器若是从一个裸句柄起的（在搜索行上按
      `Enter` 就是），队列条目里除了 url 什么都没有 —— 标题是**之后**才回填的，而且回填进的是
      **播放器记录**，队列文件写过一次就不再动。于是横幅顶着标题、底下那一行印着 url。
      补的是同一个事实的同一个来源（`CURRENT_PLAY_TITLE` / `CURRENT_PLAY_DUR_WIRE`），不是第二
      份真相；`--queue-show` 那一侧的同一个缺口记在 ROADMAP.md 上。
  - **URL 直贴与外部容器接入：单视图的原生承接。**
    用户从浏览器复制 URL 进入 `ting` 时，系统在三处入口统一前置分流（终端 Bracketed Paste、`n` 搜索输入框、CLI 冷启动 `ting <URL>`），绕开 `<engine>-search` 对 URL 的阻断门，由 `load_url` 完成原地解析：
    - **单曲 URL：非破坏性聚焦，不中断当前收听。**
      通过 `<engine>-resolve --info -j` 获取元数据并投影为单条搜索记录置于 `ALL_ROWS`，光标高亮停留在该条目上。用户可按 `Enter` 立即起播、按 `+` 静默入队、按 `a` 收藏至歌单、按 `c`/`i` 查看分 P 与章节。坚决不走“贴上即粗暴切歌”的侵入式设计。
    - **容器 URL：复用播放列表视图展开全量曲目。**
      对歌单、专辑、合集等容器链接，调用 `<engine>-resolve --items -j` 获取条目列表，通过 `stash_search` 暂存前序搜索状态，将清单全量展开并复用 `build_playlist_rows` 载入单视图（`LIST_SOURCE="playlist"`）。用户可自由上下翻阅收听，并通过 `b` 键（`back_to_search`）一键原路返回前序搜索视图，彻底打通人机界面直达外部容器的闭环。
    - **双向互降兜底**：单曲解析若遇容器报错（如 B 站音频歌单或网易云非 song 路径），自动回退至 `--items`；反之容器解析若遇单曲，自动回退至 `--info`，消除边界形态的误判。
  - **仍然没有第三个渲染器，理由没变。** 一个 "mini player" —— 用三行渲染同样那几个事实 ——
    会是一个状态两个渲染器，也就是会漂移的重复。今天这个数是**一个**，而不是两个。

  - **防闪烁的原地渲染，应用里再没有一处 `clear`。**
    1 秒一拍的实时刷新靠 `\033[H`（光标归位）平滑更新时间与进度条，不做整屏抹白、也不闪。
    正因为什么都不抹，**一帧发出的每一行都必须带 `\033[K`** —— 空白的间隔行也不例外。
    一帧的高度会变（提示块按宽度折行、details 块按标题折行、进度条要等 mpv 头一秒的
    `time-pos`），而一个没擦的间隔行会继续显示上一帧画在那一行上的东西。

    一次以 `clear` 开场的重绘 —— 先抹白、再重画，一帧两个可见状态 —— 会让任何按键都把整个
    列表闪一下，而暂停/恢复把这一点暴露得最清楚，因为真正变化的只有横幅里的一个字形。
    DCS 帧同步只在支持它的终端上把"先白后画"藏起来，而在 tmux 下同步默认是关的，
    于是什么也藏不住。`display_list_menu` 的做法是：
    归位光标、边画边擦，以一个 `\033[J` 收尾，而暂停/恢复恰好重画**一行**
    （一行变化、零个 `ED` 序列 —— 用 `tmux pipe-pane` 的流在两个标记之间数 `ED` 量出来的，
    因为 tmux 在 pane 打开时会自己发一个 clear；这是一条**记录下来的测量**，
    不是一条被守着的断言 —— 数 `ED` 是对画面本身做断言，而套件不做那件事）。
    换行源（`b`/`h`/`c`/`i`）同样不 `clear`：帧以 `\033[J` 结束，进来的那一帧盖住出去的那一帧，
    应用里再没有一帧空白。

    这个渲染器有而当初那张卡没有的两个细节：
    - **在结果行上，`\033[K` 放在最前面，不是最后。** 时长轨是用 CHA（`\033[<n>G`）定位的，
      它**跳过**标题与轨之间那些格子而不写它们，所以尾随的擦除会让上一帧更长的标题从那个缝里
      透出来。**先擦、再画**是唯一能盖住"画本身从不触碰的那个洞"的顺序。
    - **过滤输入行的光标用一个 `\033[J` 收尾。** 它一次擦掉那一行的其余部分**以及**下面的每一行，
      并把光标留在下一个键入字符必须落到的位置 —— 前面再加 `\033[K` 是多余的，而移动光标是错的。

    **这没有改变什么：一次按键仍然重算并重写整帧，而这是有意的。** 走掉的是终端*显示*的状态数
    （白，然后画好 → 画好），不是工作量。每个键处理器都以 `continue` 结束，循环顶端调
    `display_menu`，而 `display_menu` 是屏幕唯一的写者 —— 没有脏区跟踪，也没有局部重绘路径。
    在 100x30 的 pty 上实测：一次暂停发出 **2413 字节、耗时 15–24 ms**，
    与真有四行变化时一次下箭头发出的帧逐字节相同。

    重算的代价就是 reflow 的代价。列表几何是**每帧测量**的，不是固定的：`PAGE_SIZE` 是
    `LINES_N` 减去量出来的 chrome，`print_hints` 按宽度打包（1–4 行，行数随 chrome 语言变化），
    而 details 块有多高取决于选中标题折了多少行 —— 所以一帧要读一次 `stty size`、跑一遍提示打包、
    跑**两遍** `print_details`（先量后画），并把每一行过一遍 `truncate_disp`。
    任何状态变化都*可能*挪动那份几何，所以渲染器选择重算，而不是试图知道"什么时候它不会变"。

    暂停是唯一一个**可证明**不会挪动几何的变化 —— 一行之内的一个字形加一个词，
    而那一行的长度省略早就定死了。只重画那一行考虑过并被否决：它需要横幅的**绝对屏幕行号**
    （今天 `chrome_h` 是**边画边累加**的，它不是一张任何东西都能查的行号表）、需要一次 CUP 或
    save/restore 去够到那里，而且横幅的标题省略还是得重算，因为那取决于 `nav_cols`
    以及导航块有没有被丢掉。结果会是**第二条覆盖第一条子集的绘制路径**，副本会漂移，
    而每一次横幅改动都得做两遍。
    每次按键 2.4 KB、约 20 ms，在打字速率下是看不见的，而唯一会自己重复的重绘
    （播放时的时钟、`Starting` 的滴答）跑在 1 Hz。要重新考虑，是等到某一帧真的必须画得比这更快，
    而不是因为字节数看着大。
  - **进度条就是那条活的 rail，也是整屏唯一一条横线。** `render_prog_bar pct total`
    拿走它可以占用的**整个**格宽，调用方传 `nav_cols - 1`，并从第 0 列开始打印 ——
    于是它比屏幕上任何一行都宽：左边越过行的光标槽（`mark_w`），右边越过时长轨、压过滚动条那一列。
    这是**故意不守列网格**的唯一一行。它曾经缩进 2 格、切到 `right_edge`，让两端与时长轨对齐；
    对齐反而害了它 —— 一条两端都卡在列网格上的线读起来像**又一个字段**，
    于是读者要去猜它的端点是不是在说什么。分隔线不是字段：让它明显比上下都宽，
    上带与行之间就只剩一条线，没有端点需要解释。
    **是 `nav_cols - 1` 而不是 `nav_cols`**：写终端**最后一列**会把光标留在延迟折行态，
    而一个把那个状态兑现成真换行的终端，会花掉一行 reflow 没有计过的高度 ——
    与一个多量一格的字段是同一类故障。右边留一格空气，看不出来，也折不了行。
    这一条也是上面那个时间徽章换来的：已播/总长上浮进横幅的括号里之后，
    这条 rail 两端一个数字都不带，整条长度都是纯轨道。
    它是作为一条**横线**画的，不是作为正文：更早的时候它吃了 4 格的正文缩进，
    于是左边缘吊在 rail 里面、只有右边缘齐平。而 `[`/`]` 两个端点没有了：括号是一种边界，
    而一条"职责就是恰好与 rail 等宽且没有边界"的线不能有端点。`━` 表示已播、`─` 表示剩余，
    是分隔线自己的笔画家族，于是已播部分读起来像是 rail 变粗了 ——
    而不是一个停在画面上的小部件。**是重线，不是双线**：`═` 试过，它在这一行上是**两笔**，
    而这条线上其他每一个字形都是一笔 —— 于是它不再读成"同一条 rail 变粗了"，而读成另一条
    rail 接在细的那条后面。整根 bar 的前提是**一条线随着填充改变笔画粗细**，
    而笔画粗细正是唯一不需要图例就能读的东西。那两个括号还占着调用方
    2 格宽度去放标点；如今那 2 格买到的是 2 格分辨率（`width = total`，不是 `total - 2`）。
    渲染出来的串**永远**恰好是那么多格 —— 已播段 + 剩余段，每一个位置都严丝合缝，
    100% 时就是一整条重线；而老的固定 42 格的条在 0% 时量出来 46 格、50% 时 44 格、100% 时 47 格，
    于是每次刷新那一行都在抖。`repeat_glyph` 负责生成那些连续段，因为
    `printf 'x%.0s' $(seq 1 0)` 仍然会打印一格（printf 总要把格式串走一遍）。
  - **剩余段是强调色暗一档，所以同一道接缝被说了两遍。** `render_prog_bar` 交出的是**两段**
    纯文本而不是一整串：已播段发满强度的强调色，剩余段发 `C_DIM` + 同一个强调色。
    **不是第二个色相，也不是一块脱了色相的灰** —— 屏上一次运行只说一套主题、色相只有一个强调色
    （见「chrome 一次运行只说一套主题」），而"这个强调色，但不是那个稳定的东西"这句话本文件早就有词：
    `play_state_marks` 的 LOADING 档就是 `C_DIM` 叠强调色。于是调色板一分钱没多花。
    为什么值得说两遍：笔画粗细是**逐格**的差别，在一条 79 格宽的 rail 上要把眼睛贴上去数；
    明暗是**整段**的差别，扫一眼就分得开。章节区间那三种读法（落在细段=还没到、
    落在粗段=已播过、跨过接缝=正在里面）因此同时也是三种明暗，不必再去数笔画。
    **关掉颜色它自己退回原样**：`C_DIM` 与 `C_CYAN` 在 `--color never` / `NO_COLOR` 下都是空串，
    两段照原样打印，整条线退回"只有笔画粗细"那一档 —— 这条 bar 一直以来的地板，没有降低。
    分段是按 `filled` 这个**格号**切的，两条路径都一样：断口只是替换掉它落在的那一格的字形，
    从不挪动接缝，所以一格属于哪一段只看下标，断口跟着它落在的那一侧的颜色走。
    颜色由**调用方**施加、两段字符串本身保持纯文本 —— 与宽度层对一切要量的东西提的是同一个约定。
  - **没有播放头字形，粗细变化本身就是播放头。** 曾经有一个 `╸`（U+2578，重左半线）坐在两段
    中间。它只涂自己的左半格、右半格留白 —— 于是**整条线上唯一一处必须不是边界的接缝，
    被画上了半格白**，眼睛把已播那一段读成"到此为止"，而不是"同一条 rail 换了个粗细"。
    整根 bar 的前提本来就是"一条线随着填充改变笔画粗细"，而粗细变化是这一行上不需要
    图例就能读的那个东西；再放一个字形去标记同一件事，只能挡它的路。所以 rail 从 `━` 不间断地
    直接进 `─`，而**这一行上唯一的白就是章节边界** —— 这正是断口之所以能被读成断口的原因。
    连带走掉的还有那半格补偿：`╶`（细右半线，U+2576）当初存在只是为了填回 `╸` 右半格的白，
    如今断口两侧每一格都是满格笔画，每一处断口天然就是一格。两个字形也一并退出 `CW_NARROW` ——
    宽度表是一份"这个 UI 会画什么"的断言，为一个没人画的字形留一条，是一条没人能验证的断言。
  - **直播没有位置，所以它不给位置读数。** mpv 报的 `time-pos` 是在**这场广播**的时间轴上，
    而 `duration` 是直播边缘，于是 `percent-pos` 从第一秒起就是 ~99.98%，进度条被钉满 ——
    在一个 24/7 电台上实测：`time-pos=77390 duration=77403 percent-pos=99.98`
    （同龄的一个点播读数是 0.03%）。所以 chrome 改为看那一行自己的 `live_status`
    （原样带在 `R_LIVE` 里；把它变成 `CURRENT_PLAY_DURATION` 上那个 `GL_LIVE` 徽标的是
    `play_selected`），用 `【MM:SS ● LIVE】` 取代那对位置读数 —— 那是**这个**听众接上之后的
    墙钟时间，mpv 给不了 —— 并且不画条。`CURRENT_PLAY_IS_LIVE`/`CURRENT_PLAY_STARTED`
    带着这些；两者在停止时都重置。
  - **客户端靠"每轮循环问一次"来得知播放器的死亡。** 一个 detached 播放器拥有自己的生命周期：
    曲终或 mpv 崩掉时没有任何东西回调 `ting`，而 IPC 层对此刻意保持安静
    （`send_mpv_ipc` 吞掉每一个失败，`mpv_get_prop` 在死 socket 上答空），
    于是一个丢掉的播放器杀不死 UI。**安静不等于被注意到** —— 所以 `check_player_alive`
    跑在主循环的顶端，**并且**跑在 `filter_live` 自己那个键循环的顶端（`/` 开着时那个循环
    永远不回主循环），并在播放器一消失就经 `clear_play_state` 清掉整块 `CURRENT_PLAY_*`。
    测试方法是对信封里那个 pid 做 `kill -0`，而那是 **bash 包装进程**的 pid：包装进程阻塞在
    mpv 上，所以"包装进程活着"恰好等于"还在播"，这与播放器自己回收时依据的
    （ARCH-player.md「运行时 IPC」 的进程组存活）是同一个真相，只是从客户端一侧、
    用一个 builtin、零 fork 够到 —— 便宜到 1 秒一拍也付得起。**空**的 pid 意思是"未知"
    而不是"死了"（`play_selected` 只要求 id 与 sock），所以它不动 chrome。
    pid 复用会让它误报，与 ARCHITECTURE.md「风险登记」 为播放器自己的 `group_alive`
    记下的完全一样。这次清除是静默的：那些空状态本身已经说明了，
    而在列表视图里它会落在下一次按键上，因为那次读是阻塞的。
  - **TUI 拥有终端的 echo，而每一个键入字符在成为"一个键"之前先被拼装完整。**
    在 bash 3.2 上 `read -rsn1` 交回的是一个**字节**，所以在过滤或新搜索提示处键入一个 CJK 字符，
    会作为两到三次独立按键到达 —— 过滤什么都匹配不到，提示回显出乱码。
    `utf8_complete` 在任何一个读取器把它称为"键"之前，从它的**首字节**（按表成员关系分类，
    见 ARCHITECTURE.md「可移植性契约」）把这个字符补完，后续字节的读带超时，
    于是一个撕裂的序列卡不死那一秒一拍的刷新。退格于是按**字符**工作而不是按字节：
    `${q%?}` 在 3.2 上本来就能剥掉一整个，但 `\b \b` 的擦除是**一格**而一个 CJK 字形占**两格**，
    所以被删掉的字符用 `disp_w` 量一下、擦掉那么多格。而驱动自己的 echo 整个会话都是关着的 ——
    连同规范模式一起：`stty -echo -icanon min 1 time 0`，并经与光标同一个 trap 恢复到进来时
    `stty -g` 存下的状态：`read -s` 只按**单次读**压制回显，于是两次读之间，
    驱动会把一次突发输入留在队列里的东西回显出来 —— 叠在这个 UI 自己已经画的回显上面。
    ICANON 跟着 echo 一起关，是因为"`-echo` 而 ICANON 还开着"正是 `getpass()` 的 termios 签名，
    而终端会对这一对做出反应（ARCHITECTURE.md「风险登记」与「可移植性契约」）；
    `min 1 time 0` 让一次裸读阻塞在一个字节上，而不是在零字节上空转。
    过滤的兜底分支必须从 `?)`（一个字节，所以永远不是一个完整 CJK 字符）放宽成 `*)`，
    这正是这两处必须同批发的原因 —— 而它止步于方向键分支没有认领的那些转义序列，
    否则 PageUp 会把 `[5~` 打进查询里。
  - **粘贴是一段文本，不是一串按键 —— 而只有终端知道它从哪儿开始、到哪儿结束。**
    在开启 bracketed paste（DECSET 2004）之前，一次粘贴与"打字很快"在 tty 这一侧完全无法区分：
    列表视图会把粘进来的每一个字符当成一个键派发。实测粘 `jazz #hop` 进列表：`j` 移动光标、
    `a` 打开"新建播放列表"的命名提示、其余字符打进了那个提示里。`#`、`s`、`d` 更糟 ——
    它们分别切换行号、停掉播放器、删掉一条已存的记录。**靠时序去猜是猜，不是判断**：
    2004 是终端把这件事说出来的标准途径，所以它和 echo 一样，是这个 app 为一次会话改动、
    并必须交还的终端状态 —— 于是它**由 `tty_echo_off`/`tty_echo_restore` 这一对开关**，
    与光标走同一个 trap。
    - **非 bracketed 终端（如 macOS 原生 Terminal.app）的原生缓冲尾随嗅探。**
      macOS 默认自带的 Terminal.app 长期未支持 DECSET 2004，用户按 `Cmd+V` 贴入 URL 时，字节流作为原始字符瞬间灌入 tty。若按普通按键处理，首字母 `h` 立刻触发 `open_history`，后续字符更会连环触发切主题、移动队列与停播。
      为了在不给普通高频导航键（方向键、`j`/`k`、空格、回车、音量、快进退）引入任何延迟的前提下彻底解决该问题：对非导航键触发输入，通过 `stty min 0 time 0 </dev/tty`（POSIX termios Case D 非阻塞读）零等待排干 tty 缓冲区中**已有**的突发字节（`check_unbracketed_tail`）。若探测到尾随数据，则自动合流组装为 `PASTE` 事件派发；若无后续字节（纯人工按键），则原样按对应单键功能执行，既消除未支持 2004 终端下的乱码派发，又绝对不损害高频键位响应。
      **零等待是判断本身，不是优化。** 粘贴是一次写入，余下字节在读到第一个字节之前就已排好；
      曾经的 `time 1` 多等 100 ms，把间隔不到 100 ms 的两次独立按键（`p` 后接 `?`）也并成一次粘贴，
      还让每个非豁免键在无尾随时白等 100 ms。
      **突发不等于粘贴。** 按住一个键的自动重复、连按两下 `?`、飞快敲出的 `12j`，仍可能在
      一次重绘期间于第一个字节后面排队，落进同一次排干。没人会往列表里粘贴"同一个字符重复 N 次"或"一串数字、至多跟一个触发它的 `j`"，
      所以这两种形状（尾巴不超过 64 字节）被拆回按键逐个交还（`REPLAY_KEYS`，和 `PENDING_KEY`
      一样由下一次读取消费），其余一律按文本处理。代价是明码写下的：往列表里粘贴一个纯数字 ID
      现在是跳行，不再是搜索 —— 要搜它，走 `n` 提示。
    - **两个读取器都要认它，不是只有一个。** 列表经 `read_esc_tail` 解码出 `\e[200~`，
      而查询提示跑的是自己那圈字节循环，会把这个开头的 `\x1b` 当成**取消键** ——
      只开 2004 而不动提示，会让"在 `n` 提示处粘贴"变成"关掉提示"。所以 payload 的消费
      （`read_paste_tail`）被拆出来给两边共用，提示的 `\x1b` 分支先看一眼再决定取消。
    - **payload 里的换行变成一个空格，而不是一次提交。** 这正是"知道它是一次粘贴"的意义所在：
      换行之后的字节是用户**粘进来的内容**，不是他按下的键。这是同一个 bug 的另一半 ——
      `jazz\n#ch` 从前会去搜 `jazz`，然后把 `#`、`c`、`h` 当命令执行掉。
    - **粘贴在列表里分流：URL 直解，文本预填。**
      通过 `extract_url_target` 自动剔除两端引号、空白以及 B 站/网易云移动端复制出来的分享文本外壳（`【视频标题】`、`分享...单曲:`）。
      若内容是合法 HTTP(S) 或已知站点 URL（`is_url_target`），直接调 `load_url` 完成原地解析：
      单曲调 `<engine>-resolve --info -j` 暂存前序搜索（`stash_search`）并投影为高亮单行结果（光标就位，按 `Enter` 播、按 `+` 入队、按 `a` 收藏、按 `b` 返回原搜索，不粗暴中断当前播放）；
      容器调 `<engine>-resolve --items -j` 暂存前序搜索（`stash_search`）并全量展开为多行列表（按 `b` 原路返回）。
      若内容是普通文本，则依然打开 `n` 提示符并预填，保留用户删改意图的空间。
      在 `/` 实时过滤模式下，若检测到粘贴或敲入完整 URL 并回车，同样自动退出过滤模式并直通 `load_url`，杜绝过滤模式下粘贴死锁。
  - **终端尺寸来自 `stty size </dev/tty`，不是 `$(tput cols)`。** 在命令替换里，
    ncurses 可能错过窗口尺寸 ioctl，转而按 terminfo 的默认答 80x24 —— 实测：
    一个 60 列的 pane 报了 80，于是那时的卡片画出 80 宽的 rail，每一行（rail、标题、进度条）都折了。
    `term_size()` 通过这个 UI 本来就要求的那个 TTY 读真正的 ioctl，
    再依次以 `tput`、80x24 兜底。（`t-play` 的 `viz` 模式用同样的方式给它的滤镜定尺寸 ——
    只是宽度照抄、**高度乘二**，因为 `--vo=tct` 画的是半格：`ARCH-player.md`「终端可视化」。）
  - **chrome 一次运行只说一种语言。** 把标签写成中文字面量、而帮助、错误与字段标签留在英文，
    会让这个工具读起来像同时在说两种语言。`init_ui_strings` 把每一个标签**一次性**解析进全局量
    —— bash 3.2 没有关联数组，而每次绘制查一次表会在每次重绘时 fork 或重新分支 ——
    来源依次是 `TING_LANG=en|zh`、`zh*` 的 locale、再不然英文（这也覆盖 cron/CI，那里 `LANG` 是空的）。
    那只是**起始**语言：`set_ui_lang` 与初始选择被拆开，于是 **`l` 键**可以在任何视图里实时重填
    这张表，且不碰播放。折行的缩进用 `disp_w` 量，不用 `${#var}`："导航:" 是 3 个字符但 5 格。

    **这条规矩如今是穷尽的：任何作为 chrome 画出来的东西，都不是它打印处的一个字面量。**
    它有两轮不是这样：提示行走了表，而播放状态（`Playing`/`Paused`/`Starting`，画了两处：
    当时是列表横幅的标签与卡片的状态）、页眉，以及每一条**瞬时**行（启动提示、`n` 提示、
    `searching…`、`→`/`o` 的动作回显、无匹配文案、过滤横幅、`Quitting…`）
    留在一个中文框架里说英文。它们之所以容易被漏掉，恰恰因为它们是瞬时的：它们打进滚动区，
    下一次重绘就抹掉，所以它们从不出现在一张截下来的帧里。三条约束塑造了修法：
    - **表里不能引用 `GL_*`。** `set_ui_lang` 在选项解析期间跑，`init_glyphs` 在它之后跑，
      所以一个标签里带字形会在第一次调用时于 `set -u` 下中止。因此一个字形在**中间**的句子
      按字形切成几个条目、在打印处组合 —— 空行文案是四个条目夹两种字形
      （`$S_NO_MATCH $GL_DASH $S_NO_MATCH_NEW $GL_SEP $S_NO_MATCH_FILT $GL_SEP $S_NO_MATCH_SRC`）——
      把一个字面破折号或圆点焙进去会活过 `TING_ASCII=1`，而那恰恰是字形表存在要防的那一件事。
    - **一个**打印点**一个条目，不是一个词一个条目。** `S_SORT_ACT` 刻意重复 `S_SORT`
      的中文值：提示行把键拼成小写、动作标题拼成 Title case，
      这个区别英文有、中文没有。共用一个条目会为了补一个中文的缺口而改掉英文的输出。
      `S_MORE_ACT` 如今没有提示行上的孪生兄弟（`m` 退役后，那个动作由 `→` 承担，
      而两个方向键在提示行上是**一个**条目），所以它是一个只剩标题的条目。
    - **经得起翻译的语序。** `→` 的回显里那个计数短语从 `for 50 results` 改成 `· 50 results`，
      于是**一个**固定的 `printf` 格式服务两种语言（中文要的是"，共 50 条"）；
      一个按语言分的格式串会把版式又塞回表里。这是这一轮对英文输出唯一一次刻意改动。

    **按设计保持英文的**：帮助文本、错误句子（`Play failed:`、`no results`、`search failed`），
    以及页眉/状态行的 `k=v` 字段标签。
    `search failed` 后面先带引擎信封的 `reason`，再带引擎 stderr 的那一行建议
    （`search failed (network): no chrome cookies: macOS blocks Ghostty …`）：`-j` 下原因在
    stdout 的信封里、建议在 stderr 里，只读 stderr 的旧写法两样都丢了 —— 一次"终端 app 读不了
    Chrome cookie"就这样被报成了一句什么都没说的失败。**成功时**同一行变成一条提示
    （`store_notice`，下一个键就消失）：结果照来、登录却没带上，恰恰是最需要说、又最安静的那种；
    一次干净的搜索 stderr 为空，所以这条提示不会平白出现。状态行的认证段同理多了第三态：
    `--auth` 报 `cookie_readable:false` 时写"匿名（cookie 读不到）"，而不是"已登录"。
  - **chrome 一次运行只说一套主题 —— 而且那是终端的主题，不是我们的。** 默认调色板
    （`minimal`）只用 ANSI 16 的索引码；刻意不用 RGB、也不用 256 色 —— minimal/mono
    路径能发出的转义只有 0/1/2/32/33/34/36 与 1;3x 的复合，加上音源胶囊在 minimal 档的
    底色索引 41/45 与 97（见下面那条例外），`mono` 一个都不发。这是一条**看着源码守的
    不变量，不是一道门**：断言它要 grep 脚本正文，而本仓的测试只驱动真实入口、
    不对源码文本下断言（见「测试与回归约定」），所以这里记的是规矩本身。
    于是默认情况下 ting 就用用户终端已有的那套配色渲染 —— One Dark、Catppuccin、
    随便什么 —— 而不是在里面再摁上第二套。十一个社区主题是第二层：它们用 24 位 RGB（38;2）
    发出自己的**标志性强调色**，但**仅当**终端声明了 `COLORTERM=truecolor`；
    否则回退到最近的 ANSI-16 索引，于是在能力有限的终端上 chrome 永远不会变成垃圾。
    每一个主题、社区的也不例外，都要过同一道过滤：层级靠灰阶（dim → normal → bold），
    色相只有**三个角色** —— 强调色 `C_CYAN`（页眉、选中标记，以及那些 rail：静态 rail
    与活的进度 rail 是同一个对象的两个状态，所以"暗 rail 压在强调色条上面"
    读起来像两条只是碰巧同宽的无关线条），加上播放态 `C_PLAY` 与暂停态 `C_PAUSE`；
    社区调色板剩下的部分（它的红/紫/…）仍然刻意丢掉。
  - **第二色相回来了，而第一次尝试为什么失败值得留着。** 它曾经是按主题的
    `C_GREEN`/`C_YELLOW`，在强调色不是绿色的地方读起来就是"这不是这个主题"
    （gruvbox 的橙色 chrome 旁边一个橄榄色状态），于是两个状态被收到强调色上、
    交给**字形**承载（`▶` / `❚❚`）。那样是成立的，代价是整屏只剩一个色相、95% 是灰。
    但要修的从来不是"不要第二色相"，而是**一个不属于这套调色板的绿不是这个主题的绿**。
    现在每个调色板报出自己那一对（catppuccin 的 green/yellow、rose-pine 的 pine/gold、
    kanagawa 的 springGreen/carpYellow……），状态于是读成主题的一部分，而不是贴在它旁边。
    字形没有退场：`▶` / `❚❚` 照旧，色相是同一个事实的第二条通道而非替代品，
    所以一个无色会话什么都没少。**加载态不取第三个色相**，仍用暗强调色 ——
    它不是播放器的第三个状态，而是搜索还没完，和把我们带到这里的那次 fetch 同一套视觉语言。
  - **亮度不是声明的，是对着底算出来的（`tone_for_bg`）。** 这不是打磨：实测下来，
    好几个调色板**在自己的 light 变体上根本没有读得出来的绿** —— nord 的 aurora 绿
    压在 Snow Storm 上是 1.8:1、黄是 1.4:1；monokai 压根没有官方 light 变体，
    在白底上是 1.6:1 与 1.4:1。一张十六进制表算不出这件事，因为一个十六进制从不看自己
    画在什么上面 —— 和 `row_hl_from_accent` 对底色说的是同一句话。所以表只声明**色相**，
    亮度交给底。底的来源与其余各处的混色完全一致：终端肯答时用 `detect_bg` 那次 OSC 11
    回复里的 `BG_R/G/B`，不肯答时用假定的黑/白 —— 于是在一台真实背景并非主题自家底色的
    终端上（常见情况），量的是事实而不是主题作者的假设。
    **压暗走纯乘法**（三通道同乘 92/100），通道比例不变、色相分毫不动 —— 而 light 正是
    全部故障所在的那一侧；提亮则向白混，确实会洗淡色相，但那是罕见路径
    （一个主题一步：rose-pine 的 pine 压在自家近黑底上），且一个已经到 255 的通道没有别的抬法。
    **亮度用 γ≈2 的整数代理**，不是 WCAG 那条 `((c+0.055)/1.055)^2.4`：那条曲线要浮点，
    而 bash 没有。拿 13 个调色板 × 两种底与真公式对过，代理阈 3.50 把每一个推导出来的颜色
    落在真实 3.4:1 ~ 4.5:1 之间 —— 这正是它需要的精度：这个下限是可读性阈值，不是对外发布的数字。
    最坏 8 次整数乘法、零 fork，每次 `set_theme` 跑两遍（启动时与按 `t` 时）。
  - **强调色不过这道推导，原样打印主题公布的那个十六进制。** 它是主题作者为自己那块底
    亲自挑的唯一一个颜色，重新定亮度等于替他们做决定；出厂强调色实测跨度是
    2.7:1（everforest light）到 10.5:1，这个跨度是主题们的，不是我们的。
    两个例外各有自己的理由，记在 `set_theme` 对应的 arm 上：**solarized** 的立论就是
    一套强调色同时服务两种底（只有 base 色调翻转），给它编一个 light 变体是在反驳这个主题
    而不是补全它；**monokai** 没有官方 light 变体，而它的签名黄 `#e6db74` 在白底上是 1.4:1
    —— 强调色又不许被推导修 —— 所以它两块底都取 monokai 的粉：同样是 monokai 的签名色，
    在自家底上 10:1、在白底上 3.8:1，而**跨两种底保持同一个色相**正是这里每个主题都在做的事
    （它们改亮度，从不改色相）。
    `C_MARK` 是选中/过滤的复合样式（bold + 强调色）。`TING_THEME` 挑家族
    （`mono` = 零色相，播放态用 bold、暂停态用 dim —— 两个状态分得开，而色相是这个名字
    唯一排除的东西）；`--theme` 压过环境变量，而 **`t` 键**可以在任何视图里
    实时轮换家族 —— 用的就是启动时那次 `set_theme` 重解析，由 `COLORS_ON` 把门，
    于是一个无色会话（`--color never` / NO_COLOR / 非 TTY）保持无色。
    `minimal` 的播放/暂停取 ANSI 32/33：在这个"颜色是什么由用户终端说"的调色板上，
    绿也是用户的。
  - **音源胶囊是屏上唯一一处颜色不属于主题的地方，而它与 `C_PLAY`/`C_PAUSE`
    不是同一类东西。** 状态行第一段（`source_seg`）带一格品牌底色与左右各半格空气：
    `yt` 暗红、`bili` 樱花粉、`ne` 经典红，前景恒为白。上面那三个角色管的都是**主题内**
    的色相：强调色说"这一处要你看"，播放绿与暂停黄说"播放器现在是什么状态"，
    三者都随主题走、都从主题自己的官方色里取。品牌底色答的是另一个问题
    （"这些行是谁家的"）：它自带前景与背景两端、不与任何 chrome 元素争同一条视线、
    也**从不随主题变**，因为它是外部服务的标识，不是这套调色板的一员。
    **这是一个例外，按例外记在这里。**
    **三档，各自只发它所在主题已经许诺过的东西**：`mono` 不发底色（mono 的承诺就是零色相，
    一块红疤是替用户改他刚做的选择）；`minimal` 发 ANSI-16 的底色索引，**在真彩终端上也走这一档**
    —— minimal 的性质是"红是什么由用户终端说"，一个索引正好是这句话，而 RGB 不是；
    其余主题在真彩下发品牌自己的 RGB，否则退回同一个索引，与强调色同一条阶梯。
    **字是 token（`ne`）而不是品牌全名（`NetEase`）**：那个 token 是 `--engine` 收的词、
    也是行按自己的 `engine` 字段路由时用的词，换成全名等于让读者在两套词汇之间做翻译，
    换来的只有宽度 —— 状态段 39→46 格，行内右贴的门槛（`st_w + 29`）从 68 列推到 75 列，
    于是一台 72 列的终端从此多花一行 chrome、少一行结果；带底色的 token 是 41 格 / 70 列。
    **未知引擎没有胶囊，退回裸 token**：引擎是探测出来的（上面「引擎发现」），
    一张写死的品牌表只认识它写下的那几个，所以第四个引擎丢进来时必须是"没有底色"，
    而不是"随便给一个颜色"；混源列表（`PLAYLIST_ENGINES` 是 `unique | join("+")`）走同一条出口，
    因为一块底色压在两个品牌上是一句假话。
  - **段落是纯文本加一条颜色通道，颜色绝不焙进被测量的那个字符串。** `disp_w` 的契约是
    "量纯文本，颜色在打印时施加"，而状态段有**两条**路径都要量它：行内右贴那一整串，
    以及宽度不够时掉回自己一行的 `print_hints`。把 SGR 拼进段落里，那 ~20 个字节会被算成
    ~20 格，右贴的 CHA 就落错列 —— 与"某个字段多量一格"同一类故障。所以胶囊走 `PILL_MARK`
    这条自己的通道（`\x1f` + SGR + `\x1f` + 文本），一次遍历同时产出**打印串**与**测量串**，
    两条路径共用同一份纯文本。底色两端都用 `C_ROW_END` 收口而不是 `C_RESET`：
    关色时 `C_RESET` 是空串，收不住一块底；而进口也要收一次，否则调用方那一层 dim
    压在胶囊的白字上，印出来是品牌底上的一块灰字。
  - **键帽的底色是一个"面"，因此它是唯一一块没有色相的底。** 提示块的键位坐在一块底上
    （`C_KEYCAP`），而不是套一对方括号。方括号是每个键多两个字形、整块多出 48 格，
    实测在英文 100 与 62 两档各多一行 —— 而这一行这个块花不起：它自己的门（`nav_ok`）
    在装不下时丢的是**整块**，退回横幅那三个键。无留白的底一格不花：分隔符从 ` · `
    换成三个空格，三格换三格，块高分毫不动（en 100/62 = 3/5 行，zh = 3/4 行，改前改后同）。
    **没有色相，这是它与屏上另一块底的分界。** 键帽是键印在上面的一个面，不是一个状态，
    所以它从终端自己的背景朝**相反的极**混（暗终端朝白、亮终端朝黑），落在中性灰上；
    在播行那块底朝**强调色**混，于是它仍然是这一帧里唯一有色相的底 ——
    两块底靠色相区分成两类事实，而它们本来就是两类。朝强调色混会在 chrome 最忙的一行上
    摆二十四块强调色小片，并让"强调色"同时意味着"这行在播"与"这是个键"。
    档位比行底更轻（14/10 对 30/18）：键帽只要在三格字后面读成一个凸起的面，
    而行底要在满屏任何位置一眼找得到。同一个式子、同一份来自 `detect_bg` 的 `BG_R/G/B`、
    终端不肯答时同一套假定黑白。`minimal` 与音源胶囊同理走索引档（`100;97`，两端都设，
    于是亮暗终端都读得清；只设一端的 `47` 或 `100` 必有一边看不见），`mono` 什么都不发。
  - **没有「自己配一个强调色」的主题，刻意的。** 0.18.0 之前有过 `custom` 与
    `UT_ACCENT` / `UT_ACCENT_LIGHT` 两个键：十三套主题已经覆盖大部分口味，为"连一个颜色都要
    自己定"的人留一个主题名、两个键、一道校验和一组测试，不划算。`t` 键曾把 `custom` 写回用户
    配置，所以一份写着 `TING_THEME=custom` 的文件读成 `minimal`，保留一个版本 —— 不能因为 ting
    自己写下的一个词把用户挡在门外。
  - **合法主题名只在一处声明。**
    合法名字的集合过去被拼写**五遍**（cycle 校验器的 allowed 串、
    `--theme` 门的模式、那道门的报错文案，以及 `usage()` 的**两**处列表），加一个名字
    等于改五个字符串、忘掉一个；现在是一个 `THEME_NAMES` 常量，两道门读它、逗号形式由它派生，
    而 `usage()` 那两句英文散文由 `tests/contract.sh` 的一条检查盯着 —— 那条检查比的是
    **命令自己说的两样东西**（门的报错文案 与 `--help`），不是去源码里 grep 那个常量。
    门也因此从「子串命中」改成了**逐个精确比对**：`--theme "gruvbox onedark"` 恰好是那张
    名字表的一个子串，子串门会放它过去，然后它从 `set_theme` 的 case 尾部掉出去 ——
    一个强调色都没设，chrome 无声地变成没有色相。
  - **值的拼法是 `0xRRGGBB` 而不是 `#RRGGBB` —— 实测，不是口味。** `#` 在这个配置格式里
    **根本无法表达**，加引号只会让它烂得更安静（2026-09-01，直接跑 `ut_read_config`）：

    | 配置里写 | 读回来的值 |
    |---|---|
    | `UT_VIZ_COLOR=#d65d0e` | 空 —— `line="${line%%#*}"` 把它整个当注释剪掉了 |
    | `UT_VIZ_COLOR="#d65d0e"` | `"` —— 剪注释发生在剥引号**之前**，静默变成垃圾 |
    | `UT_VIZ_COLOR=0xd65d0e` | `0xd65d0e` |

    第二行是这条决定真正的理由：一个用户直觉上会写的写法，不报错、不留痕，
    只是把颜色变成一个引号（2026-09-26 用 `UT_VIZ_COLOR` 重测，结果同上）。
  - **亮色与暗色终端都拿到一个读得清的强调色。** `TING_BG=auto` 的链条：显式的
    `TING_BG=light|dark` 赢；否则看 `$COLORFGBG`（rxvt 家族，bg==15）；否则发一次 OSC 11
    背景色查询（`\033]11;?\033\`）；再否则算暗色。对 `minimal`/`mono`，亮色把青换成蓝 ——
    黄色在白底上读不清，所以它不是任何主题的强调色；对社区主题，
    亮色选该主题**自己的**亮色变体（mocha→latte、night→day、polar-night→snow-storm、
    gruvbox light、onedark→one-light、dracula→alucard、rose-pine→dawn、
    everforest dark→light、kanagawa wave→lotus；solarized 与 monokai 两块底共用一套，
    各自的理由在「主题与色彩」）。这个探测是照着 bash 3.2 的形状写的：那里 `read -t`
    只接受**整**秒，所以一次没人答的查询在启动时花掉 1 秒、且只花一次，
    并且在 tmux / `TERM=dumb` 下跳过 —— 它们答不了。回复
    （kitty 的 16 位 `rgb:RRRR/GGGG/BBBB`、xterm 的 8 位 `rgb:RR/GG/BB`，以 BEL 或 ST 结尾）
    是**逐字节**拼起来的（3.2 上没有 `read -d`）；RGB 之和 > 384（中灰）是亮/暗的分界。
    **那份回复里的颜色本身也留下来**（`BG_R/G/B`），给在播行的底做混合基准
    （见「在播那一行的底」）。空是常态而不是错误：`TING_BG` 写死时查询根本没发，
    `$COLORFGBG` 只给判定不给颜色，tmux 与 `TERM=dumb` 压根不问 ——
    所以下游每一处都必须在没有它的情况下也能工作，它让答案更准，而不是让答案成立。
  - **协议这一层是有礼貌的。** `--color auto` 尊重 `NO_COLOR`（显式的
    `--color always|never` 仍然赢）。降采样由 `COLORTERM` 把门：一个社区主题只有在终端声明时
    才是 24 位，否则就是 ANSI-16 —— 调色板从不猜。全屏重绘裹在 Kitty 的同步输出对
    （DCS `=1q` / `=2q`）里，于是一次重绘不会闪出半渲染的帧；`TING_SYNC=0|1` 可以覆盖，
    而它在 tmux 下默认关（tmux 会缓冲输出，而且本来就需要 terminal-overrides 透传）。
  - **一条宽度规矩，只在一个地方：`char_w`。** 一个非 ASCII 字符按**两**格算 ——
    对 CJK（East-Asian Wide）是精确的，对其余一切是保守的。**那个默认方向本身就是安全属性**：
    多算会让一行提早一两格打包、永远不会跑出边缘，而少算会溢出。所以 2 是兜底，
    只有那些**量过**不是 2 的字符才进表。
    这条规矩要是在五个地方各写一遍（`disp_w`、`disp_fits`、`truncate_disp`，
    以及 `wrap_print` 的两个循环），改一处就会静默地与另外四处不一致；
    **测量与断行不一致，比统一地多算更糟**，所以它们都调 `char_w`。
  - **量宽从不走完一段没有上界的文本（`disp_fits`）。** `disp_w` 那条 ASCII 快路径是
    **全有全无**的：一段 3621 字符的描述里只要有 54 个 emoji（用来分段的那种），
    整段就掉出快路径、逐字符走一遍。而 `truncate_disp` 开头问的只是一个是非题 ——
    "这段是不是已经放得下 max 格" —— 所以它问的是 `disp_fits` 而不是 `disp_w`：
    `char_w` 的取值域是 `{0,1,2}`、全非负，累计宽度只增不减，越过 `max` 的那一刻答案
    已经不可能反转。**严格等价**，代价从**文本长度**改成**预算**。
    实测（3.2.57，那段真描述，预算 576 格）：整段 0.550s → 有界 0.195s；
    条目卡片"顶部画完、底部还没画"的那段静止从 0.88 秒降到 0.20 秒。
    这条只对**开头那次判定**成立：裁剪循环本来就早退（`((w + CHAR_W > budget)) && break`），
    `wrap_print` 是按**词**量的（每个词各自吃到快路径），所以整条链上再没有第二处没上界的遍历。
  - **chrome 自己的字形按它们真实的一格入表**，这正是让版式**精确**而不只是**安全**的原因。
    这一点之所以站得住，是因为这套套件的字形库存刻意是**非图形**的 —— 文本呈现，
    `t-play` / `yt-search` / `yt-resolve` / `bili-*` / `ting` 里没有任何 emoji ——
    所以这些字符都不可能背着表带上一个 U+FE0F 变成 2 格的 emoji 字形。
    全部 17 个都量到一格（`tmux display-message -p '#{cursor_x}'`）：

    **这份封闭库存（ARCHITECTURE.md「人机面」）** —— chrome 能画出来的每一个字形，由 `GL_*` 声明加上进度条与分隔线
    生成，其分类是从 UCD 读出来的（`unicodedata.east_asian_width`）而不是猜的。
    扫过每一条非注释行，除了中文标签文本之外找不到别的非 ASCII 字符，
    所以这份清单是**完整的**，不是**挑选的**。

    **字标同时也是一条语言串。** 多音源演进后项目中文名定为 `听`（ting）。在中文语境下，
    字标采用**东方式方印徽标 `【 听 】`**（ASCII 模式下为 `[ 听 ]`），并在视觉上与播放状态
    **动态联动（Live State）**：
    - 未播放或暂停待命时：渲染为沉静的纯色加粗方印 `【 听 】`；
    - 正在播放（Playing）时：内芯动态通电点亮为反色高亮实体色块（`【 听 】`），宛如一盏发光的音频指示灯。
    其纯文本在任何状态下均为恒定的 8 格（全角方括号与汉字各 2 格，加两端空格各 1 格），
    保证 `disp_w` 测量零抖动、省略截断零漂移。英文模式下为 `ting`。
    它自成一个 `set_brand`，由两者一起解析，并在 `l` 键当场翻转语言时实时重绘。

    **页眉图标是一个两格的槽，里面固定是 `♫`。** U+266B 一格（`CW_NARROW` 里有它），所以
    `GL_NOTE` 自带一个空格把两格补满，字标每一帧都从同一列开始。`TING_ASCII=1` 下整个槽消失
    （`GL_NOTE=""`）。

    **一条刻意的规矩：键名怎么拼 —— 键帽上印着什么就画什么，没印的留词。**
    `⏎`（Enter）与 `⇥`（Tab）是物理键帽上真的印着的符号，所以提示块画符号；空格键的键帽是
    空白的，所以 `Space` 留作一个词 —— `␣`（U+2423）是任何键盘都不显示的字形，
    在一个专门用来告诉读者"按哪个键"的块里，它是个字谜。方向键丢的是斜杠不是形状：
    `↑↓` 本身就是那一对键，而 `/` 是一个"或"，只该花在两个键没有共同形状的地方
    （`-/=` 仍然带着它）。这条规矩挡住的形状是"为了紧凑把每个键都换成符号"。

    **Neutral EAW —— 在每个终端里无条件一格（9 个）**

    | 字形 | 码位 | 声明为 | 名称 |
    |---|---|---|---|
    | `⏎` | U+23CE | `GL_ENTER` | Return Symbol |
    | `⇥` | U+21E5 | `GL_TAB` | Rightwards Arrow To Bar |
    | `♫` | U+266B | `GL_NOTE`（图标槽的一半，自带空格凑满两格） | Beamed Eighth Notes |
    | `❚` | U+275A | `GL_PAUSE`（画作 `❚❚`） | Heavy Vertical Bar |
    | `❯` | U+276F | `GL_CARET` | Heavy Right-Pointing Angle Quotation Mark Ornament |
    | `▖` | U+2596 | `GL_SPIN` | Quadrant Lower Left |
    | `▗` | U+2597 | `GL_SPIN` | Quadrant Lower Right |
    | `▘` | U+2598 | `GL_SPIN` | Quadrant Upper Left |
    | `▝` | U+259D | `GL_SPIN` | Quadrant Upper Right |

    那四个象限既是取数 spinner，**也是** `Starting` 播放态 —— 一个动画复用两处，
    于是"等一次搜索"与"等一条流"看起来是同一件事 —— 而它们的 EAW 分类正是它们被选中的理由：
    U+2596..U+259F 是 Block Elements 里唯一一座 Neutral 的孤岛，所以这个动画在每个终端、
    每种设置下都是一格。显而易见的替代品都不是：`◐◓◑◒` 与 `▁▃▅▇` 那些条是 Ambiguous，
    于是 `TING_AMBIG_WIDE=1`（或一个把 Ambiguous 当宽的终端）会让帧在一格与两格之间跳。
    它们仍然进 `CW_NARROW`，哪怕没有任何东西去量 spinner 那一行 ——
    这样"每个字形都有已知宽度"这条不变量是**由构造成立**的，而不是取决于字形碰巧打在哪儿。

    **Ambiguous EAW —— 默认一格，只有在 `TING_AMBIG_WIDE=1` 下才是两格（16 个）**

    | 字形 | 码位 | 声明为 | 名称 |
    |---|---|---|---|
    | `·` | U+00B7 | `GL_SEP` | Middle Dot |
    | `—` | U+2014 | `GL_DASH` | Em Dash |
    | `•` | U+2022 | 无 `GL_*` 名字（见表后） | Bullet |
    | `…` | U+2026 | `GL_ELL` | Horizontal Ellipsis |
    | `←` | U+2190 | `GL_AH`（画作 `←→`） | Leftwards Arrow |
    | `↑` | U+2191 | `GL_AV`（画作 `↑↓`） | Upwards Arrow |
    | `→` | U+2192 | `GL_AH`、`GL_ARROW` | Rightwards Arrow |
    | `↓` | U+2193 | `GL_AV` | Downwards Arrow |
    | `─` | U+2500 | 进度条轨道、分隔 rail | Box Drawings Light Horizontal |
    | `━` | U+2501 | 进度条填充 | Box Drawings Heavy Horizontal |
    | `▣` | U+25A3 | `GL_CPU`（资源读数的 cpu 标签） | White Square Containing Black Small Square |
    | `▤` | U+25A4 | `GL_RAM`（资源读数的内存标签） | White Square With Horizontal Fill |
    | `▶` | U+25B6 | `GL_PLAY` | Black Right-Pointing Triangle |
    | `▎` | U+258E | `GL_CURSOR`（光标那条强调竖线） | Left One Quarter Block |
    | `●` | U+25CF | `GL_LIVE` | Black Circle |
    | `█` | U+2588 | `GL_BAR_THUMB`（滚动条拇指） | Full Block |
    | `│` | U+2502 | `GL_BAR_TRACK`（滚动条轨道） | Box Drawings Light Vertical |
    | `≥` `≤` | U+2265 U+2264 | `GL_GE` / `GL_LE`（时长上下界那两段） | Greater/Less-Than Or Equal To |

    `•` 是这张表里唯一一个**没有绘制点**的成员：`GL_BULLET` 是焦点卡列表项的记号，
    卡片被删掉时那个名字跟着走了（见上面"第二个渲染器是被删掉的"），而码位留在 `CW_AMBIG` 里。
    留它的理由与那四个象限留在 `CW_NARROW` 的理由是同一条：这张表要的不变量是
    "**这套件能发出的每一个字形都有已知宽度**"，而这条要**由构造成立**，
    不能取决于此刻还有没有人打印它 —— `usage()` 的字形清单今天仍然印着它。
    因此"每一个画出来的字形都必须有一个 `GL_*` 名字"这条规矩没有被它破坏：
    它不是一个画出来的字形。

    这 16 个 Ambiguous 就是**全部**依赖配置的表面：唯一一批格数会被某个终端设置挪动的字符，
    也是 `TING_AMBIG_WIDE` 唯一碰得到的一批。那 9 个 Neutral 按其分类的定义就是一格，
    任何设置都够不到它们。`♫` U+266B 属于后者而不是与箭头同列 —— 它是 Neutral，
    所以哪怕在 `TING_AMBIG_WIDE` 下也仍是一格。

    因此 TUI 画出来的一切都落在四个桶之一：ASCII（1 格）、这 25 个（入表）、
    CJK 标签文本（2 格，精确），或者未入表因而被保守多算 —— 最后这个桶里
    `【` `】` 是特例：它们同样不入表，但默认的 2 对它们不是多算而是**精确**。`TING_ASCII=1`
    （非 UTF-8 locale 下自动开）把这 25 个全部换成 ASCII 等价物，
    于是这份库存恰好只有两个状态、没有依赖字体的中间地带 ——
    这也是为什么每一个画出来的字形都必须有一个 `GL_*` 名字。最后一批硬编码字面量是分页圆点
    （行内的 `●` / `○`），它们先被收进 `GL_DOT` / `GL_DOT_OFF`，而后随分页那一行**整条退役**
    （滚动条接走了"我在哪"这个问题）—— 名字与码位一起删掉了，因为一个没有调用方的字形名字
    就是下一次有人以为它还在画什么。

    一格是这里在用的每一个终端的**默认**：Ghostty（`grapheme-width-method = unicode`），
    以及 Terminal.app / iTerm2 / tmux —— 在它们那里"把 ambiguous 宽度当双宽"是一个出厂关闭的
    opt-in。`TING_AMBIG_WIDE=1` 只为 Ambiguous 那一行恢复保守的 2 —— Neutral 字形无论如何都是一格。
    它是一个显式旋钮而不是靠 locale 猜，因为 locale 什么也没说：Ghostty 在 `zh_CN.UTF-8` 下
    仍然把这些渲染成一格。`render_prog_bar` 早就把这个假设焙进去了 —— 它承诺一个恰好 `total`
    格、由 `━` 与 `─` 构成的串，而这只有在每个都是一格时才成立。在 60 列、中文 chrome 下实测到的
    效果：导航行在它的第一行上多放得下一项（`导航: … v 模式  n 搜索` = 量出 58 格，实际 58），
    而不是把它折下去。
  - **这份精确性精确地建立在什么之上。** 那些入表的字形只在**文本呈现**下才是一格：
    同一个终端里量过，`▶` 是 1 格，而 `▶️`（U+25B6 U+FE0F）是 2 格，表却会说它是 1。
    所以 `build_all_rows` 里 `clean` 的承重部分**不是**它那些 emoji 块区间 ——
    而是它剥掉 U+FE00–FE0F 与 U+200D，正是这一点保证了到达测量环节的任何东西都不是 emoji 呈现。
    任何活过 `clean` 的东西都是文本呈现，因此要么入表且正确、要么（未入表）被多算，
    于是"不溢出"这条性质对任意 YouTube 标题都成立，而过滤器不必穷举每一个 emoji 码位。
    如果哪天那个剥离被放宽，表就得先有一条 base+VS16 规则：一个基字符后面跟 U+FE0F 就是 2 格，
    表说什么都不算。**失败方向是不对称的，而这是唯一不安全的那一个** ——
    给 `GL_*` 加一个字形却忘了宽度表，只会回落到 2（多算，安全）；
    把一个没量过的字符塞进宽度表，才是会溢出的那种。
  - **零宽类是被修正过的**，因为在那里"两格"在每个终端里都是错的。在基字符仍按两格算的前提下，
    下面每一条都让整个序列的结果从"仅仅保守"变成**精确** ——
    对照终端自己的光标推进验证过（`tmux display-message -p '#{cursor_x}'`）：

    | 序列 | 旧 | 现在 | 终端实际 |
    |---|---|---|---|
    | `Ocean Coffee ☕️ Vibe`（U+FE0F） | 22 | **20** | 20 |
    | `flag 🇨🇳 cn`（区域指示符） | 12 | **10** | 10 |
    | `👍🏽 ok`（肤色修饰符） | 6 | **5** | 5 |
    | `café latte`（分解式，U+0301） | 12 | **10** | 10 |
    | `family 👨‍👩‍👧 here`（ZWJ） | 22 | 18 | 14 |
    | `● LIVE`（chrome，Ambiguous） | 7 | **6** | 6 |
    | `▶ ❚❚ ❯ ♫ ·`（chrome） | 16 | **10** | 10 |
    | `▎`（光标记号，Ambiguous） | 2 | **1** | 2 |

    零格：U+200D ZWJ、U+FE0E/U+FE0F、肤色 U+1F3FB–U+1F3FF、组合记号
    U+0300–U+036F / U+20D0–U+20F0 / U+FE20–U+FE2F。一格：区域指示符 U+1F1E6–U+1F1FF。
    这些块之外的组合记号（阿拉伯文、天城文、泰文）不在表里，保持多算 —— 保守，绝不短算。
    一个 ZWJ emoji 序列仍然多算；把它折叠起来需要一次真正的字素簇行走，
    在 bash 3.2 里不值那个重量。这些表在启动时**按字节构建**（`cw_range`）而不是写成字面量：
    一行塞满不可见组合记号的源码是读不了的。纯 ASCII 串完全跳过逐字符行走，
    于是这个共享 helper **比**它取代的那个内联判断**更快**（对一行打包好的提示做 300 次测量：
    之前 94 ms，之后 5 ms）。
    累加要写 `n=$((n + CHAR_W))`，绝不写 `((n += CHAR_W))`：一个求值为 0 的算术命令返回退出码 1，
    于是一个开头的零宽字符会在 `set -e` 下中止脚本。
  - **切割落在字素边界上（`cluster_back`）。** 把一个基字符与它的组合记号、连接符或旗帜搭档
    切开，不只是量错，而是画出**错误的**字形：半面旗渲染成一个孤零零的字母方块，
    一个失去依附的 VS16 或 ZWJ 会挂到省略号上。`truncate_disp` 把切点往左走到一个真正的边界为止。
    一个 RI 只有在它前面那个字符也是 RI 时才挡住切点 —— 否则每一个落在旗帜前面的切点
    都会白白吃掉它前面那个字符。`wrap_print` 不需要这段行走：一个零宽字符加 0 格，
    所以它永远绊不倒预算判断、也永远不会开启一行续行 —— 记号免费地留在它的基字符旁边。
  - **所有 chrome 行都按量出来的宽度排版，不是写成固定串。** `disp_w` 量的是**纯文本**
    （一个非 ASCII 格算两格 —— 标签是 CJK，所以它们比字符数暗示的更早用完地方），
    并**通过全局量**返回，因为它在一次重绘里要跑好几遍，而 `$(...)` 会 fork。在它之上：
    `print_hints` 把 `key<TAB>label` 条目（或裸字段）打包进尽可能少的行，带首行/续行前缀，
    条目之间用 `HINT_SEP`（默认两个空格，调用方可覆盖 —— 与 `HINT_KEY_COLOR` 是同一种
    "一次调用一次覆盖"的形状，而且打印器与打包器的适配判断读的是同一个值，
    于是一个打包器不知道的分隔符不可能让某一项提早一格折行）；`truncate_disp` 省略掉那种
    "与固定 chrome 共享一行预算"的变长值。它被用在导航行、空状态文案，
    以及状态行（它的 `min=`/`max=` 如今只在设置过时才出现 —— 在 `0s` 默认值下它们纯占宽）。
    Now-Playing 横幅把固定部分剩下的都给标题，在会把标题挤到 12 格以下之前先丢掉它内联的
    提示块。结果：每一条 chrome 行在 46 列都装得下，而旧的固定串从约 72 列往下就会在条目中间折。
  - **列表视图里**每一行**都是一条物理行，结果行也不例外。** 它们是最后一批未经测量就打印的行，
    也是最要命的那批：在 62 列，一条 `标题 · 时长 · 播放量 · 频道` 的行要占两到三行，
    于是十个条目填满 21 行，把页眉、状态行、Now-Playing 横幅和整个导航块统统顶出屏幕顶端 ——
    版式刚刚打包好的每一条提示，全花在那些随后就滚走的行上。每一行的**标题**被省略到
    "序号字段、两格间隔与时长轨之后剩下的宽度"（`cols - iw - 1 - 2 - rail`）。
    标题行（一条长查询会折）与过滤输入行的文案用同样方式省略，于是整个视图逐行可测量。
  - **一行就是一个标题加一个时长；其余一切都是它下面的一个段。** 一行一条物理行是必要但不充分的：
    把一行拼成 `标题 · 时长 · 播放量 · 频道` **一个**串再从右边省略，
    会让省略**先**吃掉元数据 —— 在 62 列时一行就是一个被砍断的标题、旁边什么也没有，
    整个截断预算都花在那三个最后被切掉的字段上。所以一行带的是标题与一条右贴的时长轨，
    而完整标题、频道、播放量与视频 id 住在分页圆点下面的一个 **details 段**里，只给选中的那一行。
    轨上打的是光秃秃的 `LIVE`，而 details 行打的是 `● LIVE · live now`：
    一个数字列里不想要状态字形，而在一行散文里同一个字形读起来就是一个徽标。两者都用 `short_dur`，
    于是信封里补零的 `06h:10m:58s` 永远上不了屏 —— 一行也不会与它自己的 details 块矛盾，
    因为两者都从**同样的字段**渲染，而不是从对方渲染。
  - **序号是一个定宽列；标记在它前面有自己的槽位。** 把前缀写成每行的字面量 ——
    选中时 `> 1. `、没选中时 `  1. ` —— 会让宽度是 `4 + <位数>`，
    而一页一旦进到两位数，每一个一位数的标题都会比周围的行左移一格。参差不齐，
    而且恰恰是在眼睛**竖着**扫的那一列上。所以序号在一个 `iw - 2` 格的定宽子字段里右对齐
    （最大序号的位数 + 1 给那个点），它前面的标记槽是恒定的 2（`"> "`，未选中行留 `"  "`），
    再用一个空格把字段与标题分开：每一行 `iw + 1` 格前缀，`iw = ${#NUM_ENTRIES} + 3`。
    宽度取自 `NUM_ENTRIES` 而不是取自当前页，所以翻页时它不动；而因为它是一个数，
    `row_w` 与 CHA 的轨跳都读它，而不是各自重新推导前缀。在一位数的页上这个子字段不需要补白，
    于是输出与旧的字面量逐字节相同 —— 这个字段只有在总数跨进两位数时才显形，
    而那恰恰是它存在的那种情形。

    **每一行都保留自己的序号，选中的那行也不例外。** 第一版做法是在选中行上用 `>` 取代序号，
    理由是"你只会为**不在**的那一行敲序号"。那个理由讲的是键盘，而这一列不是：
    把光标所在那行的序号抹掉，等于拿走了唯一一个说明"那是哪一行"的标签，
    而当一个读者想说清自己在哪儿时，找的正是它。已回退；标记改为拿到自己的槽位，
    而那正是定宽子字段腾出来的地方。
  - **提示行用点号连接、且没有括号。** 这个形状是在当年那张焦点卡上定下的，而它活得比卡长：
    带 `[方括号]` 的键名、两空格连接、句子式标签（`back to list`、`pause / resume`）量出来
    110 格；去掉括号（粗键/暗标签的字重差别本来就把两者分开了）、标签各砍成一个词、
    条目之间改用套件自己的 `GL_SEP`（` · `，暗色），量出来 63 格 —— 一直到 63 列都是一行
    （`TING_AMBIG_WIDE=1` 下是 69，那时 `←`/`→`/`·` 各花两格）。再窄就折成两行，与其他每一个
    chrome 块走的是同一条优雅退化的路。中文标签是**重新裁**的，不是机械地截：
    `返回列表选单` → `列表`、`快退 / 快进 5s` → `跳转`，于是中文那行量出来也是 63。
  - **chrome 不带标签，结构由排版承载。** `Title:` / `Channel:` / `Time:` / `Mode:` /
    `Status:`（以及提示块的 `Controls:` 与导航块的 `Navigation:`）都没有了：粗体标题、
    暗色频道、一行由 `GL_SEP` 连接的暗色元信息，状态保留它的颜色。补白也随标签一起消失：
    `%-8s` 在 bash 3.2 上补的是八个**字节**，所以一个 CJK 标签渲染出来的宽度与适配估算
    假设的不同 —— 没有标签，就没有补白可搞错。横幅的标题也不带 `▶`：播放状态住在它前面
    那个带颜色的状态里，一个事实两个指示器是同一种重复的微缩版。
  - **一格提示只画在这个键**能动作**的地方，而"能不能"有两层：装了没有，和**现在这个视图**里
    有没有意义。** 第一层原来就在（`e` 只在装了第二个引擎时画、`a`/`b` 要 `t-playlist`、
    `h` 要 `t-history`、`c`/`i` 要引擎有那个动词、`+`/`>` 要真的有播放器在放）。第二层是后补的：
    `o`（重排搜索并重取）、`e`（换源并重取同一个 query）、`c` 与 `i`（都替换掉屏上的行，
    而暂存槽只有一个）四个键的函数第一行都是 `search_only`，所以在歌单 / 历史 / 分P / 章节
    视图里，它们的**全部效果**是一句"只对搜索结果生效"的提示 —— 一个量宽度的块，
    不能拿一格去说"这里不行"。`d` 早就按这条规矩画（只在歌单视图），
    补上的是把同一条规矩铺到那四个键上。
    **一个例外，明写在这里**：从分P 视图**出去**的那一格 `c`（以及从章节视图出去的那一格 `i`）
    照画不误，不管能力探测此刻怎么说 —— 人正站在那个视图里，
    而一个把人带到某处的键，必须在那里写得下自己。
    顺带退掉的是 `e` 那个**按下标 splice 进数组**的写法：下标是位置，它上面每加一个键就得改一次，
    而当时守着那个数字的只有一句注释。整块改成**按顺序构建**，每个条件键待在它自己该在的位置上。
    （审议里点名的第三个死格 `m` 早在 0.3.10 就被 `←/→` 边缘取数换掉了，派发表里根本没有它。）
  - **键位提示块也丢掉了它的标签，并补上了它从没写下来的那些键。** `Navigation:`
    是 chrome 带上最后一个标签，它走的理由与当年卡片的 `Controls:` 一样：**键本身就是内容**，
    而它的邻居 —— 上面的横幅、下面的 rail —— 也都不带标签，所以这个词只是在宣布读者本来就看得见的东西。
    它还在这个视图最宽的那一行上占了 12 格。`S_NAV` 从两张语言表里**删掉**而不是留着定义，
    因为没有任何地方读它。分隔符是 `GL_SEP` —— 而 `HINT_SEP` 要在**测量**调用与**打印**调用两处都设，
    绝不能只设一处：` · ` 是 3 格而默认是 2，跨 11 个间隔就是 11 格，足以把这个块从一行推成两行。
    而一次**少算** chrome 的测量，恰恰就是页眉被顶出屏幕的原因。
    还有三个键曾**在这个唯一以"写下键位"为职责的视图里缺席**：音量、`Space` 暂停、
    `[ ]` seek —— 它们都由菜单循环那个通用分支处理，所以在这里一直是能用的 ——
    横幅的窄终端兜底记着音量与暂停，`ting --help` 的键表与
    ARCHITECTURE.md「支持的工作流」 也都记着，正是这一点让它们的缺席是一个**缺口**而不是一个决定。
    它们聚在末尾、挨着 `s`，因为在一个其余都在讲移动与搜索的清单里，它们是播放键。
    seek 键印成 `[ ]` 而**不是** `[/]`：`/` 在这一行里是"或"的分隔符（`-/=` —— 方向键
    自键帽化之后已经把它丢了，`↑↓` 那一对本身就读成一对），
    但这两个键**本身就是**方括号，所以一个被它们裹住的斜杠读起来像"一个被括起来的 `/`"，
    并与三项之前那个真正的 `/ 过滤` 撞车。一个空格能说出"两个键"，
    而不必花掉一个在这行里已经另有含义的字符。`S_SEEK5` 更名为 `S_SEEK`：
    它的值本来就是那个光秃秃的词，而当时它同时服务卡片的 ±5s 箭头与列表的 ±10s 方括号，
    所以旧名字唯一做到的事就是宣称一个步长（卡片走后只剩方括号，名字仍然对）。

    `p`/`P` 不在这个清单里了：不是"不写进文档"，是**退役**了（见下一条）。

  - **`p`/`P` 退役，`j`/`k` 补上。** `p` 从前是 `Tab` 的一个别名（那时 `Tab` 还
    切视图），

    26 位（大小写同绑）的键空间。补进来的 `j`/`k` 是现代 TUI 的桌面赌注
    （lazygit / k9s / yazi / gh-dash / spotify-player 全数支持），此处空闲、零反义，
    而且**只取这一对，不取 hjkl 全套**：`h` 已经是历史（`b`/`h`/`c` 这个行源键族的内聚更
    值钱），`g`/`G` 被大小写同绑封死，半套 vim 比没有更糟。
    - **它们骑在 `↑`/`↓` 自己的 case 臂上**，不新开两条：一条别名要是自己一条臂，就是把
      翻页那段算术抄了第二份，而这个文件里每一块重复都是为了消掉这种漂移才重写的。
    - **只在列表视图，而 `filter_live` 刻意不接它们**：`/` 开着时 j 和 k 是用户正在打的字，
      一个会吃掉字母的导航键是不能用的。卡内方向键另有职责（章节游标），
      所以 j/k 在卡上落到 `*)` 的 no-op。
  - **提示块有三档，`?` 是那道门。** `core`（出厂档）只印这个视图**自己的活**：
    移动、对行的动作、回程、`q`，外加 `?` 自己；`full` 是它今天有的每一个键；
    `hidden` 则将底部提示块与间隔完全隐藏，把这几行交还给行高预算。
    三态循环为 `core → full → hidden → core`。
    - **实现是逐格把门，不是先建一个 core 数组再往上追加。** `keys_full` 与 `keys_hidden` 是
      **状态函数**（`[[ "$KEYS_TIER" == "full" ]]`，不 fork），每个只属于 full 的格子在**它自己该在的
      位置**上带一句 `keys_full &&` —— 于是 full 档打印出来的顺序与它一直以来的顺序逐字节
      相同；`keys_hidden` 时直接跳过构建与测量，`nav_h=0` 且 `nav_ok=0`，Banner 不弹回退提示，
      布局引擎自动将腾出的 2~6 行垂直高度划拨给内容行（Reflow）。
    - **腾出来的是预算，不是行数。** scroll 模式的行数就是"放得下的"，所以 hidden 直接多出几行；
      page 模式的行数是 `UT_PAGE_ROWS` 压到放得下为止，hidden 只在矮终端把一页压到它以下时
      才起作用，高终端上多出的是空白。刻意不让 hidden 放开这道上限：那会把 `UT_PAGE_ROWS`
      从"page 模式的上限"变成"除非键位藏起来时的上限"，一个配置键的意思随另一个键漂移。
    - **回程是 core，进门是 full —— 这是这次分档里唯一不是"本职 vs 其余"的地方。**
      一个换过词的存储键（`b back to results`、`h`、`c`）是人**此刻站着的那个房间**唯一的
      出口，core 要是把它藏了，人就被留在里面、屏幕上没有一条印出来的出路；而同一个键
      **打开**那个房间时，它只是一个可以去的地方，那正是 full 的用途。
    - **`?` 在 core/full 打印，且永远是块里最后一格；hidden 态下全隐藏。** 它是整块里唯一一个既不关行、
      也不关播放器的格子；hidden 态下虽无提示字样，但全局按键循环中 `?` 依然监听，按一次即切回 `core`。
    - **`？`（全角）与 `?` 同绑。** 这是一个双语 TUI，zh 输入法下 shift-/ 出的是全角问号，
      `utf8_complete` 本来就会把它拼成一个键，所以这是多一个 case 模式，不是第二条代码路径。
      case 模式里那个 `?` **必须带引号**：裸 `?` 是"任意单字符"的 glob，会把它下面每一个键吞掉。
    - **它是第八个写回键**（`UT_KEYS=core|full|hidden`，机制见 `ARCH-cli-contract.md`「配置面」「写回」）：
      一个每次开会话都要重按的偏好不是偏好。也因此它在出厂 `config` 里有一个值，
      而一个拼错的值**当场就死**，与 `UT_PLAY_QUALITY` 走同一道闸。
    - **它藏的是提示，不是键。** core 与 hidden 档下 `i`、`a`、`b`、`h`、`c`、`v`、`f`、`o`、`e`、
      `l`、`t`、`9`/`0`、`Space`、`s`、`[`/`]`、`+`、`>` 全部照按不误 —— 派发表一格都没动。
    - **`t` 曾经一档都不印，那是漂移不是分档（2026-08-31 补上）。** 它在 `usage()` 与 README
      的键表里一直都在，唯独这个块里没有 —— 而这个块是用户唯一一个"读一个词就知道这个键干嘛"
      的地方。它按块自己那条规矩带门：`COLORS_ON` 关着时 `cycle_theme` 直接返回，
      与单引擎装机上的 `e`、没装 `t-playlist` 时的 `a`/`b` 同形。
  - **横幅的尾巴是一个位置，不是一个时长，而且它是一枚徽章，右贴于 `right_edge`。** 单独打印曲目长度
    （`▶ Playing: … · 3:34`）只是把它下面那一行上已经有的数字再说一遍；所以它打印
    `【1:12/3:34】`，与它下面那条活 rail 画的是同一对，于是读数与条不可能互相矛盾。
    **括号是新的，`·` 走了，且与资源占用一同右对齐。** 横幅的右侧状态段（位置读数、资源消耗与
    窄终端键位提示）由 `CHA` 绝对跳转直接右贴于 `right_edge`，与上方状态行和下方时长轨在同一列
    垂直对齐，消除了因曲目标题长度不同导致的横向跳动。行首先发 `\033[K` 保证行内重绘不留缝隙残影。
    一对括号用一个字形说完"我属于我左边那个东西"，还顺手从那一行上撤掉一个点。它也省了一格：
    括号形量出来 15，旧的 `· 1:12 / 3:34` 是 16，于是下面那套省略预算分到的标题反而**多**了一格，不是少。
    括号用 `GL_TIME_L`/`GL_TIME_R`（`【` `】` U+3010/U+3011，`TING_ASCII=1` 下回退成 `[` `]`）：
    它们是 East-Asian **Wide** 而不是 Ambiguous，在任何终端都是两格、`TING_AMBIG_WIDE` 也拨不动它，
    所以它们不进任何 `CW_*` 表 —— `char_w` 的兜底 2 对它们本来就是精确值，不是保守值。
    它不额外花任何 IPC：`PT_CUR` 与 `PT_TOTAL` 就是那个共享时钟最后留下的值，最多一秒旧，
    而这正是这一行绘制的分辨率。`PT_CUR` 为空意味着还没有任何读数落地 ——
    按下 Enter 之后的第一帧、第一次滴答之前 —— 那时回退成单独显示时长，而不是打印一个光秃秃的 `/`；
    `PT_TOTAL` 以同样方式回退，而因为 `fetch_play_times` 用那一行自己的 `short_dur` 给它播种、
    只有在 mpv 答话之后才用 `fmt_sec` 换掉它，这个读数在播放开始一秒后不会改变**形状**。
    直播保留它自己的形态（`【12:34 ● LIVE】`，没有斜杠）：mpv 的钟描述的是那场广播，
    不是这一次收听，所以没有可以拿来做分母的总长 —— 括号里那个分隔点也跟着走：
    `12:34 / ● LIVE` 读起来像一个比值，而这一对恰恰不是比值，一个空格就够分开它。**这件事也暴露了 `clear_play_state` 不完整。**
    它为 rail 重置了 `PT_PCT`，却把 `PT_CUR` 与 `PT_TOTAL` 留着，
    而 `play_selected` 是在启动下一首**之前**经 `stop_current_playback` 够到它的 ——
    于是横幅会一直显示**上一首**的已播时间，直到第一次滴答把它覆盖掉。
    如今三个一起清，而"空"也恰好就是兜底所读的那个"还没有读数"的信号。
  - **横幅带一个播放器足迹字段（`▣ N% ▤ NM`，UT_RESOURCE）。**
    标签是 `GL_CPU`/`GL_RAM`（▣ U+25A3 / ▤ U+25A4，Ambiguous，入 `CW_AMBIG` 表；
    `TING_ASCII=1` 下回退成 `cpu`/`ram` 文字）。
    读的是同一对缓存（`RES_CPU`/`RES_MEM`，`fetch_play_res` 在共享时钟上每
    3 拍采一次，与 `t-play --watch` 心跳带出 `cpu`/`mem` 的步长相同），
    渲染也不为它花任何 fork。**口径是播放器的进程组**（wrapper + mpv + 可能的回退 mpv，
    pgid == wrapper pid），不是整机 —— 整机负载任何系统工具都给，这个进程组只有拿着 pid 的
    ting 知道。读法是一次 `ps -A -o pgid=,%cpu=,rss=` 加 awk 按组求和（约 24ms）：`ps -g`
    在 macOS 与 procps 下语义不同，全表扫描是唯一一种两个平台同一拼写的读法；%cpu 取 ps 自己
    的语义（衰减/生命期均值，不是瞬时值），rss 两边都是 KB。空闲不采：没在播就没有可量的组，
    而钟本来也只在播放时转。
    **怎么读这个数：网络流下 ~300M 是 mpv 的正常体型，不是泄漏。** mpv 播网络流会把还没播到
    的内容囤在内存里防断流，出厂上限 `--demuxer-max-bytes=150MiB`（前向）+
    `--demuxer-max-back-bytes=50MiB`（回退，供往回跳），囤满即停涨（实测 v0.41.0：前向缓存
    顶满正好 150M，加解码器与共享库落在 ~300M）。缓冲期的尖峰（~400M+）是 yt-dlp 那个 Python
    进程还在组里；解析完它退出，数就落回 mpv 自己的。一个放大器：audio 模式的 `ba/b` 链回落到
    混流格式（如 yt 的 f18）时，囤的字节里有一半是不会渲染的视频轨。嫌大在**你自己的 mpv.conf**
    里调 `demuxer-max-bytes`（`run_mpv` 不传 `--no-config`，用户的 mpv.conf 生效）—— mpv 的
    调音面已经存在，套件不为它再包一个键。丢弃顺序里它排在键尾之后、位置读数之前 ——
    足迹说的是播放器的开销，不是曲目。
    与 PT_ 三元组一起在 `clear_play_state` 清空，计数器同时归零，
    于是下一个播放器的第一拍就采样，而不是接着上一个播放器的步幅走。
  - **时长轨是用绝对列跳定位的，不是算出来的补白。** 靠补白右对齐会发出 `room - DISP_W`
    个空格，那会把这一列放在**我们的测量**说的地方 —— 而宽度规矩是**按设计多算**的。
    一个由数学粗体字母组成的标题（`𝗖𝗛𝗜𝗟𝗟`：量出 2 格、画出 1 格）会把它的时长停在
    比上一行左约 10 列的地方：参差不齐，而且是在那个唯一因"要被扫视"而存在的列上。
    `\033[<n>G`（ECMA-48 CHA）把光标移到第 *n* 列，不管它之前打印过什么，
    于是即使某个标题量错了，轨在每一行也落在同一格上。列是 1 起的，
    所以一个 `rail_w` 格的右贴字段从 `cols - rail_w + 1` 开始。标题**仍然**被截断到给轨留出位置
    ——这是**由构造保证**的；列跳修的是测量漂移，它不给溢出发许可证 ——
    而在"某个标题渲染得比量出来更**宽**"这种理论情形下，CHA 会往回移动、干净地覆盖掉标题的尾巴，
    而不是把轨推到折行，这正是我们想要的失败方向。它是一次光标移动而不是文本：
    它从不进 `disp_w`，也不打扰 `\033[K` 的处理。
  - **details 段里唯一一件行上没有的事，是简介。** 这个块从前印的是：整条标题（只有在行被截断时
    才有新东西）、`频道 · 时长 · 播放数 · id` —— 时长是 rail 的重复，id 是给人复制的，章节行上更
    是一件新事都没有（`1:47 · CLeZyIID9Bo&t=0`，连 id 都被 `t=` 拼坏了）。原因不在这个块：
    搜索信封里当时就只有这些字段。**每个引擎的搜索响应里本来都带着 `description`，从前都把它
    扔了** —— yt 的 flat 搜索给的是站方自己截断的那段摘要，bili 的搜索接口给的是简介本身 ——
    所以它现在是信封的一个字段（`ARCH-cli-contract.md`「数据契约」），不多花一次请求。块里最多两行，
    **截两次**：先按两行能装的宽度 `truncate_disp`（省略号从这里来，因为折行没有办法说"还有"），
    再由 `WRAP_MAX` 兜底，因为按词折行可能把一行花在更少的字上。
    - **`WRAP_MAX` 住在 `wrap_emit` 那一个出口上**，理由与 `WRAP_LINES` 一样：一个提前停止
      喂数据的调用方就是第二个折行器，可以和这一个在"行落在哪"上产生分歧。标题**刻意不设**
      上限 —— "看到完整标题"正是这个块存在的理由。
    - **章节行的那一行改成说这一章是什么**：`章节 7/53 · 1:47 · CLeZyIID9Bo` —— 位置（行号是
      **过滤后**的序号，章节号是条目的，两者在过滤时不同，所以 `n` 跟着行走）、真时长、
      以及**剥掉 `t=` 的** id。位置只在 `chapters` 与 `parts` 两个源上印，按**视图**把门而不是
      按字段：一个将来长出 `n` 的仓库不该借走这个词。
  - **第二件行上没有的事，是"它到底怎么到我这儿来的"：真正在解码的那一份。** 编解码、分辨率、
    帧率、码率、采样率、声道 —— 一条搜索行里**一个都没有**，而且不是这个块的问题：yt 的 flat
    搜索条目里根本没有 formats 这个字段（对着 yt-dlp 自己的 entry keys 核过），三个站的搜索
    信封都只到"这是什么"为止。这些事实只在**有播放器把流打开之后**才存在，所以它们来自 mpv
    的 socket（`fetch_play_times` 每拍那一批请求），而不是引擎。
    - **不来自引擎，这正是重点。** 播放器记录里的 `selected` 是引擎**要到的**格式串
      （`"251 - audio only (medium)"`）—— 是请求不是答案，对解码器最后拿到了什么只字未提
      （ARCH-player.md「运行时 IPC」）。只有 mpv 知道，而 TUI 本来就每拍在问它。
    - **只印在"正在播的那一行"上。** 它是这个块里唯一一个源头是**活进程**而不是已取回记录的
      成员，所以它只能对那一行为真；印在别的行下面，就是给另一首曲子的说明配了错的图。行的
      匹配走 URL 而不是下标 —— 与 `chapter_span` 同一个 `handle_key`、同一对 `{engine, url}`，
      理由也一样（重排、过滤、翻页都会动下标，动不了 url）。`handle_key` 会剥掉 `t=` 段，
      于是**章节行不需要单独一个分支**就能匹配上：在解码的是整个条目，与playhead落在第几章无关。
    - **九个属性搭的是那批请求已经开着的连接**，不是自己一条 stride：连接、`nc` 的 fork 与 `jq`
      都已经付过了，往一条正在跑的管道里多写九行 `get_property` 是这个文件里最便宜的读，比
      "每首取一次"要配的失效逻辑更便宜（标题那条 tripwire 已经在了，再来一个消费者就是再来一个
      要维护正确的东西）。每拍都取还顺手让 `audio-bitrate` 保持诚实：mpv 是按最近解出来的包算的，
      所以它是个**会动的**估计值，开头几秒不给答案是正常的。
    - **取不到就整段不印，而不是印 0。** 与元数据行丢掉缺失的播放量是同一条规矩：为一件我们
      没有的事实印一个零，是说了一件不真的事。
  - **details 段是变高的 chrome，且在行被画出来之前就测量。** 它占用它需要的高度：一行元数据
    + 至多一行"正在解码什么" + 至多两行简介（简介是**折行**而不是省略，也是这个块里唯一按行
    数变化的成员）。这让它成为"高度取决于**选择**"的 chrome，
    而在行之后才测量的 chrome，花掉的是页眉而不是一行。所以 `print_details` 遵守
    `DETAIL_MEASURE`，方式与 `print_hints` 遵守 `HINT_MEASURE` 一模一样，
    只报 `DETAIL_LINES` 而不画（这需要给 `wrap_print` 加一个 `WRAP_MEASURE` 模式，
    并通过唯一的 `wrap_emit` 汇流，于是计数器不可能与打印器漂移）。让它不循环的是**顺序**：
    先钳住 `selected`（不需要页面几何）→ 为它测量这个块 → 推出 `PAGE_SIZE` →
    再从 `selected` 推出 `page`。因为页跟着选择走，这个块描述的那一行永远在屏幕上，
    所以页永远不可能把选择从测量脚下抽走 —— 没有需要跨多帧才能收敛的东西。
    因此当选择跨过"一行标题"与"三行标题"时 `PAGE_SIZE` 会变化一行；那是"不给标题设上限"
    的既定代价，而 reflow 本来每次重绘都重算它。在一个矮到两者不能兼得的终端上，
    块让位、行留下 —— 与导航提示做的是同一笔交易。
  - **每行十一个原始字段，用 US 分隔 —— 永远不是渲染好的串，也永远不是 tab。**
    details 段每行都需要频道、播放量、直播态与一个 id，所以一行不再是一个显示串。
    前六个是搜索行本来就有的那些；**后五个每一个都是同一条理由长出来的**——
    那件事是**行**的属性，不是会话的属性，也不能从相邻行去推，因为实时过滤一重排就错：
    第七个 `engine`（在播放列表成为第二个行源时加的，ARCH-player.md「持久状态层」）——
    一个存下来的清单可以混源，所以"哪个引擎播这一行"跟着行走；
    第八个 `rail` —— 这一行自己点名的那一格 rail，是十个里唯一一个已经是显示形态的，
    只有章节表写它（一个区间，不是一个长度），别的源留空、照旧由渲染器对 `duration_fmt`
    走 `short_dur`；第九个 `description` 与第十个 `n`（条目里的序号），是 details 段
    要说的那两件行上没有的事（见上面"details 段里唯一一件行上没有的事"与章节那一节）；
    第十一个 `thumbnail`，只有搜索行有，两个存储都不存封面（一个 CDN url 活不过什么，
    ARCH-cli-contract.md「数据契约」）。
    - **第十个字段在队列行源上是承重的，不只是印出来的序号。** 队列行把条目自己的 `index`
      放进 `n`，因为在那里它要回答两件事：哪一行在播（与 `pos` 相等），以及每个动作键把哪个
      `index` 发给 `t-play`。用行记录而不是屏上位置，正是因为**实时过滤与重排会动位置**
      而这个字段跟着行走 —— 和第七、第八个字段被放进记录里的是同一条理由。
    字段数是承重的：`read` 会把剩下的一切都给最后一个变量，
    所以每一处读记录的地方（`load_rows`、`apply_filter`）都必须数得一样多。`IFS=$'\t' read` 会**折叠连续的 tab**
    （tab 是 IFS 的*空白*字符），于是一个空字段会静默地把它后面每一个字段都挪位 ——
    而一条直播行的 `duration_fmt` **就是**空的，一个原型正是这么把频道名读成了播放量。
    ASCII 的 US（0x1f）不是 IFS 空白，所以空字段活得下来；`clean`/`oneline` 把两个自由文本字段
    里的空白折叠掉，于是没有哪个字段能包含换行、把一条记录劈成两条。视频 id 是从 url 推出来的，
    不作为独立字段携带。`play_selected` 直接读那些数组，也就不必"按 ` · ` 切开、
    重新解析那个拼好的显示串" —— 一个标题里含有那个分隔符就会切错。
    同样的 tab 陷阱也在 `t-play -d -j` 的信封解析里（`id`/`pid`/`sock`，
    全都默认 `""`、用 `@tsv` 连接：一个不报 pid 的播放器会把它的 socket 路径放进 `pid`，
    于是守卫拒掉一次其实已经启动的播放）；它现在也读 US。
  - **没有播放量不等于播放量为零。** 当播放量未公开时（每一条直播行、部分投稿），
    信封报的是 `view_count: null`。`// 0` 会把它变成 "0 views"，也就是陈述一个我们并不拥有的数字；
    如今这个字段发成空，details 行把那一段整个省掉。
  - **一页能放多少行是量出来的，不是猜的（reflow）。** `PAGE_CAP = LINES_N - 8` 把 chrome
    硬编码成 8 行，而 chrome 是**由构造**变高的：`print_hints` 按终端宽度打包，
    所以状态块与导航块随宽度与 chrome 语言占 1–4 行。那个常数只有在英文、≳72 列时才对。
    在 tmux 里用真脚本量过：40×20 时 chrome 是 11 行，于是十条一行的行加页脚在一个 20 行的终端里
    是 21 行，把页眉顶出去 —— 与"一行一条行"当初要终结的是同一种失败，只是从另一侧到来。
    50×14 与 62×12 以同样方式坏掉。`display_list_menu` 如今**边打印边数** chrome
    （`print_hints` 报 `HINT_LINES`），再从剩下的推出 `PAGE_SIZE`。
    再重算 `NUM_PAGES`、把页钳住 —— **每一次重绘都做**，于是一次 resize 或一次 `l`
    语言切换会重新分页而不是溢出 —— 一个只在启动时算一次、之后不复查的 `PAGE_SIZE` 会溢出。
    分页圆点那一行只有在**多于一页**时才计费，而且是先对着"没有圆点时的尺寸"检查的，
    于是这次预留不可能循环；另有一行留给光标的停靠行，因为填满最后一行并发出它的换行
    会把屏幕整体上滚一行、于是又赔上页眉。details 段以同样方式计费，来自它自己那次测量，
    顺序如上。
    提示块自己的适配判断也必须预留那一行分页行：块之后的行是空行、一条结果行、
    行后的空行、光标停靠行，**以及**只要列表会分页就会有的页码指示 —— 这个判断只在矮终端上咬人，
    而在矮终端上"多于一个条目"总是意味着"多于一页"。不带它量过（发布版本亦然）：
    一个 62×10 的终端保留了这个块、打印 7 行 chrome、一条行、一个空行和 `page 1/17`，
    把十一行塞进十行 —— 页眉出顶，而这正是 reflow 存在要防的那次失败。
  - **当预算付不起一行时，是页脚把行数还回来。** reflow 里其他每一个块都能丢掉自己 ——
    导航提示会，details 段会。行不能：一个没有行的列表不是列表，所以 `psize` 有一个硬地板 1。
    那个地板会赢过一个为零的预算，于是帧高出一行、把页眉顶出去 ——
    正是 reflow 存在要防的那次失败，只是从下面到来。在 62×12、`/` 打开时量过：
    chrome 8 + 间隔 1 + 过滤提示 1 + 光标行 1 + 圆点 1 + 一行 = 一个 12 行 pane 里的 13 行，
    标题行就没了。所以页脚不是一个数：
    间隔、过滤的说明行、光标行与分页行**分开计费**，而当预算盖不住列表欠下的那些行时，
    它们按价值顺序被回收 —— 间隔什么也不承载，过滤提示教的那个模式它下面的光标行已经在演示，
    分页行是真实状态所以最后走，而光标行永远不丢，因为它回显用户正在敲的东西。
    在 62×12 上这恰好买回需要的那两行：页眉、一条行、圆点与光标行全都活下来。
    只有当再没有什么可丢时地板才溢出，而在那里溢出是诚实的 ——
    那个终端没有任何一种排法能同时显示页眉、一条行与一个光标行。
    回收循环里那个"列表欠不欠一行圆点"的判断用的是 `NUM_ENTRIES > 1`，
    而不是随后给圆点计费时那个 `> psize` 的判断：这个循环只在 `psize` 落到 1 的区间里跑，
    而在那里两者一致。它不是关于页脚的第二种意见，它是同一种意见、只是早到还来得及花出去。
  - **四处降级之间的先后，以及为什么它是一条链而不是一个循环。** 一帧上有四处各自独立的降级 ——
    键块的闸、横幅的字段阶梯、details 段的闸、页脚的按价值回收 —— 每一处的判断都对，
    但它们之间谁先谁后从来没被声明过，于是"在这个终端上该看见什么"答不上来。
    次序不是按重要性排的，是按**测量时刻**排的，而这正是它成不了循环的原因：
    它与上面那条四步链（钳光标 → 为它测块 → 由 chrome 推行预算 → 由光标推窗口）
    是同一条约束的两种说法 —— 键块的内容可以依赖宽度、列表模式、行源、已装引擎和当前播放器，
    **唯独不能依赖行数**。所以**键块先走**：它的闸在最上游，在任何东西能依赖行数之前就决定了。
    所以**页脚的回收最后走**：它是四处里唯一一处已经知道行数的降级，
    也因此是唯一一处**能把行数还回来**的。横幅的阶梯与 details 的闸夹在中间、互不相干 ——
    前者花的是**宽度**，后者花的是**高度**，同一个终端上一个降一个不降不是矛盾。
    把四处连起来的是一对共用的下限：可丢修饰字段的存活下限 `LAYOUT_MIN_FIELD=12`（过滤状态、横幅按键尾与资源占用）与
    不可丢主体文本的预算下限 `LAYOUT_MIN_BUDGET=8`（横幅丢弃时间尾阈值、结果行标题与歌单选择项的下限钳位），
    于是"窄"在这个文件里只有一个意思。两者的数学界线清晰区分了「丢弃阈值」与「截断下限」：
    8 格是核心主体文本维持语义可读的物理底线（2 个完整汉字或 5 个 ASCII 字符加省略号）；
    12 格则是修饰字段值得占据整行宝贵空间的收益阈值（低于此值则信息量过低，不如整段丢弃以腾出空间给主体文本）。
    主体文本自身预算绝不向终端物理宽度之外向上 clamp，以防在极窄几何下折行顶掉页眉。
    **这一条不由套件持有，并且这是有意的**：它的可证明形式是"在某个几何上该看见什么"，
    也就是对一张画面断言，而测试指南明令拒绝这类断言（版面证明归 `capture-pane`）。
    它由 `tests/drive.sh` 在 100×30、62×10、62×12（`/` 打开）、40×20、30×24（播放中）、
    24×24 上驱动、由人读帧确认，硬判据只有一条：页眉在第一行。
    说清楚谁在跑它，是这条不变成"没人跑、于是默认报绿"的散文的唯一办法。
    **跳行的两件事由同一条界线切开，理由完全相同**：`Nj` 之后光标停在第几行、
    待输入的行号画在哪一格，都是对一张画面的断言，归 `drive.sh` 与 `capture-pane`；
    几何表另加两条 —— page 模式下 `12j` 必须把页码带到 2（钳跑在渲染之前，不带就被打回第 10 行），
    以及**同一几何下寄存器空/非空两帧行数必须相同**（后者要单独跑一趟以数字收尾的，
    因为以 `j` 收尾会把寄存器消费掉、拍下来的每一帧都是空的）。
    越界静默 no-op 同样在这一侧：一个没做上界判断的实现把 `selected` 放到列表之外，
    渲染器照样把它钳回来、TUI 照样活着，套件能断言的东西分辨不了这两者。
  - **跨一次重新分页时，锚是**选择**，不是页码。** 用户看的是**一行**。从 `selected` 推出 `page`
    能让那一行留在屏幕上；把选择钳进旧的页码则会把它瞬移 —— 实测：把 24 行 resize 到 12 行，
    每页从 10 条掉到 2 条，选择从第 15 行弹回第 4 行。
  - **矮到放不下提示块的终端，拿到的是它的行。** `HINT_MEASURE=1` 跑 `print_hints`
    完全相同的打包并报出高度而不绘制，于是列表视图可以在真正花掉这些空间之前先问
    "它会有多高？"。低于约 12 行时，导航块是一个 10 行屏幕里的 4 行、无论怎么重新分页都会把页眉顶掉，
    于是它走、结果留下 —— 与 Now-Playing 横幅对它内联提示做的是同一笔交易，
    而横幅的窄终端兜底会把播放键接过去。在 40×10 与 62×8 验证过。低于 24 列的终端按设计仍不在范围内
    （`layout_cols` 的地板）；在 35 列时提示块会如文档所述在条目中间折行。
  - **`truncate_disp` 绝不超过给它的 max。** 把剩余预算往上钳到 1，会打破这个函数唯一的承诺：
    在 `max=1` 时它发出了一个字符**加**省略号，两格。当预算装不下那个记号时，记号就得走。
    今天没有任何调用方会走到那儿（四处不可丢核心文本全部对齐钳在 `>= LAYOUT_MIN_BUDGET` (8)，横幅也在标题空间低于此下限时提前丢弃副字段）—— 它是那条契约上的守卫。
  - **一个钳、一次取数、一条 rail。** `layout_cols` 是唯一的宽度钳（地板 24，无上限：
    列表把全部宽度用于它的行）。地板从 40 降到 24，是因为 40 的钳本身就是它声称要防的那个垃圾：
    在 30 格的 pane 里按 40 格排版，每一行都折，页眉被顶出顶部；24 是最宽的那个单个提示字段仍然
    放得下的宽度。那个**可选上限**曾经是参数，因为播放器卡片传 80、
    免得它们的 rail 在超宽窗口里拉满 —— 卡片走了，参数跟着走：一个视图一个宽度，
    而一个没人传的参数是一个调用方并没有做出的承诺。`fetch_play_times` 是 `PT_CUR` / `PT_TOTAL` / `PT_PCT` 背后唯一的
    `time-pos` / `duration` / `percent-pos` 取数，也是 `CURRENT_PLAY_PAUSED` 背后唯一的
    `pause` 读取，直播特例也包含在内：同样的三条 `nc | jq` 管道在两个播放器视图里各内联一遍
    会漂移，而直播路径取 mpv 的钟只是为了把它丢掉（它描述的是那场广播，不是这次收听）。
    直播路径只问 `pause`、别的什么都不问 —— 一条连接一个属性 ——
    因为暂停 chrome 恰恰是那条路径**免费搞错**的东西：任何别的东西在驱动这个 socket
    （`t-play`、某个 agent 自己的 `nc`、第二个 TUI）都会让横幅断言一个播放器已经离开的状态。
    `toggle_pause` 也不再猜：它调 `t-play --pause`/`--resume` 并从信封里取 `paused`，
    于是横幅在按键那一刻是从一个**读数**重绘的。那次盲翻只作为"一次什么都没答上来的调用"
    的兜底留存，而滴答的读取仍会纠正它。**先乐观，后真相。** 分隔 rail 由 `repeat_glyph`
    构建并按 `(宽度, 字形模式)` 缓存，而不是 `printf '─%.0s' $(seq 1 "$cols")` ——
    那是一次 fork，而且恰恰是 `repeat_glyph` 存在要取代的那个写法，还要跑两遍，
    好让 ASCII 模式下把 Unicode 那条丢掉。`repeat_glyph` 与 `render_prog_bar` 如今像宽度层其余部分
    一样**通过全局量返回**（`GLYPH_RUN`、`PROG_BAR`），于是一次重绘不为它们花子 shell。
- **进程清理保证。** 一个 `EXIT INT TERM HUP` trap 确保 `ting` 会话期间生出的任何后台播放器
  在退出（`q`）时被自动、干净地停掉。
- **过滤是一次对已取行的、纯 bash 的实时收窄** —— 不走网络、不重新取数、不用外部工具
  （这正是 ARCHITECTURE.md「人机面」 得以成立的原因）。`/` 进入过滤模式；**每一次击键**都在 `ALL_ROWS` 上重跑
  `apply_filter` 并重绘，于是列表**边打边窄**（本地列表收窄的最佳实践 —— fzf / 命令面板那一派，
  而不是回车才应用）。`↑↓←→` 在过滤后的集合内移动（共享的 `move_selection`），
  `Enter` 播放高亮的那条匹配，`Esc` 清掉过滤并退出。
  **两条边在过滤开着时不响** —— `move_selection` 里那个 `FILTER_MODE == 0` 的判断：
  过滤给出的是**匹配**的一页，跑到它的尽头不是"再来一批行"的请求。这一条是量出来的，
  不是想出来的：`more_results` 里那句"这里不可能有过滤开着（filter_live 自己占着键循环）"
  曾经是一句**断言**而不是事实 —— `filter_live` 的方向键分支调的就是同一个
  `move_selection`，于是 `/` 之后打 `zzz`（零匹配）再按 `→`，会真的多取 20 行、并把过滤
  丢掉（2026-08-29 实测的红）。现在判据由调用点强制，回归检查在 `contract.sh` 的 TUI 段。
  输入行坐在屏幕**底部**（fzf 风格，列表下方），
  渲染时不带尾随换行，于是**真正的终端光标**就是那个插入符 —— 没有假方块。
  选中行由一个 `> ` 插入符标记（ASCII，不怕字体），不是反显条。匹配语义是社区标准：
  大小写不敏感（`shopt -s nocasematch`，限定作用域）、空格分隔的 **AND** 词元、空查询恢复全部。
  词元在 glob 里被引号包住（`*"$tok"*`），于是用户输入的 `*`/`[`/`?` 按字面匹配 —— 没有注入。
  检索串是**每行每次击键现合成**的，而不是作为第八个字段存下来：行本来就有那些零件，
  这个串永远不会被打印，而一个存下来的键会多出一样需要与渲染器保持同步的东西。
  它含标题、频道、播放量与**两种**时长形态 —— 信封的 `11h:53m:45s`（与过滤器一直以来匹配的东西
  对齐），以及 `short_dur` 的 `11:53:45`（因为那才是轨上显示的形态，
  而一个匹配不了屏幕上那个东西的过滤器，看起来就是坏的）。它还含直播行的字面词 `LIVE`，
  正是这一点让"敲 live"在今天仍然有效 —— 如今已经没有哪一行携带一个渲染好的 `● LIVE` 串可供匹配。
  匹配到的行被原样重新发出，于是 `ALL_ROWS` 始终是唯一来源，一次过滤永远不可能把一行弄劣化。
  `n`（新搜索）保持"回车提交" —— 它要走网络 —— 所以两个提示**刻意**分道扬镳
  （页内过滤是实时的；一次远程搜索是要提交的）。
- **chrome：位置与光标。** "我在这份列表的哪里"曾经是一行分页圆点（`●○○`，当前的那个填实），
  它占掉一整行去说一个数字、超过十二页就退化成 `page X/Y`，而在没有页的模式里根本无话可说。
  如今这个问题由**最右一列的滚动条**连续地回答：每个可见行一格，拇指长度按屏上占比算 ——
  取整而不是截断，否则拇指永远够不到轨道底部，最后一屏会永远读作"快到了"。
  页码只在**有页的那个模式**里作为一段状态出现，不占行。
  它印在标题行上，而标题行先于回流（reflow）画出，所以它除的是**上一帧**的 `PAGE_SIZE`。
  回流一旦改了页大小（键位档切换、resize、首帧的临时页大小），`display_menu` 就在同一个
  帧保持里再画一遍 —— 页大小只由几何决定、不看页码，第二遍即是终值；页大小不变时不多画。
  菜单绘制期间终端光标是隐藏的（于是不会有一个游离方块停在页脚下面），
  只在底部过滤输入、键入式提示与播放时显示；一个 `trap … EXIT` 在退出 / 出错 / Ctrl-C 时把它恢复。
- **一行的两个状态是正交的，而且经常落在同一行上。** 「光标指着这里」和「播放器在放这个」
  从前共用一种画法（选中行加个记号），于是同一时刻只有一个能成立 —— 而 `Enter` 之后的第一帧
  两者本来就在同一行。如今光标是左侧那个槽位里的记号（`GL_CURSOR`），在播是**整行底色**。
  - **`GL_CURSOR` 那次改名换来的东西，现在兑现了。** 它当初与 `GL_PLAY` 同形（都是 `▶`），
    名字先拆出来，就是为了有朝一日其中一个换字形时不必先做拆分；如今它是 `▎`（U+258E）。
    **是一条竖线，不是一个箭头，区别在于这个记号指的是什么。** 三角是个指针，它指向标题的
    第一格，于是它成了那一格上的装饰；而光标选的不是一格，是**一行** —— 说这件事的记号
    应该是一道立在整行旁边的竖笔，用主题色，像页边线标出一个段落。它也更安静：`▶` 是一个
    实心三角，两行之外在播那行还有一个同形的 `▶` 在跟它抢，而 `▎` 在整屏上没有第二种读法。
  - **那个槽位的宽度是量出来的，不是写死的（`mark_w`）。** 从前是字面量 2 —— 那时的记号
    碰巧 ASCII 安全。`▎` 是 East-Asian Ambiguous（块元素被 EAW 从中间劈开的方式与盒绘一样：
    U+2580..U+2595 Ambiguous，U+2596..U+259F Neutral，后者才是转圈动画那四个象限待的地方），
    所以它进 `CW_AMBIG` 跟着 `CW_AMBIG_W` 走，**不进 `CW_NARROW`**：钉成一格，它会在
    `TING_AMBIG_WIDE=1` 下量 1 画 2，让光标那一行的标题比其余每一行都右移一格 ——
    参差就出在眼睛正扫的那一列、正看着的那一行上，也正是「右贴与 `right_edge`」那条 `╸` 陷阱。
    槽宽改为向宽度层要（每帧一次 `disp_w`，对象是个单字符串，不是每行一次）：
    `mark_w = disp_w(GL_CURSOR) + 1`。它在 `▎` 上恰好等于 `CW_AMBIG_W + 1`，
    而在 `TING_ASCII=1` 的 `>` 上仍然是 2 —— 那正是手写 `CW_AMBIG_W + 1` 会算错的一格。
    填了的槽与空的槽都从这一个式子生成，于是两者不可能对这一列有多宽产生分歧。
  - **在播那一行的底，从反白改成了强调色的淡色调（`row_hl_from_accent`）。** 反白是终端能做出的
    对比度上限，而这恰恰是问题：整行反转是一块板砖，它把文字翻成背景色，喊得比它报告的那件事
    更响 —— 在播那一行并不比读者正指着的那一行更重要。淡底把同一件事说在它该有的力度上，
    而且不动文字。**反白留作地板**，给画不出淡底的终端：那里"吵"胜过"没有"。
    - **底色是调出来的，不是声明出来的。** 调色板里只有一个颜色，这是设计（`ARCHITECTURE.md`「人机面」）；
      把底色写成自己的常量，就是每主题每明暗一组，七个主题十四组要跟着强调色一起维护。
      按比例调一次答上每一个主题。
    - **混合是从背景出发、朝强调色走一小步，不是"取强调色的百分之几"。** 第一版就是后者，
      当场有两个主题看不见：nord 的强调色是一支去饱和的冰蓝，取它 30% 得到 (40,57,62)，
      而 nord 自己的底是 `#2e3440` (46,52,64) —— 同一个亮度，一块看不见的底；gruvbox 暗色
      同样落在 `#282828` 的五个点以内。只按强调色算的式子不可能知道这件事，因为它从不看自己画在什么上面。
      **那就去看。** `detect_bg` 本来就在问终端要背景色（OSC 11），从前只留下亮/暗那个判定；
      `BG_R/G/B` 把同一份回复里的**颜色**也留下来，混合对着它做。nord 于是变成 (73,94,107)
      压在 (46,52,64) 上 —— 明显是另一块底，也明显仍然只是一层淡色。不多发一次查询、不多一个依赖，
      答案本来就已经在线上了。
    - **终端不肯答的时候（tmux、`TERM=dumb`、`TING_BG` 写死、`$COLORFGBG`），假定的黑或白是
      同一个式子换了个背景，不是第二条代码路径** —— 从黑出发混合，恰好就是"强调色的百分之几"。
      这也意味着 tmux 里跑到的是回退档：那是诚实的降级，不是 bug。
    - **两个常量而不是一个**（`ROW_HL_MIX_DARK=30` / `ROW_HL_MIX_LIGHT=18`）：眼睛对这两侧不对称，
      淡底上的深色字比深底上的浅色字更早显出色调，所以亮色那一档更轻。
      两个都是百分比，于是将来任何一个新主题都白得一块底 —— 这正是要点。
    - **`minimal` 与 `mono` 没有淡底，这是定义不是遗漏。** 前者的整个立身之本就是只用 ANSI-16
      （它的实际颜色归用户的终端所有），后者刻意无色相；两者都没有可混合的 RGB，于是落回反白地板。
      同理，任何不声明 `COLORTERM=truecolor` 的终端也落回地板。
    - **`set_theme` 一进门先把 `C_ROW_HL` 打回反白。** `t` 键会在活着的屏幕上重进这个函数，
      而一个自己没有淡底的主题绝不能继承上一个主题装上去的那块底 —— 那会是一个主题的颜色活进另一个主题里。
  - **底色是画法上的一个顺序问题，不是一个颜色问题。** 先开底色、再写文字、再 `\033[K` ——
    那一下是 back-colour erase，它把底色带过时长轨的 CHA **将要跳过而不写**的那一段。
    顺序反过来（跳完再开底）行中间就是一个洞，而那个洞占了这一行的大半。
    这条对 24 位底色与对反白一样成立（已在 tmux 下实测：`\033[48;2;…m` + `\033[K` + CHA 跳格，
    捕获回来的那一行底色连续覆盖跳过的那一段），所以换底不动这个顺序。
    **不能用算好的空格去铺底**：宽度层对非 ASCII 是故意多算的，铺出来的底会停在「我们的测量
    以为标题结束的地方」，而不是终端真的画到的地方 —— 每一行 CJK 或数学粗体标题都会参差。
  - **`C_ROW_HL` 的声明值不在调色板里，也不受 `COLORS_ON` 管。** 反白是**属性**不是色相，
    `--color never` / `NO_COLOR` / 管道下也要留着：一个看不见「哪行在播」的终端，比一个没有色相的
    终端糟得多。它是**地板不是成品** —— `set_theme` 会在能画淡底的地方把它换掉（见上）。
    `C_ROW_END` 必须是它自己那个 `\033[0m` —— `C_RESET` 在关色时是**空串**，
    拿它收尾会让底色一路铺到屏幕底部。
  - **在播那一行是按 url 认的，不是按下标记的。** 「这一行在播」要在换排序、换过滤、改行数、
    切列表模式之后仍然成立，而这四件事都会改下标、都不会改 url。判定用的是 `handle_key`，
    与章节行上的 Enter 决定 seek 还是 launch 时问的是同一套归一化。
    **每帧只算一次**（`PLAYING_IDX`，在渲染循环之前）：3.2 没有关联数组，写进循环就是每行一次
    平行数组扫描 —— 而按字节读键意味着一次 CJK 按键是三遍读取、三次重绘。
    章节视图是唯一的例外，那里 url 天然不相等（章节行带 `&t=`），在播的那一章是**播放头落在
    它区间里**的那一章：先在条目自己那张有序的章节表上找一次区间，再拿它去比可见行，
    而不是对每个可见行问一次 `chapter_span`（那会是 35 × 20 而不是 35 + 20）。
  - **滚动条画在底色之外。** 反白档下那个 `█` 是一个洞，正好落在读者最可能盯着的那一行上。
    所以底色铺到时长轨那一列为止，不到屏幕边。
- **屏幕上每一个右贴都从同一个式子来（`right_edge`）。** 时长轨、状态段与播放横幅三处右缘
  各算各的，就一定会有一处差一格；而差一格的症状是折行，也就是**多出一行 reflow 不知道的高度**。
  **进度条不在这份名单里，而这是它的定义而非疏漏**：它是分隔线，不右贴任何东西，
  按 `nav_cols - 1` 铺满整屏（见上面「进度条就是那条活的 rail」）。
  一个右贴字段与一条横线遵守同一个式子，正是当初让它读起来像字段的那件事。
  它是 `nav_cols - CW_AMBIG_W - 1`：最后那一列（或两列）是滚动条的，再加一格空气。
  **`CW_AMBIG_W` 而不是字面量 2** —— `█` 与 `│` 是 East-Asian Ambiguous，`TING_AMBIG_WIDE=1` 下
  gutter 真的是两格宽。这条推理反过来也咬过一次：盒绘块被 EAW 从中间劈开（满长横线
  Ambiguous，重半线 2574..257F Neutral），所以进度条那个 `╸` 播放头当初必须进 `CW_NARROW`
  而不是跟着 `━ ─` 进 `CW_AMBIG` —— 进错了表，它在 `TING_AMBIG_WIDE=1` 下会变两格，
  把 bar 顶出它被测量的宽度。那个字形如今已经不画了（见「进度条就是那条活的 rail」），
  于是这条陷阱只剩下"每加一个 chrome 字形都要先问它落在 EAW 哪一边"这条教训。
- **状态是一串**值**，不是一串 `键=值`。** 从前那一行是 `engine=yt  results=40  sort=view_count
  auth=chrome  mode=video (video-enabled)` —— 一份 debug dump，而且是整屏最宽的一行。
  每一个 `键=` 都在给一个**自己已经说明了自己**的值命名：只有音源会拼成 `yt`，只有计数会拼成
  `40 结果`，而 `mode=video (video-enabled)` 用两套词把同一件事说了两遍。所以键走了、值留下。
  **说不清自己的那几个各留一个词，把 `=` 换成一个空格**（`音量 40`、`队列 2/5`）：
  一个裸 `40` 和一个裸 `2/5` 是读不出来的。分界线就是这一条 —— 值能独立成立时段就是值，
  不能时是一个短语，永远不是「字段名加标点」。auth 那一段说的是**有没有登录**而不是哪个浏览器：
  `chrome` 作为一个段命名的是一个程序，不是一个状态。默认值仍然一格都不占，规矩没变。
  省下的那一行是这么省的：段短到可以右贴在标题行上，而标题行本来就有一整个空着的右半边。
  **标题行的来源字段留着** —— `query='chill'` 与 `playlist='chill'` 是全屏唯一一句说明这些行
  从哪来的话，而没有任何一段携带它（一个歌单和日志用的是同一个计数单位）。
- **一帧是三段：上带、行、下带。** 键位块搬到了最底下（chrome 收在两端，中间全是内容），
  于是下带里同时有两个**高度可变**的成员。保住它可单遍算出来的是**顺序**，四步，抄的是详情块
  一直在用的那条链：① 先钳光标（不需要任何窗口几何）② 为它测详情块（需要光标，不需要行数）
  ③ 由测得的 chrome 推行预算 ④ 由光标推窗口。
  **所以键位块的内容可以依赖宽度、列表模式、行源、已装引擎、播放器状态 —— 唯独不能依赖行数。**
  一旦它读行数，① – ④ 就从一条链变成一个环；而一个在 100×30 上第一遍就收敛的环，
  要等到有人改变终端大小才会露面。它的高度在任何一行打印之前就记了账，它的**内容**在横幅
  打印之前就定了 —— 后者是横幅那条窄终端兜底（"键位块被丢掉时我来说播放键"）不至于依赖一个
  在它之后才做出的决定的原因。
  下带按价值回收：两条空行分隔先丢（一条分隔线什么也不携带，它只说明两样东西不同，
  而这件事它们的内容已经说了），然后是过滤器那条说明行（它在教一个下面那个光标正在演示的模式）。
  键位块不进这个回收循环，光标永远不丢。
  - **横幅那条占位空行取消了。** 它原来是为了「开始播放时列表不跳」而留的；键位块搬走之后
    它成了连着两条空行里的第一条，而标题下面两条空行读起来像渲染出错。代价明写：现在开始播放
    列表跳**两行**（横幅加它的进度条）而不是一行 —— 那一帧本来就整屏重绘，
    而换掉的是一条在每一次没有播放的会话里一直挂在屏幕上的空行。
- **跳行只有一条规则：数字打进一个寄存器，`j` 结束它。** 从前是一键一行 —— `1`–`9` 跳可见窗口的
  那一行、`0` 特判成第十 —— 于是第 12 行**根本叫不出名字**，而且那套编号是**窗口相对**的，
  跟旁边那列从列表顶上数起的绝对序号在第一屏之后就对不上。现在两者是同一个数。
  代价明写并接受：`3j` 比从前的 `3` 多一次击键。换来的是键盘上只有一个跳转手势，
  而不是「小于十走这条、十以上走那条」的两套。
  - **消歧靠终结键，不靠时钟。** 等待窗口会把代价压在最常用的那条路上，而这个仓库刚拆掉一个
    「为了确认 Esc 是孤立的而等一秒」的等待 —— 再装一个是走回头路。
    非数字非 `j` 的键清掉计数并**照常执行**（vim 的规矩）：吞掉那个键会把一次误触变成两次。
  - **清空点在两个 case 段之前，不在列表段里。** 通用段九条 arm 全部以 `continue` 收尾，
    根本走不到列表段 —— 清空放在后面，`1` `=` `j` 会跳到第 1 行而不是下移一行。
    一处清空，不是每条 arm 各清一次：后者是一张要维护的名单，漏一个就是一个不清空的寄存器。
  - **`j` 必须先从方向键那条 pattern 里摘出来。** bash 的 `case` 取第一个匹配，
    留在上面的 `j` 会让新 arm 变成死代码，`Nj` 静默什么都不做、还不报错。
  - **数字读作十进制是护栏，不是风格。** `0` 成了合法首位之后 `010` 会被当八进制读成 8，
    而 `08` 更糟：3.2 上那是 `value too great for base` 打进帧里。实测（2026-09-02，
    对着一份故意改坏的副本）**整个 TUI 活不过去**，所以 `contract.sh` 的证人是它后面那个
    `n` 提示开不开得起来，而不是那行错误文字 —— 死掉的 pane 抓下来是空的，grep 得干干净净。
- **行号是可关的，而跳行不看它。** 大多数时候光标就回答了「哪一行」，一列序号是**每一行**
  都在付、只为十次里那一次跳转服务的 chrome，所以出厂是关的（`UT_ROW_INDEX`，`#` 键切）。
  `Nj` **不依赖**这个开关：一个含义随显示状态改变的键，是穿着一套键位衣服的第二套键位 ——
  这也正是打第一位数字时**不**替用户把行号临时打开的理由（那还会改变行前缀宽度 `iw`，整列右移三格）。
  开关决定的是这个地址**看不看得见**：地址是绝对的，关着行号时第一屏之外就只能靠数。
- **待输入的行号画在光标停靠行上，右对齐**（vim 的 showcmd）。三条理由各自都够：
  (1) **帧高必须不变** —— 自己占一行的回显会在敲第一位数字时抽掉一条结果行、按 `j` 又还回来，
  每跳一次闪一下，而且它让一个块的高度依赖「后来才知道的东西」，正是四步链禁止的；
  光标行本来就在 `LAYOUT_CURSOR_ROW` 的预算里，画上去一格不多花。
  (2) **它永不被回收** —— 页脚按价值回收会依次丢间隔、提示间隔、过滤说明行，唯独光标行不丢，
  所以这块画布在 24×24 上也在。(3) 过滤模式走另一条分支，那里数字是查询文本，寄存器不存在。
  右对齐的列是 `right_edge - 宽度 + 1`，与状态段共用同一个表达式；**直接跳到 `right_edge` 是错的** ——
  那是最后一个字符该落的列，从那儿起打会越过 `nav_cols` 折行，而在最后一行折行就是一次换行、
  屏幕整体上滚、页眉出顶，正是这个落点要防的那次失败。
- **取数 spinner。** 一次搜索是 TUI 唯一无物可画的时刻 —— 在启动时它更是一个空白终端上唯一的东西
  —— 而一条不动的 `searching "lofi"…` 读起来像卡死了，这就是为什么这一行如今以一个转动的象限结尾
  （`▘▝▗▖`，`TING_ASCII=1` 下是 `|/-\`）。三个值得留住的决定：(1) 它夹的是 `fetch_json`
  而不是它的调用方，于是启动取数、`n`、`→` 与 `o` 全都从**一个**实现里得到动画，
  第五个调用方也会自动拥有它；(2) 跑在后台子 shell 里的是**动画**，不是搜索 ——
  把搜索后台化需要一个 rc 文件和一个完成标记，因为 `kill -0` 对一个未被回收的子进程仍然成功、
  于是轮询永远不结束，而且 `fetch_json` 那三个不同的返回码还得靠文件偷渡回来；
  (3) 计时器是 `sleep 0.12`，因为 bash 3.2 没有别的 —— 那里 `read -t` 会把小数超时截断
  （实测：`-t 0.2` 在一个 5 秒的管道上一直坐到底），而 1 秒一帧不算动画。
  每一帧打印自己的字形再退格盖回去，于是这一行永远不变长；`spin_stop` 擦掉最后一帧并收尾这一行，
  正是这一点让 `report_fetch_failure` 的句子落在干净的一行上。echo 在 `spin_start` 处关掉，
  并且**刻意不恢复** —— 否则一个在取数中途按下的键会落进 spinner 那一行里，
  而每一个调用方都正走向菜单循环，那里本来就是关着 echo 跑的。
- **一个时钟。** 按视图授予 `read_nav_input` 的 `-t 1`（当年是卡片永远有、
  列表只在 `CURRENT_PLAY_LOADING` 时有）会让列表一个活元素都不能有，
  而同一个超时授予两次就是两个改节拍的地方，它们会漂移。条件只有一处，
  而且它不问是哪个视图在上面：它问的是**有没有东西在等这个时钟** ——
  屏幕上有东西能在不按键的情况下变化（那就是播放），或者内存里有一个偏好还没落盘。
  `[[ -n "$CURRENT_PLAY_ID" ]] || ((CURRENT_PLAY_LOADING)) || [[ -n "$PREF_DIRTY" ]]` ——
  play id 覆盖一个正在跑的播放器，LOADING 覆盖 socket 出现之前那个窗口，
  那时 spinner 必须在还没有任何东西可轮询之前先转起来，第三个覆盖延后的写回：
  没有它，一个什么都不放的会话里改的偏好会一直停在内存里到退出为止 ——
  阅读器会**阻塞**，`nav_tick` 根本不跑。一串 cycle 键因此只多付一次醒来，
  而那一串正是延后本身要吸收的东西。它**刻意**是双向的：
  列表在整个播放期间都滴答（它的 rail 是活的，见下），而什么都不播时**没有东西**滴答 ——
  当年那张卡会永远每秒重画一次静态的 `(nothing playing)`。实时过滤免费搭上这趟车，
  因为 `filter_live` 驱动的是同一个读取器。
  - **`read_query_input` 被刻意排除在外。** `n` 新搜索提示有自己的读取器、且不带超时：
    在那里滴答会在一条查询正被键入时把屏幕重画。
  - **时钟拥有轮询，渲染器不拥有**（`nav_tick`）。渲染器只需要百分比给它的 rail 与横幅，
    所以那次轮询在滴答上发生。`fetch_play_times` 是一对 `nc` + `jq` —— 两次 fork ——
    把它放进渲染器会让每一次方向键按下都赔上一次 IPC 往返。一次在两拍之间发生的重绘
    复用上一次的值，最多一秒旧，而那本来就是 rail 绘制的分辨率。**每拍恰好一次轮询。**
    （当年那张卡在自己的渲染器里轮询，因为它的整个正文就是那个读数 —— 于是同一拍会有两次；
    只剩一个渲染器之后，这个例外没有了。）
- **两条一模一样的满幅横线，是这次改版删掉的第一样东西。** 曾经有两条：一条收住 chrome 带、
  一条开启 details 段，同一个强调色、同一个宽度、一屏之隔。读者会去找一个并不存在的区别 ——
  而在章节视图里那个区别**真的存在、却看不见**：下面那条其实是第二个进度条，画的是播放头在
  **被选中那一章**里的位置，上面那条画的是它在整个条目里的位置。两个时钟，一个形状，没有标签。
  所以那条边界线走了（chrome 与行本来就靠暗度和位置分开，下面那条空行足够当分界），
  读数以**一条**独立的进度条回来，坐在它所描述的那个横幅正下方。
- **章节那个事实没有被丢掉，它搬到了同一条 bar 上，变成 rail 上的两处断口。** 断口标的是
  **光标所在**的那一章在整片里的起止，而不是在播的那一章 —— 在播的那一章已经由它自己那一行的
  反白说了，bar 上再说一遍就是这次改版要删的那种重复。于是读法是位置性的：断口在播放头右边 =
  还没放到，在左边 = 放过了，夹住播放头 = 你正在里面。撞格时**播放头赢**：它是关于这一秒的
  事实，而断口还有另一端可以说话。
  - **标记就是那个断口本身，不是画在断口里的任何字形。** 两个候选都在真实宽度下画出来看过，
    都输给了同一件事。`[`/`]` 是**坐在 rail 上的标点**：两个墨重、笔画家族又不同的字形，在整屏
    唯一一行"要一眼读完"的线上跟那道粗细变化抢注意力。`│` 更细、也确实属于 rail 自己的笔画家族，
    但它输的理由和括号一样：**一道竖笔横穿一条横向 rail，会把顺着它扫过去的视线拦下来。**
    这一行的读法是从左扫到右 —— 进度条本来就是这么一回事 —— 而一道通高的竖笔就是横在这道
    扫视上的一堵墙，还是两堵。只有断口不打断这个流，因为它根本不是一个标记：rail 停一格再
    接上，本身就已经是一条边界 —— 这与当初把 bar 自己那对端括号拿掉时是同一条论证
    （见上面「进度条就是那条活的 rail」）。它在两种模式下几乎都是白给的：一个空格在任何
    宽度表下都是一格。
  - **每一处断口都恰好是一格白，而且每一处都只是一个空格。** 这曾经要专门补偿：断口一旦落在
    播放头 `╸` 的右邻，那半格留白加上一个空格画出来是**一格半**白，一眼看过去就比别处宽，
    于是那个位置改画 `╶`（细右半线）把缺的半格补回来。如今这一行上没有播放头字形了
    （见「进度条就是那条活的 rail」），断口两侧每一格都是满格笔画，一格白是构造出来的结果，
    那个特例跟着造成它的字形一起消失了。
  - **区间不足三格时只留开口那一处断口。** 两处断口中间什么都没有，那不是一段区间；更要命的是
    两处断口会**相邻**，画出两格白、读起来是一处宽断口而不是两处边界。这一行上每一处空白
    要么是一格、要么就不是断口，所以宁可把收口那处丢掉，也不让它把开口那处的白撑成两倍。
  留空只留给答不上来的问题 —— 没在播、直播、还没有读数、播放器里是**另一个**条目
  （`handle_key` + engine 这一对，与章节行上的 Enter 在决定 seek 还是 launch 时问的是同一个问题）、
  或者引擎没有发布 `end_time`。章节的终点是**按起点**在条目自己的章节表里查的，不是按行号：
  过滤与翻页会重排行（`chapter_sec` 从行的 url 里把偏移读回来正是为此），
  而 `ITEM_CHAP_*` 是引擎发布的整张表。
  函数因此从 `chapter_pct` 改名 `chapter_span`：它现在返回的是起止秒数，不是百分比，
  而一个不返回百分比的 `_pct` 是要先被怀疑才能用的名字。
- **光标跟着播放头走，而不是跟着按键走（`chapter_follow`）—— 章节视图的另一半。** 少了它视图会
  冻住：一章放完了却仍然被选中、断口还夹在它上面，而正在播的那一章在屏幕上没有任何东西说明这件事。
  缺的是**选择本身也是条目那个时钟推动的东西**。
  是**跟随**，不是抢夺：用户一动光标就归用户。`CHAP_FOLLOW_SEC` 记住上一次看时播放头在哪一章，
  只有当选择还停在**那一章**上才移动 —— 曲目在播时往下翻两章看看，不会有东西被夺走。它存的是
  起点**秒数**、从不是行号，理由与 `chapter_sec` 存在的理由相同：过滤与翻页会重排行，一个行号
  在下一次按键之后就指向另一章了。锚在 `ITEM_URL`/`ITEM_ENGINE` 而不是被选中的行上，因为问的是
  **这个视图**的问题（这里每一行都是同一个条目的一个偏移），答案不该随光标移动而改变 —— 于是
  `chapter_span`、`play_chapter` 和它对"播放器里是不是这个条目"的理解是同一个。
  `open_chapters` 在门口先跑一次同一个函数：播放器里就是这个条目时，视图**开在正在播的那一章**上。
  播放头在第 9 章而光标在第 1 行，既是卡住感的第一帧，也会把光标停在任何一次跨界都够不到的地方。
  翻页由它自己设 `page_index`（`selected / PAGE_SIZE + 1`，与 `display_menu` 重新分页时同一个式子）：
  一个随后被主循环钳回旧页的选择，等于没有移动。`filter_live` 也调它，理由与它同样要调
  `check_player_alive`/`player_check_ready` 一样 —— `/` 开着时那个循环不回主循环，它略过的东西
  就冻结整场；而过滤掉了新那一章时，光标就留在原地。
- **三个播放态，不是两个。** `-d` 在播放器一 fork 出来就返回，但 mpv 还得经 yt-dlp 解出流、
  填满它的缓存，而在一个冷 URL 上那是**好几秒**（实测：第一次播一个 lofi 混音约 9 秒）。
  横幅在整个静音窗口里一直宣称 `▶ Playing`。如今在"已启动"与"出声"之间有一个 `Starting` 态，
  用的是取数 spinner 那几帧象限，于是这次等待看起来与它之前那次等待是同一件事。
  四件事让它成立：
  - **看 `core-idle`，不看 `time-pos`。** mpv 早在放出一个音符之前就会应答 IPC。
    `core-idle` 在播放器什么也没产出时为真 —— 加载、seek、等缓存 —— 并在输出开始的那一刻翻假，
    而那恰恰是标签该翻的那条边。`time-pos` 在文件仅仅被**加载**时就非空，
    于是它会把一条还在缓冲的流叫做"正在播放"，把问题又放回原处。
  - **正是这个状态第一次让"会滴答的列表"成为必需**（见上面的共享时钟）。
    一个只在按键时刷新的横幅，就是 `check_player_alive` 存在要防的那种陈旧 bug。
  - **一个裁决者。** `play_state_marks` 挑字形/标签/颜色；横幅传入自己的 "playing" 字形
    （`▶`）并画出返回的东西。它是为两个视图写的（卡片传 `●`），而状态与字形本来就是两件事，
    所以少了一个调用方之后它照旧带着那个参数。
  - **这个窗口里刻意不画 rail。** 列表保持它的静态分隔线 —— 活 rail 需要一个百分比而此刻还没有。
    考虑过一条"不确定"的动画 rail 并谢绝：它会成为紧挨着 spinner 与标签的**第二个**状态指示器，
    与横幅标题丢掉它的 `▶` 所针对的是同一种重复，还额外附赠一个代价 ——
    一条停在 40% 的扫描线与一首播到 40% 的曲目分不出来。而列表自己那一行无论如何都不改变宽度，
    这正是"静态"这个选择在那里免费的原因。
  - **除了成功之外还有两条出路。** 窗口期内的一次暂停会清掉这个状态 ——
    暂停时 `core-idle` 保持为真，所以那个探测永远清不掉它，而在一个用户刚刚暂停的播放器上写
    `Starting` 是一句错话。以及一个 20 秒的上限无论如何都会清掉它：
    在一条慢成那样的流上，选择是"一个永不收敛的动画"与"这个状态存在之前它显示的那个乐观标签"
    之间的二选一，而上限选后者，且只选一次。
- **URL 管道：** url 是那条 US 分隔记录的第 1 个字段，`load_rows` 把它连同那一组 `R_*`
  字段数组一起拆回 `urls[]`（bash 3.2 没有关联数组，也没有数组的数组，所以是一组平行数组），
  于是一次选取就是一次直接的数组下标 —— 绝不重新解析一条渲染好的行。
  标题不可能打破字段边界，因为 `clean` 会折叠空白（于是没有 tab 或换行活得下来），
  而分隔符是一个没有标题会携带的控制字符。
- **拒绝而不是挂起：** stdin 与 stdout **两者**都必须是 TTY，否则就 die，
  于是一次 agent/管道调用干净地退出，而不是阻塞在键盘输入上。`-h` 不需要 TTY 也能用。

### 可撤销取代预先确认

`d`、`D`、`X` 曾经各问一次 `(y/N)`；现在它们一个键生效，`z` 在 3 秒内撤回它、以及 `a`、`R`、
`+`、`x` 这些写。存储这一半（副本、核对、拒绝）在 [`ARCH-player.md`](ARCH-player.md)「撤销副本」，
这里只讲界面这一半。

- **确认挡不住误操作，撤销才能。** 连续整理时 `d → y` 很快练成一个连招，误触的那一下 `y`
  早已按下；确认的代价（两个键、一次停下来的帧）是真的，保护却是虚的。队列的 `x` 从一开始就
  不问，理由是"放错了用 `+` 放回去"—— 能不能零确认取决于恢复有多便宜，而不是操作本身多危险。
  所以缺的是一个通用的、一个键的恢复手段；有了它，三处确认连同 `confirm_key` 一起删掉，界面里
  占住输入的阻塞读只剩 `prompt_name`。
- **副本不在 TUI 里。** `ting` 只记四个标量：副本在哪个存储、提示开到什么时候、提示位上说什么、
  有没有挂起的停播。副本由拥有对象的命令在那次写的锁里写、按 `--owner $$` 分槽，能不能撤销永远
  由它判定。第一版设计是 TUI 自持一个内存缓冲，核查出十几处问题，根源只有两个：缓冲活得比屏幕上
  的提示久；缓冲只靠一个名字认对象。把副本交给所有者，这两个问题在结构上就不存在了。
- **全套件一个槽。** 写到另一个存储时，先让旧存储丢掉本进程的副本，所以 `z` 永远是"刚才那一下"，
  不会变成一个栈。
- **提示可见 ⇔ `z` 有效。** 两件事让这条从第一帧起成立：
  - **提示接在已有的 notice 后面，而不是等提示位空出来。** 写完那一帧提示位几乎总被占着（那次写
    自己的结果、删空后的 `S_PL_EMPTY`），等空位就恰好错过用户最想撤销的那一刻。撤销提示先量宽、
    不截断，标题再长也挤不掉 `z`。
  - **时钟是 `$SECONDS`。** 截止时间以 epoch 秒到达，写成功时换算一次；此后每帧、每轮的"还开着吗"
    都是算术，不 fork —— bash 3.2 既没有 `EPOCHSECONDS` 也没有 `printf '%(%s)T'`。读键的 1 秒时钟
    在有撤销时也走，否则没有播放、没有按键时，提示关闭的那一帧没人画。两个时钟都是整秒，差出来的
    那一秒里 `z` 得到存储的 `undo_expired`，照实说"无可撤销"。
- **复制不了的副作用推迟到提示关闭。** 停掉的播放器放不回去，所以 `d` / `D` 删到正在放的曲目时，
  停播挂起到提示关闭；`z` 在此之前按下，播放从未中断。
  - **到期判定在两个占屏循环（主循环与 `/` 过滤）的每一轮开头，不在 `nav_tick`**：`nav_tick` 只在读键
    超时时跑，按住 `j` 时它一次也不跑，挂起的停播就会拖到用户松手。
  - **提示以别的方式失效时，挂起的停播当场付**：新的写替换了槽、存储拒绝了 `z`、到期 —— 撤销再也
    做不成了，停播就不该再等。这条只写在一个函数（`undo_forget`）里。反过来，任何一次停播
    （`Enter` 换歌、`s`、`q`）都清掉挂起：已经没有东西可停了。
  - 阻塞提示（`a` 的选单、`R` / `n` 的输入）期间主循环不转，停播推迟到提示返回后的第一轮。那时撤销
    早已过期、用户在打字，晚停几秒无害，不值得为它在阻塞读里另开一个时钟。
- **撤销之后画的是存储说它恢复了什么。** 光标放在信封的 `index` 上，不用 TUI 自己记的下标 —— 列表
  可能已被别处改过，只有所有者知道那一行回到了哪里。改名的撤销靠信封的 `from` 认出屏幕上显示的是
  哪张列表（改名之后屏幕上是新名）。`D` 或删空的 `d` 把人带回了搜索，于是在搜索视图里撤销它们会
  重新打开那张列表；别的视图只给一句提示，不跳转。存储拒绝时（`undo_stale`：列表已被别处改过）
  不刷新、不猜；只有 `locked` 保留提示，因为副本完好、重试能成。
- **退出时丢掉副本。** `cleanup_on_exit` 调一次持有副本的那个存储的 `--undo --discard`；`kill -9`
  跳过这一步，由存储自己对死 owner 的扫尾兜底。

## 封面 —— 焦点行的一张图，走自己发的 kitty 协议

**这一节的每一条都是被实测钉住的，包括三条"画图这件事弄坏了 TUI"的教训。**
能力是可选的：`UT_IMAGE` 关着或终端不答，一个字节都不发，这个面与从前逐字节相同。

**为什么是详情区右栏，而不是每行一张。** 一行文本放不下一张图，行高变成 3 就是把 reflow、
分页与 `PAGE_SIZE` 的推导全部重写（「重排」）；而详情区**本来就**被声明为"变高的 chrome，
要多少占多少，终端太矮就整块丢掉"。把图挂在它身上是**延用一条既有契约**而不是新开一条，
并且让图的生命周期只绑在"焦点"这一个变量上 —— 这是能表达它的最少状态。

**那几行必须计入 `detail_h`，哪怕图画在文字旁边**；而且**有图无图都要计**。不计，重排就不知道
这几行被占了，光标的停靠行会撞进图的下半截；只在这一行有图时才计，上下箭头每跨过一条没有
封面的行，列表就重排一次、文字的折行宽度就跳一次。**版面不随行的内容改变**，这是同一条
"绝不抖"的规矩（「重排」）在这里的样子。

**闸门问的是列表还剩几行、文字还剩几列，不是终端有多大。** 出厂已是 `scroll` 滚屏模式，
`psize = avail` —— 把详情区顶到 7 行，是**实打实地从列表里挪走 4 行**。闸门保的是
"还剩至少 4 行可浏览"（兼容主流默认 24 行终端高度）与
"文字还剩 50 列"。过不了就**一张也不画** —— 不画小一号的，因为小一号意味着第二个转码目标
和第二套版面要跟着对齐。在 Kitty 协议发射上，严格遵循分块终结规范：最后一块真实数据携带 `m=0`，
杜绝尾随空块导致 Base64 解析器拒收。同时 `auto` 模式直接基于 `TERM`（`*kitty*`/`*ghostty*`）
与 `TERM_PROGRAM`（`ghostty`/`wezterm`/`kitty`）快速就绪，消除 tty 繁忙时探针超时的假阴性。

**闸门关上时，连同 `image_focus` 的备忘一起清掉 —— 只清脏位是不够的。** 关着的那一帧必须
把脏位清零，否则一个不会画图的屏幕会把一秒一次的时钟永远吊在那里，每一跳都为一张没人
要画的图起一次取图。但 `image_focus` 是**按行的 url 记忆化**的：同一行问第二次直接返回。
于是只清脏位、不清备忘，闸门在**同一行上**关掉又打开，这一行就**卡死**了 —— 既没有图，
也不再打算去要一张，因为备忘说这个问题已经答过了。实测 2026-09-03：第一张图还在飞的时候
把 100 列缩到 70 列（详情文字只剩 43 列，压在 50 的地板下，而行数一行没变、光标一步没动）
再放回来，这一行直到光标离开又回来才重新有图。所以两者一起清；代价是闸门重开的那一帧多一次
glob，关着的时候一次都不多 —— 那时 `image_focus` 根本不被调用。

**格子尺寸是问出来的，不是算出来的。** "一格大约宽 1 高 2"能推出 24×7 = 192×112px，
而 2026-09-03 在 Ghostty 上实测 `CSI 16 t` 报的是 **16×36 px**（长宽比 1:2.25）——
按 192×112 转码，画出来是 **12 列 × 3 行**，不到目标的四分之一。转码目标在**像素**里，
贴图在**格子**里，两者对不上时图是**尺寸错**，不是"重采样得差一点"。问不出来才退回 8×16。

**只给 `r`、不硬传 `c`，列数由终端算。** 实测：一张 192×108 只给 `r=7`，终端分配 7 行 ×
**28 列**，与"按 7 行高等比放大再折成格子"算出的 448÷16 分毫不差。配合转码阶段的
`force_original_aspect_ratio=decrease`（把图**装进**边界盒而不是**拉满**它），
16:9 占满整格宽，网易云那种 1:1 唱片封面自然是正方形 —— 站点的宽高比不需要任何分支。

**`image_clear` 的 `d=i` 不是可省的。** kitty 的图**不在字符网格里**，`\033[K` 与 `\033[J`
都擦不掉它，所以必须显式删；而 `a=d` 的 `d` 键**缺省值是 `a`——屏幕上所有贴图**，那时 `i`
根本不被读。在复用器里那会把别人的图一起删掉。退出的 trap 用大写 `d=I`，连图像数据一并释放，
且与恢复光标、恢复 echo 在同一处 —— 自绘的 UI 拥有整段会话的终端状态，就在一个地方还回去。

**`C=1` 与 `q=2` 各挡一件事。** `C=1` 让光标压根不动：`a=T` 默认会把光标推到贴图之后，
在靠下的行画图就会把整帧顶掉一行 —— 正是重排存在要防的那种失败，从下面来。
`q=2` 让终端一个字节都不回：任何应答都会掉进 `read_nav_input`，被当成用户按了几个键。

### 三条"画图弄坏 TUI"的实测教训

**它们都不是画得对不对的问题，而且都由 `tests/contract.sh` 的 tmux 段抓到** ——
那一段整体跑 `UT_IMAGE=on`，图的**样子**在 tmux 里确实看不到（tmux 不转发图形转义），
但抓住这三条靠的根本不是看画面：它们表现为 TUI 自己启不来、按键不生效、或者当场死掉。
换句话说，价值在于让整条路**真的跑起来**，而不在于让它画。
（发没发是另一回事，`pipe-pane` 读得到，见本节末尾。）

1. **`ls … | head -1` 会杀掉进程。** 缓存里还没有这张图时 `ls` 非零退出，`pipefail` 让管道
   带着它的状态，赋值继承，`set -e` 收工 —— 而"还没有"正是每一行第一次被选中时的常态。
   两处都换成 glob 循环，顺带省掉渲染路径上的两次 fork。
2. **mpv 会抢走终端。** 转码用的 mpv 与 TUI 共用一个 tty，默认终端处理会**读走按键**，
   表现是 `#`、`v` 这些键突然不生效。`--really-quiet` 挡不住 —— 那管的是输出，问题在输入；
   要的是 `--no-terminal` 加 `</dev/null`。
3. **一次 39KB 的写会被信号打断，然后 `set -e` 杀掉 TUI**（`printf: write error:
   Interrupted system call`）。封面是这个程序里最大的一次写，大到足以在 `write(2)` 里被信号
   撞上，而信号是常态：后台转码结束的 `SIGCHLD`、拖动改窗口每一列一个的 `SIGWINCH`。
   于是**发射里每一次写都容许失败**：失败不是错误，是"这一帧没有封面" —— 把半张图删掉、
   `IMAGE_DRAWN` 保持 0，下一帧自己重发。**重绘就是重试。**

**取图必须跑在按键循环之外，而这是正确性不是快慢。** 一次 curl 允许 5 秒，串在时钟上就是
键盘 5 秒不应答；套件当场就红给我们看（过滤器缩不到 0、存储键打不开），因为按键排在下载
后面。所以是一个后台子 shell，**同时只允许一个在飞**（按住 `j` 翻十行，中间九张没人会看）。
子 shell 里**必须** `trap - EXIT INT TERM HUP` —— 否则每转码完一张就跑一遍 `cleanup_on_exit`，
**把用户正在放的曲子停掉**。

**过渡期状态信息（`image_status`）居中发射于字符网格。** 在光标落入焦点行、封面拉取与转码尚未
完成的过渡阶段（`IMAGE_PNG` 为空但该行有封面 URL），详情区右栏 24×7 字符网格被填充为垂直与水平
居中的淡色动画状态提示（`${GL_SPIN} loading pic...`）。提示借助终端既有光标绝对水平跳转与
相对垂直回溯输出，不破坏左侧详情排版；转码完成并发射 Kitty 贴图后，图形协议图层直接覆盖其上；
若光标切走则由重绘行首擦除，保证过渡视觉确定且无撕裂。

**缓存在 `${TMPDIR:-/tmp}` 下，不在 `$UT_STATE_DIR` 下。** 状态目录的布局属于那两个 store
命令，这个文件从不碰它（同一条规矩管着播放列表与历史）。而封面是 CDN 字节的缓存 ——
0.15s 就能重造、按别人的时间表过期 —— 本来就不是状态；这个文件里其它每一个临时文件也都在
那里。文件名不用哈希：bash 3.2 没有内置哈希，`shasum`/`md5` 的跨平台调用是又一个要养的分歧，
而 url 的字母数字尾巴已经够唯一。列数烘进**文件名**，于是想画的人不必再问一次图有多宽。

**这一节明知没有的那一格是「画成什么样」，不是「发没发」** —— 两者的差别就是
`capture-pane` 与 `pipe-pane` 的差别，这段话原先把它写错了。`capture-pane` 拿到的是
**字符网格**，而贴图不在网格里，所以照着它写的检查永远不可能红；`pipe-pane` 抄的是程序
**写出去的字节**，在 tmux 决定拿它们怎么办之前，所以哪怕 tmux 一个都不转发，转义序列照样读得到。
套件因此证得了三件事：**发没发**（走了一趟光标就该有一次贴图上线）、
**该不发的时候没发**（`#` 重画整帧却不动封面依赖的任何一项 —— 同一个文件、同一条右边界、
上方同样多的行 —— 于是"每帧重传"的实现与"什么都不做"的实现被一次按键分开），
以及**画图有没有弄坏这个 TUI**。

**真正证不了的是渲染本身**：位置、缩放、是不是那张图 —— 那是像素不是字节，两个套件都不碰。
**「实测」而非「已证」的一条**同属此类："退出后终端不残留图像"只能由一个人盯着一个真
kitty/Ghostty 窗口看 —— 它依赖的 `image_clear` 与 trap 都在上面，但那一眼本身没有自动化的替身。
